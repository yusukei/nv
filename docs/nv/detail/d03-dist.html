nv 詳細仕様

D03. スキル・配り方・更新・試験・確かめていないこと

エージェント用のスキル、配り方、self update、出力と終了コード、試験と確かめていないこと。DES-009〜013。

設計

DES-009エージェント用のスキル REQ-008

  • スキルの中身(SKILL.md)は、nv の実行ファイルに埋め込む(include_str!)。nv の版とスキルの中身が必ず一致する
  • スキルは 2 つ: nv と wrangler-compose。入れる先は ~/.agents/skills/<名前>/(常に)と ~/.claude/skills/<名前>/(~/.claude があるときだけ)
  • nv が入れたことの印として、各フォルダに .nv-managed(入れた nv の版)を置く。uninstall skill は印のあるフォルダだけを消す。入れる先に印の無い同じ名前のフォルダがあれば、上書きせずにそのことを示す(利用者が自分で置いたものを壊さない)
  • 入れるときは、tmp/ に作ってから付け替える(2 回打っても 1 つ)
  • 成り立たない場合: Codex が置き場を変えたら、入れても効かない。置き場は 1 か所の定数にして、変わったら nv の版を上げて直す

DES-010配り方 REQ-009

  • Release に置くもの: 実行ファイルそのもの(包まない)を、nv-<ターゲット>[.exe]・wrangler-compose-<ターゲット>[.exe] の名前で。検証値の一覧 SHA256SUMS。版の文字列だけを書いた VERSION
  • ターゲット: x86_64-pc-windows-msvc・aarch64-apple-darwin・x86_64-apple-darwin・x86_64-unknown-linux-musl(静的にリンクし、どの Linux でも動く)
  • GitHub Actions: v* のタグの push で、Windows・macOS・Ubuntu の機械で組み、最後の 1 つの仕事が SHA256SUMS と VERSION を作って Release に上げる。タグの版と Cargo.toml の版が違えば失敗させる
  • 最初の導入は README に、OS ごとの取り方(macOS・Linux は curl、Windows は PowerShell の Invoke-WebRequest)を書く
  • 却下: .tar.gz・.zip に包む(展開の手間が増えるだけで、単体の実行ファイルには得が無い)
  • 成り立たない場合: macOS でブラウザから取ると、隔離の印が付き、署名の無い実行ファイルは止められる。README の取り方は curl にする(印が付かない)。署名と公証は範囲外

DES-011self update REQ-010

  1. 取り先(ビルドの時に NV_RELEASE_BASE で決める。CI は https://github.com/<持ち主>/<リポジトリ>/releases/latest/download)から VERSION を取り、いまの版と比べる。新しくなければ「最新」と示して終わる。--check はここで終わる
  2. SHA256SUMS と、自分のターゲットの nv-…(同じフォルダに wrangler-compose があればそれも)を、入れ替える実行ファイルと同じフォルダの一時ファイルへ取り、照らす。1 つでも合わなければ全部消して止まる
  3. 入れ替え: いまのファイルを <名前>.old へ名前を付け替え、取ったものを本来の名前へ付け替える(Windows でも、動いている実行ファイルの名前の付け替えはできる)。2 つ目の付け替えに失敗したら、.old を戻す
  4. 新しい nv を nv install skill --if-installed(内部の引数)で起こし、印のあるスキルだけを新しい中身で入れ直す(古い nv は新しいスキルの中身を持たないため)
  5. nv は起動のたびに、自分のフォルダの .old を消す(Windows では入れ替えたときに消せないため)
  • 却下: GitHub の API(/repos/…/releases/latest)で版を調べる(認証の無い呼び出しの回数制限があり、プロキシの網で別の口が要る。latest/download なら資産と同じ口で済む)
  • 成り立たない場合: 実行ファイルのフォルダに書けない(管理者の場所に置いた)と入れ替えられない。そのときは書けないことと場所を示して止まる

DES-012出力と終了コード REQ-004・REQ-007

  • nv 自身の出力は標準エラーに出す。標準出力は動かしたコマンドのものだけにする
  • 言語(REQ-011)は起動のはじめに 1 度だけ決める: NV_LANG → LC_ALL・LC_MESSAGES・LANG(Unix)→ macOS は defaults read -g AppleLanguages の先頭 → Windows は GetUserDefaultUILanguage の主言語。ja で始まれば日本語、決まらなければ英語
  • メッセージは、出す箇所に日本語と英語を並べて書く(tr!("日本語", "English"))。訳の表を別のファイルに持たない(訳し漏れと、鍵と文のずれを起こさない)
  • --help の説明は、組んだコマンドの定義に日本語の説明を当て直してから引数を読む。clap 自身の出すエラーの文(未知の引数など)は英語のまま
  • Windows の端末へは、Rust の標準の出力が UTF-8 を端末の文字に変えて書くので日本語は化けない(Rust の資料: 端末への出力は UTF-8 だけを受ける)。ファイルやパイプへは UTF-8 のまま書く
  • 却下: 英語だけ(日本語の環境の利用者に読みにくい。利用者の決定)。却下: 日本語だけ(公開のリポジトリで、日本語を読めない人が使えない)
  • nv 自身が止まったときの終了コードは 2。動かしたコマンドの終了コードはそのまま返す

DES-013試験

  • 単体の試験: 版の読み取り、SHASUMS256.txt の照合、ロックファイルの bin の引き方、入口が JavaScript かの見分け
  • AC-002・AC-010 の検証値が合わない側は、単体の試験(照合)で確かめる。本物の取り先での取得は CI の 1 つの仕事(NV_HOME を一時のフォルダにして実行ファイルを動かす)で行う
  • CI は Windows・macOS・Linux の 3 つで回す。エージェントの振る舞い(AC-008 の 3 回)は手で確かめる

確かめていないこと(作る前に確かめる)

  • Windows で、動いている実行ファイルの名前の付け替えが、権限の無い利用者でもできるか(一般に知られた動きだが、実機で確かめる)
  • npm の npm_config_cache が、npm ci・npm install の両方でキャッシュの場所を変えるか
  • macOS の隔離の印が、curl で取ったファイルに付かないこと
  • GitHub の releases/latest/download/<資産> が、リポジトリの持ち主と名前が決まった後の公開リポジトリで期待どおり転送されること(リポジトリの名前が決まるまで、取り先は仮)
