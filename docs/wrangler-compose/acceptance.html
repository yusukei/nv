wrangler-compose 受け入れ条件

要求仕様の REQ-001〜019 を満たしたと言える条件。--env local の条件は Cloudflare に触れずに確かめ、CI(Windows・macOS・Linux)で毎回動かす。リモートの条件は、試験用の Cloudflare アカウントの使い捨ての環境(--env ac-<日時>)で、利用者の許可を得てから確かめる。本番の環境では行わない。

試験用のプロジェクト

要求仕様の「compose ファイルの例」と同じ形のプロジェクト(web・api の 2 つの Worker、db(D1)・files(R2)・cache(KV)・jobs(Queue)、api の Durable Object Counter、シークレット stripe-key)。api は、受けた要求で D1・R2・KV に書き、Queue に送り、Durable Object を数え、受け手として Queue のメッセージを KV に書く。web は api を呼んだ結果と、シークレットがあるかを返す。

AC-001compose ファイル REQ-001

  • 試験用のプロジェクトの根でも、api/ の中でも、--env local up が同じ compose ファイルを使う(上へたどる)
  • name を省くと、compose ファイルのあるフォルダ名がプロジェクトの名前として出る
  • x- で始まるキーを一番上とサービスの中に書いても動く
  • 知らないキー(image・environment など)、型に合わないキー(d1 に ports)、無いサービスへの depends_on・bindings、depends_on の輪、.yaml と .yml の両方があることは、どれも何もせずに止まり、場所(services.web.image など)と理由が出る
  • -f を渡すと止まる

AC-002サービスの型 REQ-002

  • worker・d1・r2・kv・queue のサービスが、手元とリモートの両方で、それぞれ Worker・D1・R2 バケット・KV 名前空間・Queue として建つ
  • 知らない type は止まる
  • vars・routes・crons・compatibility_date・compatibility_flags・assets がデプロイした Worker に効いている(Worker から env の値が見え、ルートと Cron が Cloudflare に入り、静的なファイルが配られる)

AC-003つながり REQ-003

  • 手元とリモートの両方で、web から api へのサービスバインディング、api から D1・R2・KV・Queue へのバインディング、別の Worker からの api.Counter の Durable Object が通る
  • api が jobs に送ったメッセージを、consumes: [jobs] の Worker が受け取る
  • depends_on に書いていない相手でも、相手が先に建つ
  • 相手の durable_objects に無いクラスを指すと止まる

AC-004シークレット REQ-004

  • .env.<環境> の STRIPE_KEY が、手元でもリモートでも、secrets に並べた Worker からだけ見える
  • 値を変えて up を打つと、Worker の値が変わる。compose ファイルからシークレットを消して up を打つと、Worker からも消える
  • 値が無いと、何もせずに止まり、無い変数の名前が出る

AC-005変数の展開 REQ-005

  • routes: ["${WEB_DOMAIN}"] が、--env ごとに、その .env.<環境> の値に展開される。同じ名前の環境変数があればそちらが使われる
  • ${VAR:-既定} は値が無いと既定になり、${VAR:?説明} は値が無いとその説明で止まる。$$ は $ になる
  • 既定の無い変数が 2 つ無いと、2 つの名前がまとめて出て止まる
  • git の中で .env.staging が .gitignore で外れていない、またはすでに git に入っていると、何もせずに止まる

AC-006環境と資源の名前 REQ-006

  • --env ac-1 up のあと、Cloudflare に <プロジェクト>-ac-1-<サービス> の名前の Worker と資源ができている
  • 続けて --env ac-2 up を打つと、ac-1 と別の Worker と資源ができ、互いのデータが混ざらない
  • サービスに name を書くと、その名前の資源を使う。その名前の資源がすでにあれば、作らずにそれを使い、中身は変わらない
  • 手元の記録(.wrangler/ の下)を消してから up を打っても、同じ資源につながる(新しく作らない)

AC-007Wrangler の設定ファイル REQ-007

  • Worker のフォルダに Wrangler の設定ファイルが無くても、手元とリモートで動く
  • 組み立てのためのキー(main・build・rules など)だけを書いた設定ファイルを置くと、その組み立て方で組まれる
  • vars・d1_databases・routes・env・compatibility_date などを書くと、何もせずに止まり、そのキーと compose ファイルのどこに書くかが出る
  • どの操作のあとも、プロジェクトのファイルが変わっていない(git status に差分が出ない。.wrangler/ と backups/ は .gitignore で外してある前提)

AC-008up REQ-008

  • 何も無い環境に up を打つと、資源ができ、移行が当たり、Worker がデプロイされ、web の URL が api を通した応答を返す
  • 何も変えずにもう 1 度 up を打つと、何も変わらず(Worker の版が増えない)、変えるものが無いことが出る
  • api のコードだけを変えて up を打つと、api だけがデプロイされる
  • 移行を 1 つ足して up を打つと、足した移行だけが当たる。確認を求められない
  • 失敗する移行を足して up を打つと、その D1 を使う Worker はデプロイされず、どのサービスのどの移行で止まったかが出る
  • up web は api とその資源も建てる
  • compose ファイルからサービスを消して up を打つと、残った Worker が示される。--remove-orphans を付けると Worker が消える。資源は消えない

AC-009down REQ-009

  • リモートで down を打って環境名を打ち直すと、Worker が無くなり、資源の中身は変わらない。そのあとの up で、前と同じ中身が見える
  • down web は web だけを下ろし、api は応え続ける
  • down --purge で打ち直すと、Worker と資源が中身ごと無くなる。down --purge api は、web もつながる資源(files)を消さずに止まる
  • 打ち直した名前が違う、または入力を流し込んで打つと、何も消えない
  • 手元で、ほかの端末から --env local down を打つと、確かめなしに止まる。--env local down --purge は local の打ち直しで手元のデータが消える

AC-010ps REQ-010

  • up のあとの ps に、すべてのサービスがあり、Worker の URL・資源があること・未適用の移行が 0 であることが出る
  • 移行を足したあとの ps に、未適用の移行の数が出る。down のあとの ps に、Worker が無いことが出る
  • 手元で up が動いている間の --env local ps に、動いていることと手元の URL が出る
  • ps のあと、何も変わっていない

AC-011logs REQ-011

  • リモートで logs -f を打ったまま web を呼ぶと、web と api の console.log の行が、頭にサービス名を付けて出る
  • logs api は api の行だけを出す
  • 手元で up が動いている間、ほかの端末の --env local logs -f に同じ形で出る

AC-012backup・restore REQ-012

  • backup のあと、backups/<環境>/<日時>/ に、D1 の SQL(移行の履歴を含む)・R2 のすべてのオブジェクトとメタデータ・KV のすべてのキーと値とメタデータと期限・目録がある。数と大きさが環境と一致する
  • リモートの環境の控えを --env local restore --drop で戻すと、手元の D1・R2・KV が控えと一致し、戻す前に控えを取った環境名が出る。手元の控えを別のリモートの環境へ戻しても同じ
  • 控えのあとに移行を足したコードで戻すと、足した移行だけが当たる
  • 戻す先に中身があって --drop が無いと、何も変わらずに止まる
  • git の中で backups/ が外れていないと、何も書き出さずに止まる。書きかけの控えを渡すと止まる
  • API キーを用意しなくても、リモートの backup・restore が動く

AC-013dry-run REQ-013

  • --dry-run up のあと、Cloudflare の Worker・資源・シークレットと、手元のファイルが変わっていない。作る資源・デプロイする Worker・当てる移行・入れるシークレットの名前・展開した変数が出る(シークレットの値は出ない)
  • --dry-run down --purge・--dry-run restore --drop は、端末でなくても動き、何も消えない
  • 本番の操作が止まる条件(変数が無い、.env が git に入る、など)では dry-run も止まる

AC-014手元(local) REQ-014

  • Cloudflare にログインしていない PC で、--env local up が試験用のプロジェクトのすべてを動かす。web は 8787、api は 8788 で応える
  • web と api から同時に同じ D1 へ 100 回ずつ書いても、200 行がすべて入る(同時の書き込みで失われない)
  • api のコードを変えると、打ち直さずに新しいコードが応える
  • 手元の S3 互換の口へ、up が示した鍵で、AWS SDK から一覧・書き込み・読み出しができ、AWS SDK で作った署名付き URL で鍵の無い curl から PUT・GET ができる。署名を変えると拒まれる
  • Ctrl+C で止めたあと、手元のプロセスが残っていない。down のあと up を打つと前のデータが見え、down --purge のあとは空になる
  • 動いている間に同じプロジェクトでもう 1 つ --env local up を打つと、何もせずに止まる

AC-015手で行う段取りを持たない REQ-015

  • 試験用のプロジェクトを新しく clone した PC で、wrangler login と .env.<環境> を置くことのほかに何もせず、--env <環境> up で動く Worker ができる(手元・リモートとも)
  • 受け入れの間に、Cloudflare のダッシュボードで行った段取りが 1 つも無い

AC-016安全 REQ-016

  • どの操作でも、画面・ログ・控えの目録にシークレットの値が出ない(失敗したときも)
  • まだ無い環境への初めての up で、新しく作ることが出て確かめを求められる。答えが「いいえ」なら何もできない

AC-017手元と本番の違いの知らせ REQ-017

  • routes と crons のあるプロジェクトで --env local up を打つと、動かす前に、手元ではルートが効かないことと、Cron の試し方が出る
  • そのどちらも無いプロジェクトでは何も出ない

AC-018Wrangler と nv REQ-018

  • 使われる Wrangler の版が、プロジェクトの package-lock.json の版と一致する
  • Worker のフォルダに自分の package.json があると、その依存が入ってから組まれる
  • nv が無い・Wrangler が無い・古いと、何もせずに止まり、入れ方が出る

AC-019配り方・表示の言語 REQ-019

  • Node も npm も入っていない Windows と macOS で、同じフォルダに置いた wrangler-compose と nv だけで、--env local up が動く
  • 日本語の PC では日本語、NV_LANG=en では英語で出る。どちらでも、打ち直しの確かめは環境名で進む
