wrangler-compose 受け入れ条件

確かめは、試験用の Cloudflare アカウントの使い捨ての環境(Worker・D1・R2)で行う。本番の環境では行わない。Windows x64 と macOS arm64 の両方で確かめる。

この頁は、Wrangler の設定ファイルを正とした前の版の要求(0.1 系)に対する受け入れ条件。要求仕様は compose ファイルを正とする形に書き直したので、この頁も合わせて書き直す。それまでは、確かめた事実と実測の記録として読む。

AC-001環境の指定 REQ-001

  • --env staging up・-e staging up・CLOUDFLARE_ENV=staging を付けた up が、同じ環境に同じ結果を出す。--env と CLOUDFLARE_ENV の両方を付けたら --env の環境に出る
  • 環境を指定せずに up・down・backup・restore を打つと、Cloudflare に何も起きずに止まり、環境の指定が要ると出る
  • 設定に無い環境名(設定の環境名の略や別名を含む)を指定すると、何も起きずに止まり、設定にある環境名が並ぶ

AC-002設定の持ち主と Wrangler の呼び方 REQ-002

  • wrangler-compose のリポジトリと、使う側のプロジェクトに、Wrangler の設定ファイル以外の環境の定義が無い
  • wrangler-compose が動かす Wrangler の版が、プロジェクトの package-lock.json の版と一致する(PATH にほかの版の Wrangler や nv があっても。使う nv は wrangler-compose と同じフォルダのもの)
  • どの操作のあとも、プロジェクトのファイルが変わっていない(git status に差分が出ない)。D1・R2 を新しく作った up を端末から打ったときも同じ
  • 同じフォルダに nv が無い、またはプロジェクトの依存に Wrangler が無いと、何も起きずに止まり、入れ方が出る
  • プロジェクトの Wrangler が要る版より古いと、何も起きずに止まり、要る版が出る

AC-003build REQ-003

  • --env staging build のあと、Cloudflare の Worker・D1・R2 が変わっていない
  • 設定のビルドのコマンドが失敗すると、build も失敗し、理由が出る

AC-004up REQ-004

  • まだ何も無い環境(D1 を名前だけで書いた設定)に up を打つと、Worker・D1・R2 ができ、D1 にすべての移行が当たり、Worker の URL が応える
  • D1 がすべてある環境で、移行を 1 つ足して up を打つと、足した移行だけが当たり、新しいコードが出る。確認を求められない
  • D1 がすべてある環境で、失敗する移行を足して up を打つと、デプロイは行われず(前のコードのまま)、どの移行で止まったかが出る
  • まだ無い D1 がある環境で、失敗する移行を入れて up を打つと、デプロイは済み、移行が当たっていないことと、どの移行で止まったかが出る
  • 設定に database_id を書いた D1 が無いと、up は何もデプロイせずに止まり、その D1 の名前と ID が出る
  • .env.staging があると、up のあと、そこに書いたシークレットが Worker に入っている。WRANGLER_COMPOSE_ で始まる値は入っていない。ファイルが無ければ、前のシークレットのまま
  • .env.staging から 1 つ消して up を打つと、そのシークレットは Worker に残り、その名前が示される

AC-005down REQ-005

  • down を打つと、消す前に、Worker と一緒に消えるもの(シークレット・ルート・カスタムドメイン・Cron・Durable Objects)が出る
  • 環境名を正しく打ち直すと、Worker が無くなり、D1 の表の中身と R2 のオブジェクトは変わらない
  • 打ち直した名前が違うと、何も消えない
  • 入力を流し込んで(echo staging | wrangler-compose --env staging down など)打つと、何も消えずに止まる
  • down のあと up を打つと、Worker が戻り、down の前と同じ D1・R2 の中身が見える

AC-006down --purge REQ-006

  • 正しい API キーを渡して down --purge で環境名を打ち直すと、Worker・D1・R2 バケットが無くなる(オブジェクトのあるバケットも)
  • API キーを渡さない・誤ったキーを渡すと、警告が出て、Worker・D1・R2 はどれも変わらない
  • 消す前に、Worker 名・D1 の名前・バケットの名前とオブジェクトの数が出る
  • 入力を流し込んで打つと、何も消えずに止まる
  • 設定に database_id を書いた D1 があると、消す前に、消したあとの up がその D1 を作り直さないことが出る
  • 名前だけで書いた設定の環境を down --purge したあと up を打つと、空の D1・R2 が新しくでき、移行が当たる
  • 途中で止めると(網を切るなど)、何を消して何が残っているかが出る

AC-007backup REQ-007

  • backup のあと、プロジェクトの backups/<環境名>/<日時>/ に、D1 の SQL(移行の履歴を含む)・R2 のすべてのオブジェクト・目録がある。オブジェクトの数と大きさが環境と一致する
  • backup <別のフォルダ> を打つと、そのフォルダの <環境名>/<日時>/ に同じものができ、プロジェクトの backups/ には何もできない
  • git の中のプロジェクトで backups/ が .gitignore で外れていないと、何も書き出されずに止まる。git の外の書き出し先なら止まらない
  • API キーを渡さない・誤ったキーを渡すと、警告が出て、書き出し先に何もできない
  • 書き出しの途中で止めると、残ったフォルダは書きかけと分かり、restore に渡すと止まる
  • 書き出せない表を持つ D1 があると、その D1 と理由が出て止まり、完成した控えはできない

AC-008restore REQ-008

  • 別の環境に up したあと、AC-007 の控えを restore --drop して環境名を打ち直すと、D1 の表の中身と R2 のオブジェクト(キー・中身・内容の種類)が控えと一致する。up でできていたオブジェクトや行は残らない
  • 控えを取ったあとに移行を 1 つ足したコードで、上と同じことをすると、戻したあとに足した移行だけが当たり、Worker が応える
  • --drop を付けずに、中身のある(up で移行が当たった)戻す先へ restore すると、何も変わらずに止まり、空でないものと --drop のことが出る
  • restore --drop を打つと、消す前に、D1 ごとの表の数とバケットごとのオブジェクトの数と、戻している間に欠けたデータが見えることが出る。打ち直した名前が違う、または入力を流し込んで打つと、何も変わらずに止まる
  • 戻す先の D1・バケットが無いと、何も変わらずに止まり、先に up を打つよう出る
  • 書きかけの控え、または移行の履歴の入っていない控えを指定すると、何も変わらずに止まる
  • API キーを渡さない・誤ったキーを渡すと、警告が出て、何も変わらない(--drop でも)
  • 途中で止めると、何を消し、何を入れて、何が残っているかが出る

AC-009秘密の扱い REQ-009

  • up・down・down --purge・backup・restore のどれでも、画面・ログ・目録に、API キーとシークレットの値が出ない(失敗したときの出力も含む)
  • .env.staging と環境変数に別の API キーを入れると、環境変数のキーが使われる
  • アカウント ID や管轄を .env.staging に書かなくても、backup が動く
  • git の中のプロジェクトで、.env.staging が .gitignore で外れていない、またはすでに git に入っていると、up・down --purge・backup・restore は何も起きずに止まる。git の外のプロジェクトでは止まらない

AC-010配り方と更新 REQ-010

  • Node も npm も入っていない Windows と macOS で、同じフォルダに置いた wrangler-compose と nv の実行ファイルだけで、up が動く(Node と Wrangler は nv が揃える)
  • 版のタグを push すると、その版の GitHub の Release に、nv と並んで OS ごとの wrangler-compose の実行ファイルと検証値が並ぶ
  • wrangler-compose self update・wrangler-compose install skill は無い。更新とスキルは nv の AC-010・AC-008 で確かめる

AC-011dry-run REQ-011

  • --dry-run up のあと、Worker の版・D1 の移行の履歴・シークレット・設定ファイルが変わっていない。当てる予定の移行の名前と、入れる予定のシークレットの名前(値は出ない)が出る
  • --dry-run down・--dry-run down --purge のあと、Worker・D1・R2 はどれも変わっていない。消す予定のもの(--purge ならオブジェクトの数まで)が出る。端末でなくても(入力を流し込んでも)動く
  • --dry-run backup のあと、書き出し先に何もできていない。書き出す D1 とバケットとオブジェクトの数が出る
  • --dry-run restore --drop のあと、D1 と R2 の中身が変わっていない。消す予定のものと戻す予定のものが出る
  • 本番の操作が止まる条件(.env が git に入っている、API キーが無い、書きかけの控え、など)では、dry-run も同じに止まる
  • どの dry-run も、終わりに何も変えていないことが出る

AC-012表示の言語 REQ-012

  • OS の言語が日本語の PC で、--env を付けずに up を打つと日本語のエラーが出る。--dry-run up の示す内容と --help の説明も日本語
  • NV_LANG=en を付けると英語で出る
  • 日本語の表示でも、down の確かめで環境名(例: testing)を打てば進む

手元の環境(local)

AC-013〜AC-017 は Cloudflare に触れずに確かめる。ログインしていない PC でも通る。R2 のバインディング BUCKET と、移行のフォルダを持つ D1 のバインディング DB を一番上の階層に書いた試験用のプロジェクトで行う。Windows x64 と macOS arm64 の両方で確かめる。

AC-013手元の環境 local REQ-013

  • Cloudflare にログインしていない PC で、--env local up・-e local up・CLOUDFLARE_ENV=local を付けた up が、同じに手元で動く
  • 設定に env.local を足すと、--env local のどの操作も何もせずに止まり、名前がぶつかることが出る
  • --env local up で Worker が D1 に書いた行が、nv run wrangler d1 execute DB --local --command "SELECT …" で見える
  • .env.local に FOO=bar を書いて --env local up を打つと、Worker から env.FOO が bar に見える
  • git の中のプロジェクトで .env.local が .gitignore で外れていないと、--env local up は何も起きずに止まる
  • --env local のどの操作のあとも、プロジェクトのファイルが変わっていない(git status に差分が出ない。.wrangler/ と backups/ は .gitignore で外してある前提)

AC-014local の up REQ-014

  • 手元のデータが無い状態で --env local up を打つと、手元の D1 にすべての移行が当たり、Worker の URL が応える。確認を求められない
  • 移行を 1 つ足して up を打ち直すと、足した移行だけが当たる
  • 失敗する移行を足して up を打つと、Worker は動かず、どの移行で止まったかが出る
  • 動いている間に Worker のコードを変えると、打ち直さずに新しいコードが応える。console.log の出力と要求ごとの記録が画面に出る
  • 動き出すと、Worker の URL、BUCKET の手元の S3 の口の URL・バケット名・手元の鍵が出る
  • Ctrl+C で止めたあと、Worker の URL が応えず、手元の Worker のプロセス(workerd)が残っていない
  • 動いている間に、同じプロジェクトでもう 1 つ --env local up を打つと、何もせずに止まり、動いているものの URL が出る
  • 設定の dev.port を使われているポートにすると、理由が出て止まる
  • 設定に dev.ip が無いとき、ほかの機械から Worker と手元の S3 の口に届かない(127.0.0.1 だけで待ち受けている)

AC-015手元の S3 の口 REQ-015

  • --env local up の間、示された口の URL と手元の鍵で、AWS SDK(@aws-sdk/client-s3、パス形式、地域 auto)から ListObjectsV2・PutObject・GetObject・DeleteObject が通る
  • Worker が env.BUCKET.put で置いたオブジェクトが口の一覧に出て、口で置いたオブジェクトが env.BUCKET.get で読める
  • AWS SDK で作った署名付き URL(PUT と GET)に、鍵を持たない curl から書き込み・読み出しができる。署名を 1 文字変えた URL は拒まれる(403)
  • 違う鍵で署名した要求は拒まれる(401 か 403)
  • 手元の鍵は、設定の local_dev.experimental_s3_credentials、.env.local の WRANGLER_COMPOSE_R2_*、決まった値の順に選ばれる(それぞれを書いた・消した状態で、up の示す鍵と、通る鍵が一致する)。環境変数と .env.local の両方にあれば環境変数の鍵が使われる
  • up のあと、Wrangler の設定ファイルが変わっていない

AC-016local の down REQ-016

  • ほかの端末で --env local up が動いているとき、--env local down を打つと、確かめを求められずに止まり、手元のプロセスが残らない。そのあと up を打つと、前と同じ D1 の行と R2 のオブジェクトが見える
  • up が動いていないときに --env local down を打つと、動いていないことが出て、0 で終わる
  • --env local down --purge を打つと、消す前に置き場のフォルダ・D1 ごとの表の数・バケットごとのオブジェクトの数が出る。local を打ち直すと .wrangler/state/ が無くなり、そのあとの up で空の D1 に移行が当たる
  • 打ち直した名前が違う、または入力を流し込んで打つと、何も消えない
  • up が動いているときに down --purge を打つと、先に up が止まってから消える
  • down --purge のあと、.wrangler/ の state のほかのものと、プロジェクトのファイルが変わっていない

AC-017local の backup・restore REQ-017

  • up が動いていないときに --env local backup を打つと、backups/local/<日時>/ に D1 の SQL(移行の履歴を含む)・R2 のすべてのオブジェクト・目録ができ、終わったあとに手元のプロセスが残っていない。API キーを渡さなくても動く
  • up が動いているときに同じことをしても、同じ控えができ、up は動いたまま
  • --env local down --purge のあと、上の控えを --env local restore すると(up を打っていなくても)、D1 の表の中身と R2 のオブジェクト(キー・中身・内容の種類)が控えと一致する
  • 試験用の Cloudflare の環境で AC-007 のとおり取った控えを --env local restore --drop で戻すと、手元の D1 と R2 がその控えと一致し、戻す前に控えを取った環境名が出る
  • 控えを取ったあとに移行を 1 つ足したコードで --env local restore すると、足した移行だけが手元の D1 に当たる
  • 手元に中身があるときに --drop を付けずに restore すると、何も変わらずに止まる。--drop で local を打ち直すと入れ替わる。入力を流し込むと何も変わらない
  • 手元の控えを試験用の Cloudflare の環境へ restore --drop すると、その環境の D1 と R2 が手元の控えと一致する
  • --dry-run を付けた --env local の backup・restore・down --purge のあと、手元のデータと書き出し先が変わっていない

複数の Worker(compose ファイル)

AC-018〜AC-021 は、web(api へのサービスバインディングと、api の Durable Object への script_name を持つ)と api(D1 DB と R2 FILES を持つ)の 2 つのサービスを持つ試験用のプロジェクトで行う。web も同じバケットを FILES で使う。Cloudflare に触れるもの(AC-019)は、試験用のアカウントで、利用者の許可を得てから行う。

AC-018compose ファイル REQ-018

  • 要求仕様の例と同じ wrangler-compose.yaml を、compose の根でも web/ の中でも、--env local up で読める(上へたどる)。-f は受けず、渡すと止まる
  • wrangler-compose.local.yaml(サービスを 1 つ足し、ポートを変えたもの)を置くと、--env local up はそちらだけを使い(共通のファイルの中身は混ざらない)、使ったファイルの名前が出る。--env staging up は wrangler-compose.yaml を使う
  • どの操作も wrangler-compose --env <環境名> [--dry-run] <操作> [サービス…] の形で打てる(wrangler-compose --env staging up・wrangler-compose --env local up web など)。環境の指定が無ければ、compose ファイルがあっても AC-001 と同じに止まる
  • build の文字列の形と、context・config の形の両方で、同じサービスになる。config を省くと wrangler.jsonc・wrangler.json・wrangler.toml の順に探す
  • name を省くと、compose の根のフォルダ名がプロジェクトの名前として出る
  • depends_on の短い書き方(一覧)と、長い書き方(condition: service_started)の両方を受ける。condition: service_healthy は止まる
  • x- で始まるキー(一番上・サービスの中)を書いても動く
  • image・environment・volumes などのキーを書くと、何もせずに止まり、そのキーと理由が出る
  • depends_on の輪、無いサービスへの depends_on、同じ設定ファイルを指す 2 つのサービス、wrangler-compose.yaml と .yml の両方があること、"8787:8788" のような違う 2 つのポートは、どれも何もせずに止まり、理由が出る
  • compose ファイルの無いプロジェクトでは、これまでの AC-001〜AC-017 がそのまま通る

AC-019複数の Worker と Cloudflare REQ-019

  • 何も無い環境に --env testing up を打つと、api が先に、web が後にデプロイされ、web の URL が api を通した応答を返す
  • --env testing up web は api も建てる。--env testing down web は web だけを下ろし、api は応え続ける
  • api の設定にだけ env.testing が無いと、何も起きずに止まり、api の名前が出る
  • web に api へのサービスバインディングがあるのに depends_on から api を外すと、知らせが出る
  • 2 つのサービスが共有する D1 に、移行が 1 度だけ当たる(d1_migrations の行が 1 組)。2 つのサービスで移行のフォルダを違えると、何も起きずに止まる
  • down --purge web は、api も使うバケットを消さずに止まり、そのことが出る
  • backup の控えに、共有するバケットのオブジェクトが 1 組だけ入り、目録にそれを使う 2 つのサービスが書かれている。その控えを別の環境へ restore --drop すると、2 つのサービスから同じ中身が見える
  • web のフォルダの .env.testing のシークレットは web の Worker にだけ入る

AC-020複数の Worker と local REQ-020

  • --env local up で、web は ports の 8787、api は 8788 で応える。web からのサービスバインディングの呼び出しと、api の Durable Object の呼び出し(script_name)が通る
  • api が FILES に置いたオブジェクトが、web の FILES と、どちらのポートの手元の S3 の口からも見える
  • api の console.log の行の頭に api が付いて出る
  • ports を書かないサービスは、ほかと重ならない番号で応え、その URL が出る。2 つのサービスが同じポートを書くと、何も起きずに止まる
  • 1 回の Ctrl+C で、すべてのサービスが止まり、手元のプロセスが残らない。ほかの端末からの --env local down でも同じ
  • --env local up web で api も動く
  • Queues の送り手と受け手を別のサービスにしたとき、送ったメッセージを受け手が受け取る

AC-021手元で使えないものの知らせ REQ-021

  • Vectorize と Workers AI のバインディングと、routes・triggers.crons を足したサービスで --env local up を打つと、動かす前に、それぞれが手元でどうなるか(Vectorize は動かない、AI は料金がかかる、ルートは効かない、Cron の試し方)がサービスの名前と一緒に出て、そのあと動き出す
  • --env local --dry-run up でも同じものが出る
  • D1 に remote: true を書くと、本物の D1 につながることと、その ID が出る
  • Durable Objects に remote: true を書くと、Wrangler を動かす前に止まり、理由が出る
  • Hyperdrive の手元の接続文字列が無いと、要る環境変数の名前が出る
  • 表に無い種類のバインディングを持つ設定では、「分からない」と出る
  • 手元で使えないものが無い設定では、何も出ない
