wrangler-compose 受け入れ条件

要求仕様の REQ-001〜019 を満たしたと言える条件。番号は要求と 1 対 1。手元(--env local)の条件は網を切った PC でも確かめられ、CI(Windows・macOS・Linux)で毎回動かす。リモートの条件は、試験用の Cloudflare アカウントの使い捨ての環境(--env ac-1 など)で、利用者の許可を得てから確かめる。本番では行わない。

試験用のプロジェクト

要求仕様の「compose ファイルの例」と同じ形: Worker の web・api、db(D1)・storage(R2。バケット files・uploads の複数形)・cache(KV。省略形)・jobs(Queue)、api の Durable Object Counter、シークレット stripe-key。api は、受けた要求で D1・R2・KV に書き、Queue に送り、Durable Object で数え、受け取った Queue のメッセージを KV に書く。web は api を呼んだ結果と、シークレットがあるかを返す。

AC-001compose ファイル REQ-001

  • プロジェクトの根でも api/ の中でも、同じ compose ファイルが使われる
  • name を省くと、フォルダ名がプロジェクトの名前として出る
  • x- で始まるキーを書いても動く
  • 知らないキー(image など)・型に合わないキー(d1 に ports)・無いサービスを指すもの・depends_on の輪・.yaml と .yml の両方があることは、どれも何もせずに止まり、場所と理由が出る

AC-002サービスの型 REQ-002

  • 5 つの型が、手元とリモートの両方で、それぞれ Worker・D1・R2・KV・Queue として建つ。知らない type は止まる
  • D1・R2・KV・Queue のそれぞれで、省略形のサービスは資源 1 つ、複数形のサービスは並べた数だけ資源になる。1 つのサービスに両方を書くと止まる。別のサービスに同じ名前の資源があっても、別の資源として建つ
  • R2 のバケットの public・cors・lifecycle・notifications・lock・storage_class・jurisdiction が、リモートのバケットの設定に入っている。手元では public・cors・notifications が同じに効き(AC-009 の同じ試験で確かめる)、ほかは効かないことを up が知らせる
  • vars・routes・crons・assets・compatibility_date・compatibility_flags が、リモートに展開した Worker に効いている
  • compatibility_date の無い Worker のサービスは、何もせずに止まる(場所を示す)

AC-003つながり REQ-003

  • 手元とリモートの両方で、web → api の呼び出し、api → D1・R2・KV・Queue、別の Worker から api.Counter の Durable Object が通る
  • api が jobs に送ったメッセージを、consumes: [jobs] の Worker が受け取る
  • depends_on に書いていない相手でも先に建つ。相手に無いクラスを指すと止まる
  • storage.files と storage.uploads が別のバケットとして見える。複数形のサービスを名前だけ(storage)で指すと止まる

AC-004環境ごとの値 REQ-004

  • ${WEB_DOMAIN} が --env ごとにその .env.<環境> の値になる。同じ名前の環境変数があればそちらになる
  • ${VAR:-既定}・${VAR:?説明}・$$ が docker compose と同じに展開される
  • 無い変数が 2 つあると、2 つまとめて出て止まる
  • git の中で .env.staging が外れていない・すでに入っていると止まる

AC-005シークレット REQ-005

  • STRIPE_KEY が、手元でもリモートでも、secrets に並べた Worker からだけ見える
  • 値を変えて up すると変わり、compose ファイルから消して up すると Worker からも消える
  • 値が無いと止まり、無い変数の名前が出る

AC-006環境 REQ-006

  • --env ac-1 up のあと、Cloudflare に Worker は <プロジェクト>-ac-1-<サービス>、資源は <プロジェクト>-ac-1-<資源の名前>(…-ac-1-cache・…-ac-1-storage-files など)の名前でできる。手元では資源の名前(cache・storage-files)のまま。名前が長すぎるときは止まり、name を書くよう出る。続けて --env ac-2 up すると別のものができ、データが混ざらない
  • name を書くとその名前を使い、すでにあればそれを使って中身は変わらない
  • 別の PC(道具の記録が無い)から同じ環境へ up しても、同じものにつながり、新しく作らない
  • 網を切った PC で、--env local のどの操作も動く。リモートの環境の操作の間、手元で動く Worker がリモートの資源に触れていない

AC-007Worker のフォルダ REQ-007

  • Worker のフォルダにコードしか無くても、手元とリモートで動く
  • 組み立てのためのもの(どのファイルから組み立てるか・組み立ての手順)を置くと、その組み立て方になる
  • 振る舞いに関わる設定(つながり・値・ルートなど)を置くと止まり、compose ファイルのどこに書くかが出る
  • どの操作のあとも、プロジェクトのファイルが変わっていない(git status に差分が出ない)

AC-008build REQ-008

  • build のあと、手元にもリモートにも何も建っていない
  • build のあとの --env local up と --env ac-1 up が、どちらも組み立て直さずに同じ組み立てたものを使う
  • 組み立てられないコードでは、どのサービスがなぜかが出て止まる

AC-009up(手元) REQ-009

  • Cloudflare にログインしていない、網を切った PC で、--env local up がすべてを動かす。web は 8787、api は 8788 で応える
  • web と api から同時に同じ D1 へ 100 回ずつ書いても、200 行すべてが入る
  • 同じ試験(R2・D1・KV・Queue・Durable Objects の機能を一つずつ使うもの)を、手元と試験用のリモートの環境の両方に流し、結果が同じになる。違う項目は、手元で使えないものに理由とともに書かれているものだけ
  • r2 のサービスの ports の口で: cors に書いた送り元からの事前確認には許す答えが、ほかの送り元には 403 が返る。署名付きの要求の答えにも、書いた送り元にだけ CORS の見出しが付く。AWS SDK で作った署名付き URL で PUT・GET が通る。public: true のバケットのオブジェクトが http://<バケット名>.localhost:<ポート>/<キー> で内容の種類つきで返り、公開していないバケットは 404
  • R2 のイベント通知: 通知を設定したバケットにオブジェクトを置くと PutObject、消すと DeleteObject のメッセージが、本物と同じ形で数秒のうちに Queue の受け手に届く
  • R2 の試験は、バインディングの API(分割アップロード・条件つき・範囲指定・メタデータを含む)、S3 互換の API(AWS SDK での一覧・書き込み・読み出し・署名付き URL の PUT と GET・署名を変えると拒まれること)、CORS(ブラウザからの署名付き URL での PUT を含む)、公開の URL、イベント通知を含む。ライフサイクル・ロック・保管の種類は、リモートのバケットに設定が入っていることだけを確かめる
  • Queue に 25 件送ると、手元でも本物と同じく、受け手に 10 件ずつ(最大 5 秒待って)届く。受け手が失敗し続けると、手元でも本物と同じく 3 回やり直したあとで止まる
  • コードを変えると、打ち直さずに新しいコードが応える。移行を足して up を打ち直すと、足した移行が当たる
  • Ctrl+C のあと何も残らない。down のあとの up で前のデータが見え、down --purge のあとは空
  • 2 つ目の --env local up は止まる。ほかの端末からの --env local down で止まる

AC-010up(リモート) REQ-010

  • 何も無い環境への up で、資源ができ、移行が当たり、シークレットが入り、Worker が展開され、web が api を通した応答を返す
  • 展開した Worker は、手元で動かしたものと同じ組み立てたもの(同じ要約)である
  • 何も変えずにもう 1 度 up しても何も変わらない。api のコードだけ変えると api だけが展開される
  • 失敗する移行を足すと、その D1 を使う Worker は展開されず、どこで止まったかが出る
  • compose ファイルから消したサービスの Worker は示され、--remove-orphans のときだけ消える。データは消えない

AC-011down REQ-011

  • down で打ち直すと Worker が無くなり、データは残り、そのあとの up で元に戻る
  • down web は web だけを下ろす。down --purge api は、web もつながる files を消さずに止まる
  • down --purge で打ち直すと、データも無くなる。打ち直しが違う・入力を流し込むと、何も消えない(手元の --purge も同じ)

AC-012ps・logs REQ-012

  • ps に、サービスごとの有無・動いているか・URL・未適用の移行の数と、compose ファイルとの違いが出る。ps のあと何も変わっていない
  • logs -f に、web と api の console.log の行が、頭にサービス名を付けて出る(手元・リモートとも)。logs api は api だけ

AC-013backup・restore REQ-013

  • backup のあと、backups/<環境>/<日時>/ に D1・R2・KV のすべてが入り、数と大きさが環境と一致する
  • リモートの控えを --env local restore --drop で戻すと、手元が控えと一致する。手元の控えを別のリモートの環境へ戻しても同じ。戻す前に控えを取った環境が出る
  • 控えのあとに足した移行だけが、戻したあとに当たる
  • 中身がある先への --drop の無い restore、書きかけの控え、git に入る書き出し先は、どれも止まる

AC-014dry-run REQ-014

  • --dry-run up のあと、何も変わっていない。作るもの・展開するもの・当てる移行・入れるシークレットの名前・展開した値が出る(シークレットの値は出ない)
  • 本番の操作が止まる条件では dry-run も止まる

AC-015安全 REQ-015

  • まだ無い環境への初めての up で、新しく作ることが出て確かめを求められ、「いいえ」なら何もできない
  • どの操作でも、画面・ログ・控えにシークレットの値が出ない(失敗したときも)

AC-016手で行う段取りを持たない REQ-016

  • 試験用のプロジェクトを新しく clone した PC で、Cloudflare へのログインと .env.<環境> を置くことのほかに何もせず、手元とリモートの up が動く
  • 受け入れの間に、Cloudflare のダッシュボードで行った段取りが 1 つも無い

AC-017道具のサービス REQ-017

  • up のあと、道具のサービスが利用者のサービスと同じ環境にあり、ps に分けて出る。down のあと無くなる
  • 道具のサービスへ外から要求しても、何も返らない

AC-018手元と本番の違いの知らせ REQ-018

  • routes と crons のあるプロジェクトの --env local up で、動かす前に、手元ではルートが効かないことと定期実行の試し方が出る。どちらも無ければ何も出ない

AC-019配り方・表示の言語 REQ-019

  • Node も npm も入っていない Windows と macOS で、同じフォルダの wrangler-compose と nv だけで --env local up が動く
  • 日本語の PC では日本語、NV_LANG=en では英語で出る。打ち直しは環境名で進む
