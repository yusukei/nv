DES-001作りの全体 REQ-001・REQ-007・REQ-019

  • 流れ: compose ファイルを読む(DES-002) → 値を展開する(DES-003) → サービスの順を決める → 環境ごとに中で使う設定を作る(DES-005) → Wrangler を nv run wrangler … で動かす
  • 道具が作るものは、すべてプロジェクトの .wrangler/compose/ の下に置く(組み立てたもの・中で使う設定・名前の記録・手元のデータ・手元のログ)。プロジェクトのファイルは書き換えない
  • Wrangler は context(省けば compose ファイルのあるフォルダ)の package.json の版を使い、nv run をそのフォルダで動かす。組み立ての見分けに入れるロックファイルも同じフォルダのもの。Worker のフォルダに別の package.json があれば、組み立ての前にそこで nv sync を動かす

DES-002compose ファイルを読む REQ-001・REQ-002・REQ-003

  • YAML を読むクレートを 1 つ足す(serde-saphyr か serde_yaml_ng。作る時点で手入れが続いている方)。手入れの止まった serde_yaml は使わない
  • 値の木に読み、自前で確かめてから型のある形へ移す(x- を許しつつ知らないキーで止まるため)。止まるときは場所と理由を示す
  • サービスの environment・secrets は、値を展開する前に「名前: 値」の対応表へそろえる(並びの NAME=値 は値、名前だけは ${NAME})。シークレットは書いたままの値に変数の参照が無ければ止める(値を表に出さない)
  • 1 つのサービスは 1 つの資源。中では資源の並び(1 つ)として持つ。buckets などの複数形のキーは、サービスを分けるよう示して止める
  • サービスの順: bindings・consumes の相手と depends_on を依存として並べる(決まらないところはファイルの順。輪は止まる)。up に名前を渡せば依存をたどった集まり、down は渡した名前だけ

DES-003値の展開 REQ-004・REQ-005

  • 道具の変数(WC_R2_…_S3)は、展開の時点ではまだ実際の名前が決まらないので、目印の文字で囲んだ仮の値にしておく。サービスを読み終えたあと、Worker の environment の値の中の目印だけを接続先に置き換える。鍵の変数(WC_R2_…_S3_KEY・_S3_SECRET)は同じ目印で secrets の値の中だけを置き換える。目印が置ける場所(接続先は environment、鍵は secrets)の外に残っていれば止める。手元の鍵は .wrangler/compose/local/s3-keys.json から読み、無ければ読み込むときに乱数(鍵 10 バイト・秘密 32 バイト)で作る。ファイルに書く(0600)のは up だけ(--dry-run は何も変えない)。リモートでは鍵の変数に値が無いので、${変数:-…} の既定として使われずに残れば止める。リモートの実際の名前は DES-004 と同じ決め方(<プロジェクト>--<環境>--<name、無ければサービスの名前>)、アカウントは .env.<環境> の CLOUDFLARE_ACCOUNT_ID
  • docker compose の展開の決まり(${VAR}・${VAR:-既定}・${VAR-既定}・${VAR:?説明}・${VAR?説明}・$VAR・$$)を自前で書く。展開するのは文字列の値だけで、型の確かめの前に行う
  • 値は環境変数 → .env.<環境>。無い変数は集めてからまとめて示す(シークレットの変数も同じ一覧に入れる)。$5・${}・閉じていない ${ など書き方の誤りは、docker compose と同じく止める($ そのものは $$)
  • x- で始まるキーは、どの階層でも展開の前に取り除く。真偽・数の欄は、展開で文字列になった "true"・"600" も受ける
  • .env.<環境> の読み方も docker compose に合わせる: 引用符の無い値は # の前まで、'…' は書いたまま、"…" は複数行にでき \n などを文字にし、閉じた引用符のあとは注釈。引用符の無い値と "…" の中の ${VAR} は、環境変数とそれより前に書いた値から展開する
  • シークレットの値は、表に出す場面(--dry-run など)で伏せる

DES-004実際の名前と見つけ直し REQ-006

  • 実際の名前は、Worker も資源も <プロジェクト>--<環境>--<name、無ければサービスの名前>。手元では、資源はサービスの名前のまま、Worker は DES-020 の名前。Cloudflare の名前の決まりに合わなければ止まる。この環境のものは、名前が <プロジェクト>--<環境>-- で始まるものだけとして扱う(Cloudflare の一覧を名前の頭で絞る。PC の記録には頼らない)
  • 道具は ID を覚えない。操作のたびに名前で Cloudflare を引き直す(Worker・D1・KV・R2(使う管轄ごと)・Queue・Durable Object の名前空間の一覧)ので、別の PC からでも同じものにつながる。無ければ作り、あれば使う。道具が覚えるのは、前回上げた Worker の要約(.wrangler/compose/<環境>/deployed.json。変わっていない Worker を上げないためと、compose から消えた Worker を見つけるため)とデータのサービスの合言葉だけで、失っても上げ直すだけで結果は変わらない
  • 一覧・作成・設定は Cloudflare の API で行う(Wrangler の一覧の多くは JSON で答えないため)。資格は wrangler auth token --json で Wrangler のログイン(期限切れなら Wrangler が更新)か CLOUDFLARE_API_TOKEN から受け取り、表に出さない。アカウントは .env.<環境> に書いた CLOUDFLARE_ACCOUNT_ID だけ(compose ファイルを読むときに、環境変数でなくファイルの値を覚えておく)。無ければ止まり、/accounts の一覧を示す。環境変数の CLOUDFLARE_ACCOUNT_ID が違えば止まり、/accounts が読めてその中に無ければ止まる(一覧を読めないトークンでは確かめを省く)。Wrangler にも同じ ID を渡す。CLOUDFLARE_API_BASE_URL があれば Wrangler と同じくその API を使う。展開(deploy)と移行(d1 migrations apply --remote)は Wrangler で行う
  • 初めての環境かは、その環境の名前の Worker か資源が Cloudflare にあるかで見る(REQ-015)

DES-005中で使う設定を作る REQ-002・REQ-003・REQ-007

  • Worker のサービスごと・環境ごとに Wrangler の設定(JSON)を .wrangler/compose/<環境>/<サービス>/wrangler.json に作る。Wrangler の環境の階層(env)は使わない
  • 中身: 実際の名前、compatibility_date・compatibility_flags・vars・routes・triggers.crons・assets、相手の型と実際の名前・ID から作るバインディング、queues.consumers、durable_objects と移行(DES-010)。別の Worker の Durable Object には script_name を入れる
  • 手元では、ID の代わりにサービスの名前を使い、R2 にはプロジェクトの手元の鍵(DES-003。local_dev.experimental_s3_credentials)を入れる
  • リモート・手元とも、remote の指定は入れない(REQ-006)

DES-006Worker のフォルダの確かめ REQ-007

  • Worker のフォルダに Wrangler の設定ファイルがあれば、Wrangler の読み方で読み、組み立てのためのキーだけを受ける: main・build・rules・find_additional_modules・base_dir・preserve_file_names・no_bundle・minify・tsconfig・alias・upload_source_maps・$schema
  • ほかのキーがあれば止まり、compose ファイルのどこに書くか(vars → services.<名前>.environment など)を示す。define は値が振る舞いを変えるので受けない
