DES-009リモートの up REQ-010・REQ-005・REQ-015

  • 段: 組み立て(DES-007。Cloudflare に触れる前) → いまの Cloudflare を引く(DES-004) → 確かめ(初めての環境・--purge で消す資源があれば、まとめて示して環境名の打ち直し。消える Durable Object のクラスと、Durable Object を持つ消える Worker は、消す・残す・やめるを選ばせる) → 無い資源を作る → バケットの設定(DES-018) → サービスの順に: D1 の移行(d1 migrations apply --remote)、Worker を作った設定と --secrets-file(0600 の一時ファイル)で上げ、compose から消えたシークレットと、受け取らなくなった Queue の受け手を消す
  • 作る設定: 組み立てたものをそのまま(no_bundle。横のファイルも ES モジュールとして)、バインディングは実際の名前と ID、Queue の受け手は Cloudflare の既定値、routes は / か * を含めばルート、含まなければ独自ドメイン。workers.dev の URL は、ports を持ち(外から呼ばれる Worker)routes の無い Worker だけに開く(手元で ports の無い Worker はリモートでも外から届かない)。プレビューの URL は開かない
  • 前回と同じ(組み立てたもの・作った設定・シークレットの値の要約が同じ)Worker は上げない。--dry-run は同じ段を通り、変えることを示すだけ(合言葉のファイルも作らない)
  • 移行が失敗したら、その D1 を使う Worker と、それより後のサービスは行わない
  • 名前がこの環境のもので compose に無い Worker は、展開のあとに消す。名前がこの環境のもので compose に無い D1・KV・R2・Queue は示し、--purge のときだけ消す(R2 はオブジェクトの一覧の API で空にしてから消す)

DES-010Durable Objects のクラスの足し引き REQ-002・REQ-015

  • Wrangler の新しい宣言の形(exports。2026-07 から)を使う: compose の durable_objects の各クラスを {"type": "durable-object", "storage": "sqlite"} と宣言し、Cloudflare がいまの名前空間と比べて作る。移行のタグは持たない。古いキー値の保存のクラスは扱わない(利用者の決定 2026-10-13)。手元も同じ宣言を使う
  • Cloudflare に名前空間があり compose から消えたクラスは、クラスごとに消す・残す・やめるを選ばせる(環境名で消す・keep で残す・ほかの入力と空の Enter と端末が無いときはやめる)。消すクラスは {"state": "deleted"} の墓標として宣言して消し、残すクラスは今までどおり宣言する
  • 消すクラスがあれば中身も消えるので、消すものとして示し、環境名の打ち直しで確かめる

DES-018R2 のバケットの設定 REQ-002・REQ-009

  • リモート: up が、バケットごとに compose ファイルの設定と Cloudflare の設定を比べ、違えば合わせる。作るときの storage_class・jurisdiction は r2 bucket create の引数、ほかは r2 bucket dev-url(public)・r2 bucket cors・r2 bucket lifecycle・r2 bucket notification・r2 bucket lock で入れる。compose ファイルから消した設定は消す
  • 手元: Wrangler の手元の模擬に無いもののうち、再現すると決めたもの(CORS・公開の URL・イベント通知)を道具のサービス(DES-011)で効かせる。公開は入口のサービスがバケットの公開の URL を配り、CORS は S3 互換の口と公開の URL の応答に付け、通知はオブジェクトの変化を手元の Queue へ送る。ライフサイクル・ロック・保管の種類は手元では効かせない(REQ-009)
  • 手元で、バインディングからの書き込み・消去(Worker のコードの env.FILES.put など)を道具のサービスが見る手立て(通知・ロックのため)は、作る前に確かめる(確かめていないこと)

DES-021コンテナ(リモート) REQ-020・REQ-010・REQ-014

  • 作る設定に containers を入れ(DES-020 と同じ。絶対パス)、wrangler deploy に任せる。Wrangler は Worker を上げたあと、Dockerfile からイメージを作って Cloudflare のコンテナのレジストリに送り(中身が同じなら送らない)、上げた版の Durable Object の namespace に結び付けてアプリケーションを作る・変え、入れ替えを始める。入れ替えは up のあとも続く(知らせる)
  • アプリケーションの名前は Wrangler の決め方のまま <Worker の名前>-<クラス>(小文字)。Worker の名前が <プロジェクト>--<環境>-- で始まるので、持ち主が名前で分かる。道具が探す・消すのは、Worker の名前と(Cloudflare か compose ファイルにある)クラス名から決まる名前のものだけで、名前の頭だけでは選ばない(api と api-v2 を取り違えないため)
  • 変わったかの判定: 版の印(DES-015)には、コンテナを Dockerfile の場所ではなく中身のハッシュ(Dockerfile・ビルドの基点のすべてのファイル・image_vars。レジストリのイメージは参照)で入れる。どの PC から打っても同じ印になる。コンテナごとの中身のハッシュは展開の説明(--message。100 文字まで)に wc-containers <クラス>=<ハッシュ> … の形で残し、plan はそれと比べてイメージが変わるかを示す(説明に無ければ「変わるかもしれない」)。instance_type・max_instances は Cloudflare のアプリケーションと比べる
  • 消す: compose ファイルから消したコンテナ(クラスは残る)のアプリケーションは、その Worker を上げる前に消す。消したクラス・compose に無い Worker・down で下ろす Worker のアプリケーションは、Worker を消す前に消す(Cloudflare は Worker を消してもアプリケーションを消さない)
  • Docker: Dockerfile のコンテナがあれば、Cloudflare に触れる前に確かめる(--dry-run も)。リモートへのビルドは Windows でもできるので、Windows では止めない
  • コンテナを使えないアカウント: アプリケーションの一覧(/containers/applications)を読めなければ、compose ファイルにコンテナがあるときだけ Cloudflare の答えを示して止まる。無ければ今までどおり
  • ps は、コンテナのアプリケーションがあるかと、compose ファイルに無いもの(次の up が消す)を示す
