wrangler-compose 詳細仕様

手元で使えないもの

wrangler-compose --env local up(中身は Wrangler の手元の開発。miniflare と workerd)で開発するときに、使えない・本番と振る舞いが違う Cloudflare の機能の一覧。要求仕様の REQ-018 の元になる。主に使う型(Workers・D1・R2・KV・Queues・Durable Objects・シークレット)のものが対象で、ほかの製品の行は参考として残す。Wrangler の版が上がれば変わるので、確かめた版と日付を書く: Wrangler 4.149.0、2026-10-11。

根拠の見方

根拠意味
実装Wrangler 4.149.0 の wrangler-dist/cli.js の決まり(バインディングは BINDING_LOCAL_SUPPORT の表)
資料Cloudflare の資料(cloudflare/cloudflare-docs の 2026-10-11 の版)。「Supported bindings per development mode」と各製品の Local development の頁
実測手元の Wrangler 4.149.0 で動かして確かめた
推測確かめていない。仕組みから見込んだもの。受け入れの前に確かめる

バインディング

Wrangler はバインディングの種類ごとに、手元で動くか・remote: true で Cloudflare の本物につなげるかを決めている。wrangler-compose はこの表に合わせて知らせる(REQ-018)。種類の名前は Wrangler の内側の名前。

この節の remote: true は Wrangler そのものの機能の説明で、wrangler-compose は使わない(手元とリモートを混ぜない。利用者の決定)。手元で足りないものは道具のサービスが補うか、リモートの環境で確かめる。

手元だけで動く(remote: true にできない)

種類手元で起きること根拠
Durable Objects手元で動き、データは手元の置き場。本物の Durable Objects を使いたければ、それを持つ Worker をデプロイし、手元からサービスバインディング(remote: true)で呼ぶ実装・資料
静的なファイル(assets)手元のディスクから配る実装・資料
変数(vars)・シークレット.env.local・.dev.vars・設定の vars の値。Cloudflare に入れたシークレットは手元に来ない実装・資料・実測

手元でも本物でも使える

種類手元で起きること根拠
D1・KV・R2既定は手元の模擬(.wrangler/compose/local/state/)。remote: true で本物につなぐ。R2 の S3 互換 API は wrangler-compose が手元で開く(REQ-009)実装・資料・実測
Queues手元の模擬。remote: true を書いても手元の模擬のまま(miniflare が無視する。workers-sdk #13727)実装
サービスバインディング同じ up で動かしたサービス(REQ-009)か、手元の別の dev につながる。remote: true でデプロイ済みの Worker につなぐ実装・資料・実測

手元で動かすのに追加の用意が要るもの

機能要るもの・手元での使い方根拠
Cron Triggers手元では時刻が来ても動かない。curl "http://127.0.0.1:<ポート>/cdn-cgi/local/scheduled?cron=*+*+*+*+*" で呼ぶ資料

設定にあっても手元では効かないもの

設定手元で起きること・代わり根拠
ルート・カスタムドメイン(routes)・workers_dev・プレビューの URL手元の URL(http://127.0.0.1:<ポート>)だけで応える。ホスト名で振り分ける作りは、要求の Host を手で付けて試す推測
Cron(triggers.crons)自動では動かない(上)資料

設定に出ないが本番と違うもの

機能手元で起きること根拠
request.cf(国・都市・ASN など)Cloudflare から取れればその値(使う人の場所ではなく自分の回線のもの)、取れなければ決まった代わりの値実測(取れないときの警告)
R2 の公開の URL(r2.dev・独自ドメイン)Wrangler だけでは無い(workers-sdk #3687)。wrangler-compose は r2 のサービスに ports があれば http://<バケット>.localhost:<ポート>/<キー> で配る(REQ-009)資料・実装
R2 のバケットの設定(CORS・ライフサイクル・イベント通知)Wrangler だけでは当たらない(手元の S3 の口は CORS をすべて許す。実測)。wrangler-compose は ports のある r2 のサービスで CORS を、どの r2 のサービスでもイベント通知を本番と同じに補う。ライフサイクル・ロック・保存クラスは手元では効かない(REQ-009)実測・実装
D1 の Time Travel・読み取りの複製手元の D1 には無い推測
KV の結果整合性手元では書いた値がすぐ読める。本番の「しばらく古い値が見える」は再現されない推測
キャッシュ(Cache API・fetch のキャッシュ)手元のキャッシュで、本番の拠点ごとのキャッシュとは振る舞いが違う推測

R2 の機能ごとの手元の状況

基準は「ふつうのプロダクトを作るのに無いと困る機能を、本物と同じに提供する。ほとんど使わない機能は再現しない」(REQ-009。利用者の決定)。「無い」の判断は Wrangler の変更履歴と実測からの見立てで、作る前に一つずつ実物で確かめる。

R2 の機能Wrangler の手元の模擬手元での扱い(決定)
バインディングの API(get・put・head・list・delete・分割アップロード・条件つき・範囲指定・メタデータ)ある再現する(そのまま使う)
S3 互換の API・署名付き URLある(4.115.0 から。実測)再現する(そのまま使う)
CORS無い再現する(道具のサービス)。ブラウザから署名付き URL で直接上げるときに要る
公開の URL(r2.dev・独自ドメイン)無い再現する(道具のサービス)
イベント通知(オブジェクトの変化を Queue へ)無い再現する(道具のサービス)
イベント通知の作成の種類-手元では作成をすべて PutObject として送る(CopyObject・CompleteMultipartUpload を見分けない)。道具がバケットを毎秒見比べて送るので、届くまで 1〜2 秒かかる
公開の URL の範囲指定の取得(Range)・ETag・条件つきの取得-再現する(HTTP の決まりどおりに答える。利用者の決定 2026-10-13)
CORS・公開の URL(ports の無い r2 のサービス)-r2 のサービスに ports が無いと、手元の模擬の口がすべての送り元を許し、公開の URL も無い。本番と同じにするには ports を書く
ライフサイクル(期限で消す・保管の種類を変える)無い再現しない。手元の開発で期限切れを待つことはまず無い。リモートには設定を入れる
オブジェクトのロック・保管の種類無い再現しない。ほとんど使わない。リモートには設定を入れる

D1・KV・Queue の手元の状況

Wrangler 4.149.0 の手元の模擬を、資料・実装の読み取り・実測(2026-10-11)で調べた。ふだん使う API(読み書き・一覧・一括処理・移行・送受信・やり直しなど)は、どれも本物と同じに動く。下は本物と違うところと、その扱い(利用者の決定)。

製品本物との違い手元での扱い
Queue受け手の既定値: 本物は 1 回にまとめる数 10・待つ時間 5 秒・やり直し 3 回、手元の模擬は 5・1 秒・2 回(実装・実測)補う。道具が本物の既定値を手元に渡す
D1上限の一部を手元では見ない: 1 行・文字列 2MB、関数の引数 32、クエリ 30 秒、1 回の呼び出しで 1000 クエリ、DB の大きさ 10GB(実測)。バインド変数 100・1 文 100KB・列 100 は手元でも見る再現しない。ふつうの使い方では当たらない。手元で通っても本番で止まりうるので、この上限に近い使い方をするときは注意する
D1Time Travel(時刻を指定して戻す)・読み取りの複製・置き場所の指定(資料・実装)再現しない。運用の機能で、手元の開発では使わない。手元のデータは backup・restore で戻せる
D1返り値の付帯情報の一部(served_by_region・served_by_primary・timings など)が無い。duration はほぼ 0(実測)再現しない。アプリの動作に使うことはまず無い
KV本物は書いた値が他の拠点に届くまで最大 60 秒かかる(結果整合)。手元は書いたらすぐ読める。cacheTtl のキャッシュも無い(資料・実測)再現しない。再現すると試験が不安定になる。本物では古い値が読めることがあるので、コードはそれに耐えるように書く
KV同じキーへの書き込みは 1 秒に 1 回まで、1 回の呼び出しで操作は 1000 回まで(資料)。手元では制限が無い(実測)再現しない。ふつうの使い方では当たらない
Queue受け手のいない Queue に送ったメッセージは、手元では捨てられる(本物は保持期間のあいだ残る)(実装・実測)再現しない。手元でも受け手を一緒に動かすので、ふつうは起きない
Queue手元を作り直す(コードの変更で動かし直す)と、送り途中のメッセージが消える(実装・実測)再現しない。開発中の一時的なものとして扱う
Queue受け手を並べて同時に処理しない(本物は自動で増える)。一括送信の上限(本物 256KB、手元 288KB)・エラーコードが違う(実装・実測)再現しない。ふつうの開発では困らない
Queue取りに行く受け手(HTTP)・一時停止・中身の消去・保持期間(資料)再現しない。ほとんど使わない
KV・Queueイベントの購読(アカウントの出来事を Queue へ。KV・R2 では名前空間・バケットの作成と削除だけ)・KV Instant(資料)再現しない。ほとんど使わない。R2 のオブジェクトの変化を Queue へ送る「イベント通知」は別の機能で、再現する
