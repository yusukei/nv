wrangler-compose 要求仕様

01. compose ファイルを書く

利用者が書くもの(compose ファイル・.env.<環境>・Worker のフォルダ)と、その決まり。REQ-001〜007・REQ-020。

compose ファイルの例

# wrangler-compose.yaml
name: shop

services:
  web:
    type: worker
    build: ./web                    # Worker のコードのフォルダ
    compatibility_date: "2026-09-01"  # どの日付の Workers の動き方で動かすか(必須)
    ports: ["8787:8787"]            # 手元の URL
    routes: ["${WEB_DOMAIN}"]       # 環境ごとの値は .env.<環境> から展開する
    depends_on: [api]
    bindings:
      API: api                      # 相手が worker なら、その Worker を呼べる
      FILES: files                  # 相手はサービスの名前

  api:
    type: worker
    build: ./api
    compatibility_date: "2026-09-01"
    ports: ["8788:8788"]
    depends_on: [db, files, uploads, cache, jobs]
    bindings:
      DB: db                        # 相手の型で、つながり方が決まる
      FILES: files
      UPLOADS: uploads
      CACHE: cache
      JOBS: jobs                    # queue へ送る
    consumes: [jobs]                # queue から受け取る
    durable_objects: [Counter]      # この Worker のコードにあるクラス
    environment:                    # Worker に渡す秘密でない値(docker compose と同じ。NAME=値 の並びでもよい)
      GREETING: hello
    secrets: [STRIPE_KEY]           # 値は .env.<環境> の STRIPE_KEY。Worker からは env.STRIPE_KEY

  db:
    type: d1
    migrations: ./api/migrations

  files:
    type: r2                        # 1 つのサービスが資源 1 つ。R2 を 2 つ使うならサービスを 2 つ書く
    ports: ["9000:9000"]            # 手元の R2 の口(S3 互換の API・公開の URL)
    public: true                    # 公開の URL で配る
    cors:
      - origins: ["${WEB_ORIGIN}"]
        methods: [GET, PUT]

  uploads:
    type: r2
    name: incoming                  # Cloudflare では shop--<環境>--incoming(省けば shop--<環境>--uploads)
    lifecycle:
      - prefix: tmp/
        expire_after_days: 7
    notifications:
      - queue: jobs
        events: [object-create]

  cache:
    type: kv

  jobs:
    type: queue
# .env.staging(git の外)
WEB_DOMAIN=staging.shop.example.com
WEB_ORIGIN=https://staging.shop.example.com
STRIPE_KEY=sk_test_...

要求

REQ-001compose ファイル

  • 名前は wrangler-compose.yaml(.yml も読む。両方あれば止まる)。いまのフォルダから上へたどって最初に見つかったものを使う。見つからなければ止まり、書き始め方を示す
  • 書式は YAML で、docker compose の compose.yaml に寄せる: 一番上に name・context・services
  • context は、Wrangler と Node の版を決める package.json のあるフォルダ(compose ファイルから見た相対)。省くと compose ファイルのあるフォルダ。compose ファイルを展開用のフォルダに置き、コードと依存は別のフォルダに置けるようにする(docker compose の build.context と同じ考え)。package.json が無ければ止まる。ほかのパス(build・assets・migrations)はこれまでどおり compose ファイルから見た相対で、.env.<環境>・.wrangler/compose/・backups/ も compose ファイルのあるフォルダに置く
  • 一番上の name(プロジェクトの名前)は必須。無ければ止まる(PC ごとのフォルダ名で別のプロジェクトにならないため。利用者の決定 2026-10-13)。プロジェクトとサービスの名前は、英小文字・数字・- だけ(REQ-006 の決まりも守る)
  • x- で始まるキーは、どの階層でも読み飛ばす(docker と同じ)
  • 知らないキー、型に合わないキー、無いサービスを指すもの、depends_on の輪は、何もせずに止まり、どこ(services.web.image など)の何がいけないかを示す
  • compose ファイルは環境によらず 1 つ。環境の違いは変数の展開(REQ-004)だけで表す

REQ-002サービスの型

型書けるキー建つもの
workerbuild(必須。コードのフォルダ)・compatibility_date(必須)・name・ports・depends_on・bindings・consumes・durable_objects・secrets・environment・routes・crons・compatibility_flags・assets・containers(REQ-020)・placement・observability・cacheWorker 1 つ(とそのコンテナ)
d1name・migrations(移行の SQL のフォルダ)D1 データベース 1 つ
r2name・ports(手元の R2 の口)・public・public_port・cors・lifecycle・notifications・lock・storage_class・jurisdictionR2 バケット 1 つ
kvnameKV 名前空間 1 つ
queuenameQueue 1 つ
  • name は Cloudflare での名前の最後の部分(REQ-006)。道具が前に <プロジェクト>--<環境>-- を付ける。省けばサービスの名前。同じプロジェクトの中で重なると止まる
  • r2 のキーは、本物の R2 のバケットの設定と同じ意味を持つ: public(公開の URL で配る)・cors(CORS の決まり)・lifecycle(期限で消す・保管の種類を変える)・notifications(変化を同じプロジェクトの Queue へ送る)・lock(消せない期間)・storage_class(保管の種類)・jurisdiction(置き場の管轄)。public・cors・notifications は手元でも同じに効く(REQ-009)。lifecycle・lock・storage_class・jurisdiction はリモートにだけ効き、手元では効かないことを up が知らせる
  • environment は Worker に渡す秘密でない値(Wrangler の vars)。docker compose と同じく「名前: 値」の対応表か NAME=値 の並びで書き、並びに名前だけを書けば同じ名前の変数から取る。対応表で値を書かない(NAME:)と空の値になる(利用者の決定 2026-10-13)。routes はルート・カスタムドメイン(変数が空で空になった要素は書かなかったことにする。ports があって routes が空の Worker は workers.dev で公開されるので、["${DOMAIN:-}"] と書けば、ドメインを書いた環境はそのドメイン、書かない環境は workers.dev になる)、crons は定期実行の式、assets は静的なファイルのフォルダ、compatibility_flags は Workers の互換の指定
  • placement(mode: smart)・observability(enabled・head_sampling_rate)・cache(enabled)は Wrangler の同じ名前の設定と同じ形で書き、そのまま Worker の設定になる。書かないものは Cloudflare の既定に任せ、道具は値を入れない。mode が smart 以外・enabled が true/false 以外・head_sampling_rate が 0〜1 の外のときは、services.<名前>.<キー> で場所を示して止まる
  • compatibility_date は、Worker をどの日付の時点の Workers の動き方で動かすかを決める日付(例 "2026-09-01")。Cloudflare は動き方の変更を日付ごとに区切り、Worker はその日までの変更だけを受ける。省くと動かした日の日付になり、手元とリモート・動かした日ごとに動き方が変わりうるので、必須とする(利用者の決定)。無ければ止まる
  • durable_objects は、その Worker のコードにある Durable Object のクラス名の一覧(Durable Objects は Worker の中のものなので、型にはしない)
  • 型は使うものから足す。足すときは、手元で本物と互換に動く手立てを同時に決める

REQ-003つながり

  • Worker の bindings は「名前: 相手」。Worker のコードからは env.<名前> で見える
  • 相手の書き方: サービスの名前(cache)。Worker の Durable Object は <worker>.<クラス>(api.Counter)
  • 相手の型でつながり方が決まる: worker → その Worker を呼べる、d1・r2・kv → その資源を読み書きできる、queue → その Queue へ送れる、Durable Object → それを使える
  • consumes は、その Worker が受け取る Queue の一覧(書き方は上と同じ)
  • つながる相手は、depends_on に書かなくても先に建てる。depends_on はそれに足す順。つながりが輪になる(互いに呼び合う Worker など)ときは、depends_on の順だけを守る
  • つながりは、手元でもリモートでも同じに働く

値の出どころと渡り先

値の出どころwrangler-composeWorker に渡るもの止まる

WC_ の変数のうち、接続先は environment の値だけ、鍵は secrets の値だけに使える(REQ-004)。

REQ-004環境ごとの値

  • compose ファイルの文字列の中の ${VAR} を展開する。書き方は docker compose と同じ(${VAR}・${VAR:-既定}・${VAR:?説明}・$$ など、docker compose の書き方すべて)
  • 値は環境変数、次にプロジェクトの .env.<環境>(--env で選んだもの)から読む。.env.<環境> の読み方(引用符・複数行・注釈・前に書いた値の展開)は docker compose と同じ(利用者の決定 2026-10-13)
  • 既定の無い変数が無ければ、何もせずに止まり、無い変数をまとめて示す
  • 道具が値を決める変数(WC_ で始まる)がある。WC_R2_<サービス>_S3(サービスの名前は英大文字にし - は _)は、その R2 のバケットの S3 互換の API の接続先(パス形式でバケット名まで): 手元は http://127.0.0.1:<ports>/cdn-cgi/local/r2/s3/<資源の名前>(r2 のサービスに ports が要る)、リモートは https://<CLOUDFLARE_ACCOUNT_ID>[.<jurisdiction>].r2.cloudflarestorage.com/<実際の名前>。Worker が S3 互換の API で R2 を読み書きするとき、接続先を人が環境ごとに書かずに済むようにする(利用者の決定。2026-10-12)。使えるのは Worker の environment の値だけで、ほかの場所・無いバケット・決まらないとき(手元で ports が無い、リモートでアカウントの ID が無い)は止まる。${X:-${WC_R2_STORAGE_S3}} のように既定にも使える
  • WC_R2_<サービス>_S3_KEY・WC_R2_<サービス>_S3_SECRET は、手元の S3 互換の API の鍵。鍵はプロジェクトごとの乱数で、道具が作って .wrangler/compose/local/s3-keys.json(本人だけが読める)に置き、画面には出さない。秘密の値なので、使えるのは Worker の secrets の値だけ。リモートの鍵(R2 の API トークン)は道具が用意せず、アプリの側で扱う(利用者の決定 2026-10-13)。リモートでこの変数を使うと止まる(${R2_KEY:-${WC_R2_STORAGE_S3_KEY}} のように既定として書けば、.env.<環境> の値が入る)(利用者の決定 2026-10-12。決まった鍵は誰でも知っているので、LAN に開いた口が誰にでも読み書き・削除される)
  • .env.<環境> は git に入れない。git の中で .gitignore で外れていない、またはすでに git に入っていれば止まる

REQ-005シークレット

  • Worker の secrets に、environment と同じ形で書く: 「名前: ${変数}」の対応表か、名前の並び(同じ名前の変数から取る)。名前は Worker から見える名前(env.<名前>)。値は REQ-004 と同じ探し方で読む
  • シークレットの値は必ず変数から取る。compose ファイルに値を書くと(変数を含まない値・NAME=値 の並び)止まる。シークレットが git に入らないため
  • その Worker の secrets に書いたものだけが、その Worker から見える
  • 0.1.7 までの書き方(Worker の vars、一番上の secrets と environment: <変数名>)は、書き直し方を示して止まる(利用者の決定。2026-10-12: docker compose の一番上の secrets はファイルとして渡すための仕組みで、Workers では名前が 3 つになるだけ)
  • up が、手元でもリモートでも、その Worker のシークレットとして入れる。compose ファイルから消したシークレットは、up が消す
  • 値が無ければ止まり、無い変数の名前を示す

REQ-006環境

  • 環境は --env で選ぶ。local は手元、それ以外はリモート(名前は自由。pr-123 のように並べて建てられる)
  • リモートの Worker と資源の Cloudflare での名前は、既定で環境の名前を付けて道具が決める: Worker も資源も <プロジェクト>--<環境>--<名前>。名前は name、省けばサービスの名前(例: cache は shop--staging--cache、name: incoming の uploads は shop--staging--incoming)。同じアカウントに複数のプロジェクトと環境を並べても名前がぶつからない(利用者の決定)
  • 名前から、どのプロジェクトのどの環境のものかが必ず分かる(以前の版の名前(- 1 つの区切り)で作った環境は扱わない。利用者の決定 2026-10-13): 区切りは -- で、プロジェクト名・環境名・サービス名・name には -- を使えない(先頭と末尾の - も使えない)。プロジェクト名は 3 文字以上(Worker の名前が URL になるとき、3〜4 文字目の -- は予約されているため)。道具が作る・使う・消すのは、名前が <プロジェクト>--<環境>-- で始まる、その環境のものだけ。ほかの名前のものには触らない(利用者の決定 2026-10-13「必ず名前から誰の持ち主か判断をできるようにして下さい。削除も同様です」)
  • コンテナのアプリケーション(REQ-020)は、Cloudflare が名前に -- を許さないので、<プロジェクト>-<環境>-<サービス>-<クラス>-<印>(-- を - にし、末尾に <プロジェクト>--<環境>--<サービス> とクラスから作る 8 文字の印を付ける)にする。持ち主は名前の頭ではなく、そのアプリケーションが結び付いた Durable Object がこの環境の Worker のものかで判断する(利用者の決定 2026-10-13。本物の Cloudflare で確かめた)
  • 決めた名前が Cloudflare の名前の決まり(長さなど)に合わなければ、何もせずに止まり、name で短い名前を書くよう示す
  • 同じ名前のものがすでにあれば、それを使う(作り直さない)。名前がこの環境のものなので、ほかのプロジェクト・環境のものを使うことは無い
  • 手元では、資源はサービスの名前(cache・files など)をそのまま使う。Worker には、道具がプロジェクトごとに違う名前を付ける(手元のコンテナがほかのプロジェクトと混ざらないため。同じリポジトリを 2 か所に取り出して同時に動かしても混ざらない)。画面のログ・ps・logs の引数では、今までどおりサービスの名前で示す(利用者の決定 2026-10-13)
  • リモートの環境は、.env.<環境> に CLOUDFLARE_ACCOUNT_ID=<アカウントの ID> を書いたアカウントでだけ操作する(--dry-run も含む、Cloudflare に触れるすべての操作。build は触れないので確かめない)。書いていなければ、何もせずに止まり、ログインで使えるアカウントを示す。環境変数の CLOUDFLARE_ACCOUNT_ID がそれと違うとき、ログインがそのアカウントを使えないときも止まる。意図しないアカウントへの展開・削除を防ぐため(利用者の決定。2026-10-12)。手元では要らない
  • 違う環境どうしは混ざらない。ID などの実際の値は道具が扱い、利用者は書かない。別の PC からでも、同じ環境の同じ資源につながる
  • 1 つの環境のものは、すべてその環境の中で動く。手元のものがリモートの資源に触れる、リモートのものが手元に触れる、ということをしない(道具が中で行うことも含む)

REQ-007Worker のフォルダ

  • Worker のフォルダ(build)には、コードと、環境に依存しない組み立てのためのもの(どのファイルから組み立てるか、組み立ての手順など)だけを置いてよい
  • 振る舞いに関わる設定(名前・つながり・値・ルート・定期実行・環境など)がフォルダの中にあれば、何もせずに止まり、compose ファイルのどこに書くかを示す
  • 道具はプロジェクトのファイルを書き換えない。道具が作るものは、プロジェクトの中の決まった場所(.wrangler/compose/)に置く。git のリポジトリの中なら、そこが git から外れていなければ止まる。リポジトリでなければ確かめない(2026-10-13)

REQ-020コンテナ

  • Worker のサービスに containers を書くと、その Worker の Durable Object のクラスに Cloudflare Containers のコンテナを付けられる。ほかのサービスと同じ程度の基本的な対応とし、手元でもリモートでも同じに建てる(利用者の決定 2026-10-13)
  • 書き方は項目の並び。キーは class(必須。同じ Worker の durable_objects にあるクラス)・image(必須。Dockerfile の場所(compose ファイルから見た相対)か、レジストリのイメージ)・instance_type(lite・basic・standard-1〜standard-4、または vcpu・memory_mib・disk_mb)・max_instances・image_build_context・image_vars。意味は本物のコンテナの設定と同じ。1 つのクラスに付けられるコンテナは 1 つ
  • イメージは、Dockerfile から作るのを基本とする。作ったイメージは、手元では手元の Docker に、リモートでは Cloudflare のコンテナのレジストリに置き、外部のレジストリには置かない(Cloudflare で動かすなら外部に置く利点が無いため)。image にレジストリのイメージを書くのは、すでにビルドされたイメージ(外部のレジストリにあるものなど)を使うときだけ(利用者の決定 2026-10-13)
  • durable_objects に無いクラスを指すもの、同じクラスに 2 つ付けるもの、知らないキー、無い Dockerfile は、何もせずに止まり、どこの何がいけないかを示す
  • 動かし方の方針は Cloudflare の default だけを扱う(durable_object 方針は範囲外)
  • 手元: --env local up は、コンテナを Docker(か互換のもの)で、本物と同じイメージ(linux/amd64)から動かす。Worker のコードからは本物と同じに使える。Dockerfile・ビルドの基点の中身・image が変われば、作り直して動かし直す
  • 手元: Ctrl+C や down で止めたら、そのプロジェクトのコンテナを残さない。手元で作ったイメージは down --purge のときだけ消す(利用者の決定 2026-10-13)。ほかのプロジェクトのコンテナとイメージには触らない(定義 3)
  • Docker は compose ファイルにコンテナがあるときだけ要る。要るのに Docker につながらなければ、手元では何も動かさずに、リモートでは Cloudflare に触れる前に止まり、そのことを示す。コンテナの無い compose ファイルは、Docker が無くても今までどおり動く
  • 手元で本物と違う点(max_instances・instance_type の大きさが効かない、置き場・段階的な入れ替え・ssh が無い、Windows の手元では動かない、Apple Silicon では linux/amd64 をまねて動かす)は、手元で使えないものに理由とともに書き、--env local up が知らせる(REQ-018)
  • リモート: up は、Dockerfile からイメージを作って Cloudflare のコンテナのレジストリに置き、コンテナのアプリケーションを作る・変える。利用者が手でイメージを作る・レジストリに登録することはない(REQ-016)。名前は道具が決め、名前からこの環境のもの(<プロジェクト>--<環境>-- で始まる)と分かる(REQ-006)。イメージも設定も変わっていなければ変えない
  • リモート: 途中で止まったとき(Worker は上がったがイメージを送れなかったなど)は、どこまで済み、どこでなぜ止まったかを示す。もう一度 up すれば揃う
  • リモート: compose ファイルから消したコンテナと、down で下ろした Worker のコンテナは、道具がアプリケーションごと消す(Cloudflare は Worker を消してもコンテナを消さないため)。消すのは名前がこの環境のものだけ
  • --dry-run はイメージを作らず送らず、作る・変える・消すコンテナと、イメージが変わるかを示す(REQ-014)
  • ps は、コンテナがあるかと、compose ファイルとの違いを示す(REQ-012)
  • Cloudflare のレジストリに置いたイメージは、リモートの down --purge で消す(REQ-011)。また up がコンテナのアプリケーションを消すとき(compose から消したコンテナ・消したクラス・compose に無い Worker)は、そのイメージも消す(あとから見つける手掛かりが無くなるため。利用者の決定 2026-10-13)。down(--purge なし)では消さない
  • backup・restore はコンテナを扱わない。コンテナは残すデータを持たない(ディスクは止まると消える)
  • コンテナを使えないアカウント(Workers の有料プランでない)では、Cloudflare の答えを示して止まる
