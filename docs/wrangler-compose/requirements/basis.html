wrangler-compose 要求仕様

決定と用語

すべての要求のもとになる定義、docker compose から受け継ぐ理念、利用者の決定、用語。

定義

(利用者の決定。すべての要求はこの定義から決める。定義するのはここまで)

  1. wrangler-compose は、docker compose のように「手元(local)で開発したサービス」を、安全に「リモート(Cloudflare の環境)へ展開する」ためのもの。
  2. wrangler-compose は、内部では Wrangler が稼働している。
  3. wrangler-compose は、ほかの wrangler-compose のアプリと一切の資源を共有せず、プロジェクト(compose ファイル)の単位で分離している。
  4. wrangler-compose は、Cloudflare への操作を Wrangler のコマンドと Cloudflare の API で行う。ただし、使える API は wrangler login で付与される API のみとする。(2026-10-13)

これをどう使うかは、使うアプリの側の責任である。

理念(docker compose から)

  • ファイルが唯一の正: アプリの構成は compose ファイルだけが持つ。compose ファイルとコードと .env.<環境> があれば、どこでも同じものが建つ
  • コマンド 1 つで揃う: 書いたあとは up だけで動く。人が手で行う段取りを持たない
  • 宣言した状態に合わせる: up は何度打っても同じ結果になり、変わったところだけを変える
  • 作り直せるものとデータを分ける: down はデータを残し、データは明示したときだけ消す
  • 論理名で書き、名前で呼び合う: compose ファイルにはサービスの名前だけを書き、サービスは互いを名前で指す。実際の名前は道具が決める
  • 環境を混ぜない: 1 つの環境のものは、すべてその環境の中で動く。手元のものがリモートの資源に触れることも、その逆もない
  • 1 つの compose ファイルが 1 つの塊: 1 つの compose ファイル(プロジェクト)は、それだけで完結した 1 つの塊として動く。その中のサービスは、compose ファイルに書いたつながり(bindings・consumes)で、互いの資源(D1・R2・KV・Queue・Worker の呼び出し)を使う。塊の外(別の compose ファイル・別のプロジェクト)のものとは、資源を一切共有しない。プロセス・待ち受けのポート・データの置き場・Worker の呼び出し先の登録(Wrangler の dev registry)も共有しない(docker compose のプロジェクトどうしが混ざらないのと同じ)

決定(利用者)

  • 定義: docker compose のように手元で開発したサービスを、安全にリモートへ展開するためのもの(最も重要)
  • Cloudflare Containers に、ほかのサービスと同じ程度の基本的な対応をする。Worker のサービスの containers に書き、手元でも Docker で本物と同じに動かす。特定のアプリの使い方から逆算しない(2026-10-13)
  • コンテナのイメージは Dockerfile から作り、リモートでは Cloudflare のコンテナのレジストリに置く。外部のレジストリは、すでにビルドされたイメージを使うときだけ(2026-10-13)
  • コマンドと書式は docker compose に合わせる。勝手に足したり変えたりしない
  • 何ができるべきかから決め、中で使う道具の都合で要求を変えない
  • 人が手で行う段取り(設定を手で書き足す、値を手で入れる、資源を手で作る、API キーを手で発行する)が要る形にしない
  • docker compose の image の代わりに type を置き、Worker も D1・R2・KV・Queue もサービスとして並べる。型は worker・d1・r2・kv・queue
  • 主に使うのは Workers・D1・R2・KV・Queues・Durable Objects・シークレット。使うものだけを作り、作るものは本物と互換にする
  • 手元では、ふつうのプロダクトを作るのに無いと困る機能を本物と同じに提供する。ほとんど使わない機能は再現しない
  • Cloudflare の操作には Wrangler と Cloudflare の API を使う。使える API は wrangler login で付与される API のみ(2026-10-13。2026-10-12 の決定を改める)
  • リモートの環境の Worker は、利用者のサービスのものだけ(2026-10-12)
  • 環境の違いは、compose ファイルの中の変数(${VAR})を .env.<環境> から展開して表す。切り替えの口は --env 1 つ
  • 手元とリモートを混ぜない。1 つの環境のものは、すべてその環境の中で動かす
  • 1 つの compose ファイルが 1 つの塊。中のサービスはつながり(bindings・consumes)で互いの資源を使い、塊の外(別の compose ファイル・別のプロジェクト)とは、プロセス・ポート・データの置き場・Worker の呼び出し先の登録を含めて資源を一切共有しない(2026-10-12)
  • Worker のフォルダには、環境に依存しない組み立てのためのものだけを置いてよい。振る舞いに関わる設定は書けない
  • シークレットは Worker ごとのシークレットとして入れる
  • r2 のサービスにも ports を書ける。そのポートが手元の R2 の口(S3 互換の API とバケットの CORS・公開の URL)になる
  • 実際の名前は、道具がプロジェクトと環境の名前を前に付けて決める(<プロジェクト>--<環境>--<名前>)。名前は name に書き、省けばサービスの名前(利用者の決定 2026-10-13)
  • 1 つのサービスは 1 つの Worker か 1 つの資源。同じ型の資源を増やすときはサービスを足す(利用者の決定 2026-10-13「名前で指定すれば良いだけ」)
  • R2 のバケットの設定(公開・CORS・ライフサイクル・通知・ロック・保管の種類)は compose ファイルの r2 のサービスに書き、手元にもリモートにも同じに入れる
  • down はデータを残し、データは --purge のときだけ消す。手元の --purge も、リモートと同じく環境名を打ち直して確かめる
  • Queue の受け手の細かい設定は今は持たず、Cloudflare の既定に任せる
  • Node・npm の扱いは nv が受け持つ。GitHub の Release で nv と一緒に配り、更新とエージェント用のスキルは nv に寄せる
