wrangler-compose 設計

要求仕様(REQ-001〜019)と受け入れ条件を満たす作り。中では Cloudflare の公式の道具 Wrangler を実行役として使う(利用者には見せない)。Wrangler に無い機能は道具のサービス(REQ-017)で受け持つ。事実は手元の Wrangler 4.149.0 で 2026-10-11 に実測・読み取りした。

確かめた事実

事実出典
Workers・D1・R2・KV・Queues・Durable Objects・シークレットは、どれも Wrangler の手元の模擬(miniflare・workerd)で、網なしに動く実装(BINDING_LOCAL_SUPPORT)・実測
手元の Worker を別々の実行環境で動かし、同じ手元の D1 に同時に書くと、40 回中 10 回が SQLITE_BUSY で失敗する。wrangler dev -c a -c b(1 つの実行環境に複数の Worker)では 40 回すべて通り、Queue の送り手と受け手を別の Worker にしても届く実測
wrangler dev -c a -c b で外から届くのは最初の Worker だけ。最初の Worker を入口にし、ポートごとに TCP をそのまま入口へ中継すると、入口の Worker から見える URL・Host は利用者がつないだポートのまま。入口がポートで振り分けて渡した先の Worker からも元の URL のまま見える実測
macOS では、ほかのプログラムが 0.0.0.0:8787 で待ち受けていても 127.0.0.1:8787 で待ち受けられ(逆も同じ)、以後 localhost:8787 への要求は後から待ち受けた方に届く。待ち受けられるかだけでは、ポートが空いているとは分からない実測(2026-10-12)
Wrangler の dev registry は既定で機械に 1 つ(macOS は ~/Library/Preferences/.wrangler/registry)で、Worker の名前のファイルで登録する。WRANGLER_REGISTRY_PATH で場所を変えられる実測・実装(4.149.0)
Wrangler は devtools のポートを 9229 から空きを探して決め、そのあと workerd が待ち受ける。2 つの wrangler dev を同時に起動すると同じポートを選び、片方の workerd が bind(): Address already in use で止まる。--inspector-port で渡せば、そのポートを使う実測・実装(4.149.0)
R2 バインディングの local_dev.experimental_s3_credentials で、手元に S3 互換の口(/cdn-cgi/local/r2/s3/<バケット>。SigV4 のヘッダと署名付き URL)が開き、バインディングと同じ中身が見える。違う鍵は 401、署名を変えると 403実測・CHANGELOG(4.115.0)
Wrangler のログインの権限では R2 の中身を一覧できない(一覧は S3 互換の API と、人が発行する API キーが要る)。Worker の R2 バインディング(list・get・put・delete)と KV バインディング(list・getWithMetadata・put・delete)なら、その環境の中で一覧・読み書きできる実装・資料
手元のデータの置き場は --persist-to で決まり、d1 migrations apply・d1 export・d1 execute は --local --persist-to で同じ置き場を扱う実測
D1 の書き出しは表の作りと中身と d1_migrations を含み、表を消した D1 に流して移行を当てると、控えのあとの移行だけが当たる(手元・Cloudflare とも)実測(0.1 系)
Wrangler の標準入力を空にすると、確かめの問いは既定の答えで進み、資源の ID を設定ファイルへ書き戻さない。deploy --secrets-file はファイルに無いシークレットを消さない実装(0.1 系)

設計

DES-001作りの全体 REQ-001・REQ-007・REQ-019

  • 流れ: compose ファイルを読む(DES-002) → 値を展開する(DES-003) → サービスの順を決める → 環境ごとに中で使う設定を作る(DES-005) → Wrangler を nv run wrangler … で動かす
  • 道具が作るものは、すべてプロジェクトの .wrangler/compose/ の下に置く(組み立てたもの・中で使う設定・名前の記録・手元のデータ・手元のログ)。プロジェクトのファイルは書き換えない
  • Wrangler は context(省けば compose ファイルのあるフォルダ)の package.json の版を使い、nv run をそのフォルダで動かす。組み立ての見分けに入れるロックファイルも同じフォルダのもの。Worker のフォルダに別の package.json があれば、組み立ての前にそこで nv sync を動かす

DES-002compose ファイルを読む REQ-001・REQ-002・REQ-003

  • YAML を読むクレートを 1 つ足す(serde-saphyr か serde_yaml_ng。作る時点で手入れが続いている方)。手入れの止まった serde_yaml は使わない
  • 値の木に読み、自前で確かめてから型のある形へ移す(x- を許しつつ知らないキーで止まるため)。止まるときは場所と理由を示す
  • サービスの environment・secrets は、値を展開する前に「名前: 値」の対応表へそろえる(並びの NAME=値 は値、名前だけは ${NAME})。シークレットは書いたままの値に変数の参照が無ければ止める(値を表に出さない)
  • 省略形と複数形は、読んだ直後に複数形へそろえる(省略形は、サービスの名前を資源の名前とする 1 つの資源)。以降の作りは複数形だけを扱う
  • サービスの順: bindings・consumes の相手と depends_on を依存として並べる(決まらないところはファイルの順。輪は止まる)。up に名前を渡せば依存をたどった集まり、down は渡した名前だけ

DES-003値の展開 REQ-004・REQ-005

  • 道具の変数(WC_R2_…_S3)は、展開の時点ではまだ実際の名前が決まらないので、目印の文字で囲んだ仮の値にしておく。サービスを読み終えたあと、Worker の environment の値の中の目印だけを接続先に置き換える。目印が environment の外に残っていれば止める。リモートの実際の名前は DES-004 と同じ決め方(name、無ければ <プロジェクト>-<環境>-<資源の名前>)、アカウントは .env.<環境> の CLOUDFLARE_ACCOUNT_ID
  • docker compose の展開の決まり(${VAR}・${VAR:-既定}・${VAR-既定}・${VAR:?説明}・${VAR?説明}・$VAR・$$)を自前で書く。展開するのは文字列の値だけで、型の確かめの前に行う
  • 値は環境変数 → .env.<環境>。無い変数は集めてからまとめて示す(シークレットの変数も同じ一覧に入れる)。$5・${}・閉じていない ${ など書き方の誤りは、docker compose と同じく止める($ そのものは $$)
  • x- で始まるキーは、どの階層でも展開の前に取り除く。真偽・数の欄は、展開で文字列になった "true"・"600" も受ける
  • .env.<環境> の読み方も docker compose に合わせる: 引用符の無い値は # の前まで、'…' は書いたまま、"…" は複数行にでき \n などを文字にし、閉じた引用符のあとは注釈。引用符の無い値と "…" の中の ${VAR} は、環境変数とそれより前に書いた値から展開する
  • シークレットの値は、表に出す場面(--dry-run など)で伏せる

DES-004実際の名前と見つけ直し REQ-006

  • 実際の名前は、name、無ければ Worker は <プロジェクト>-<環境>-<サービス>、資源は <プロジェクト>-<環境>-<資源の名前>(資源の名前は、省略形はサービスの名前、複数形は <サービス>-<名前>)。手元では資源の名前のまま。Cloudflare の名前の決まりに合わなければ止まる
  • 道具は ID を覚えない。操作のたびに名前で Cloudflare を引き直す(Worker・D1・KV・R2(使う管轄ごと)・Queue・Durable Object の名前空間の一覧)ので、別の PC からでも同じものにつながる。無ければ作り、あれば使う。道具が覚えるのは、前回上げた Worker の要約(.wrangler/compose/<環境>/deployed.json。変わっていない Worker を上げないためと、compose から消えた Worker を見つけるため)とデータのサービスの合言葉だけで、失っても上げ直すだけで結果は変わらない
  • 一覧・作成・設定は Cloudflare の API で行う(Wrangler の一覧の多くは JSON で答えないため)。資格は wrangler auth token --json で Wrangler のログイン(期限切れなら Wrangler が更新)か CLOUDFLARE_API_TOKEN から受け取り、表に出さない。アカウントは .env.<環境> に書いた CLOUDFLARE_ACCOUNT_ID だけ(compose ファイルを読むときに、環境変数でなくファイルの値を控える)。無ければ止まり、/accounts の一覧を示す。環境変数の CLOUDFLARE_ACCOUNT_ID が違えば止まり、/accounts が読めてその中に無ければ止まる(一覧を読めないトークンでは確かめを省く)。Wrangler にも同じ ID を渡す。CLOUDFLARE_API_BASE_URL があれば Wrangler と同じくその API を使う。展開(deploy)と移行(d1 migrations apply --remote)は Wrangler で行う
  • 初めての環境かは、その環境の名前の Worker か資源が Cloudflare にあるかで見る(REQ-015)

DES-005中で使う設定を作る REQ-002・REQ-003・REQ-007

  • Worker のサービスごと・環境ごとに Wrangler の設定(JSON)を .wrangler/compose/<環境>/<サービス>/wrangler.json に作る。Wrangler の環境の階層(env)は使わない
  • 中身: 実際の名前、compatibility_date・compatibility_flags・vars・routes・triggers.crons・assets、相手の型と実際の名前・ID から作るバインディング、queues.consumers、durable_objects と移行(DES-010)。別の Worker の Durable Object には script_name を入れる
  • 手元では、ID の代わりにサービスの名前を使い、R2 には決まった手元の鍵(local_dev.experimental_s3_credentials)を入れる
  • リモート・手元とも、remote の指定は入れない(REQ-006)

DES-006Worker のフォルダの確かめ REQ-007

  • Worker のフォルダに Wrangler の設定ファイルがあれば、Wrangler の読み方で読み、組み立てのためのキーだけを受ける: main・build・rules・find_additional_modules・base_dir・preserve_file_names・no_bundle・minify・tsconfig・alias・upload_source_maps・$schema
  • ほかのキーがあれば止まり、compose ファイルのどこに書くか(vars → services.<名前>.environment など)を示す。define は値が振る舞いを変えるので受けない

DES-007build REQ-008・REQ-015

  • Worker ごとに、バインディングを持たない組み立て用の設定で wrangler deploy --dry-run --outdir .wrangler/compose/build/<サービス>/ を動かし、組み立てたもの(バンドル)を置く。docker のイメージに当たる
  • 組み立てたものに、コードと組み立てのキーの要約(SHA-256)を添える。up はいまのコードと比べ、違えば組み立て直す(--build なら比べずに組み直す)。手元の up は動いている間もコードを見ていて、変われば組み立て直して動かし直す(DES-008)
  • 手元の up もリモートの up も、同じ組み立てたものを組み直さずに使う(手元は DES-008、リモートは deploy --no-bundle)

DES-008手元の up REQ-009・REQ-005・REQ-017

  • すべての Worker(利用者のものと道具のサービス)を 1 つの wrangler dev で動かす: wrangler dev -c <入口> -c <Worker> … --persist-to .wrangler/compose/local/state。1 つの実行環境なので、同時の書き込みで壊れない
  • 入口は道具のサービス(DES-011)で、ports を持つ Worker へのつながりを持ち、要求の URL のポートで振り分ける。道具は ports のアドレスとポートで待ち受け、入口のポートへ TCP をそのまま中継する(WebSocket もそのまま通る)
  • プロジェクトを分ける(定義 3): プロセスは up ごとに別。データの置き場・ロック・設定・ログは .wrangler/compose/<環境>/ の下でプロジェクトごと。Wrangler の dev registry(wrangler dev どうしが Worker を名前で見つける登録。既定は機械に 1 つで、同じ名前の Worker を持つプロジェクトが互いの登録を上書きする)も WRANGLER_REGISTRY_PATH で .wrangler/compose/local/registry に置く。待ち受けのポートは次のとおり
  • ポートを他と分ける: ports のポートは、待ち受ける前に、そこへつないで答えるものがいないかを確かめる(127.0.0.1・0.0.0.0 などのときは 127.0.0.1 と ::1、それ以外はそのアドレス)。答えるものがいれば、ほかのプロジェクトの通信を横取りしないよう、何も動かさずに止める。wrangler dev には、入口と同じく devtools のポートも OS が選んだ空きを --inspector-port で渡し、それでもポートが重なって起動の途中で止まったときは、3 回まで起動し直す
  • R2 の口(DES-019): ports を書いた r2 のサービスは、道具がそのポートで HTTP を受け、S3 互換の口と公開の URL を受け持つ。ports の無い r2 のサービスは、手元の模擬の口(/cdn-cgi/local/r2/s3/)に Worker のポートから届くが、CORS はすべて許され、公開の URL も無い(up がそのことを知らせる)。ports のある r2 のサービスのバケットには、Worker のポートの S3 互換の口は答えない(404。本番の Worker のアドレスにも S3 の口は無い)ので、cors を飛ばして届くことは無い。そのため Worker のポートは 1 つの接続に 1 つの要求(Connection: close)で受け、要求ごとに行き先を確かめる。WebSocket などの upgrade はそのまま通す
  • ログ: 手元では、Worker のログにどの Worker のものかが付かない(実測)。そこで道具がサービスごとに小さな tail の受け手(wc-logs-<サービス>)を置き、受け手が届いたログにサービス名を付けて出す。道具は Wrangler 自身の行(起動・再読み込み・エラー)と受け手の行だけを画面と .wrangler/compose/local/logs/up.log に出し、名前の付かない生の行は出さない
  • R2 のイベント通知: 手元の模擬に無いので、データのサービスが通知を設定したバケットを毎秒見比べ、増えた・変わった・消えたオブジェクトを本物と同じ形のメッセージで手元の Queue へ送る。外から見比べるので作成の種類は見分けられず、作成はすべて PutObject として送る。前に見た中身は道具の KV(wc-notify-state)に残し、Queue が受け取ってから進めるので、動かし直しても抜けも重なりも無く、送れなかったものは次の回に送り直す
  • シークレットと vars は、作った設定の横の .dev.vars で渡す(Unix は 0600。git の外)
  • 動かす前に、移行を d1 migrations apply --local --persist-to … で当てる
  • 使う Wrangler は 4.149.0 以上(この設計を確かめた版)
  • Queue の受け手は、compose ファイルに設定を持たないので、手元の設定に本物の既定値(max_batch_size: 10・max_batch_timeout: 5・max_retries: 3)を書いて渡す。手元の模擬の既定値(5・1・2)は本物と違うため(実測)
  • 動いていることの記録と錠・ほかの端末からの止め方は 0.1 系のものを引き継ぐ。ログは画面と .wrangler/compose/local/logs/ の両方に出す
  • compose ファイルか .env.local が変われば、設定を作り直して動かし直す。コードが変われば組み立て直して動かし直す(wrangler dev は最初の設定以外の Worker の新しい束を読み直さない。4.149.0 で実測)。見るのは Worker のフォルダと、前の組み立てで esbuild が読んだフォルダの外のファイル(共有のコードなど)、ロックファイル、Wrangler の版。組み立ては別のフォルダで行い、うまくいったときだけ動いている束を置き換える。読めない compose ファイルに直したときは、直るまで今のまま動かす。同じプロセスのまま動かし直すので、ポートは閉じてから開き直す

DES-009リモートの up REQ-010・REQ-005・REQ-015

  • 段: 組み立て(DES-007。Cloudflare に触れる前) → いまの Cloudflare を引く(DES-004) → 確かめ(初めての環境・消える Durable Object のクラス・--remove-orphans で消す Worker があれば、まとめて示して環境名の打ち直し) → 無い資源を作る → バケットの設定(DES-018) → データのサービス(DES-011) → サービスの順に: D1 の移行(d1 migrations apply --remote)、Worker を作った設定と --secrets-file(0600 の一時ファイル)で上げ、compose から消えたシークレットと、受け取らなくなった Queue の受け手を消す
  • 作る設定: 組み立てたものをそのまま(no_bundle。横のファイルも ES モジュールとして)、バインディングは実際の名前と ID、Queue の受け手は Cloudflare の既定値、routes は / か * を含めばルート、含まなければ独自ドメイン。workers.dev の URL は、ports を持ち(外から呼ばれる Worker)routes の無い Worker だけに開く(手元で ports の無い Worker はリモートでも外から届かない)。プレビューの URL は開かない
  • 前回と同じ(組み立てたもの・作った設定・シークレットの値の要約が同じ)Worker は上げない。--dry-run は同じ段を通り、変えることを示すだけ(合言葉のファイルも作らない)
  • 移行が失敗したら、その D1 を使う Worker と、それより後のサービスは行わない
  • compose から消えた Worker は、記録と名前(<プロジェクト>-<環境>- で始まるもの)から見つけて示し、--remove-orphans のときだけ消す

DES-018R2 のバケットの設定 REQ-002・REQ-009

  • リモート: up が、バケットごとに compose ファイルの設定と Cloudflare の設定を比べ、違えば合わせる。作るときの storage_class・jurisdiction は r2 bucket create の引数、ほかは r2 bucket dev-url(public)・r2 bucket cors・r2 bucket lifecycle・r2 bucket notification・r2 bucket lock で入れる。compose ファイルから消した設定は消す
  • 手元: Wrangler の手元の模擬に無いもののうち、再現すると決めたもの(CORS・公開の URL・イベント通知)を道具のサービス(DES-011)で効かせる。公開は入口のサービスがバケットの公開の URL を配り、CORS は S3 互換の口と公開の URL の応答に付け、通知はオブジェクトの変化を手元の Queue へ送る。ライフサイクル・ロック・保管の種類は手元では効かせない(REQ-009)
  • 手元で、バインディングからの書き込み・消去(Worker のコードの env.FILES.put など)を道具のサービスが見る手立て(通知・ロックのため)は、作る前に確かめる(確かめていないこと)

DES-010Durable Objects のクラスの足し引き REQ-002・REQ-015

  • Wrangler の新しい宣言の形(exports。2026-07 から)を使う: compose の durable_objects の各クラスを {"type": "durable-object", "storage": "sqlite"} と宣言し、Cloudflare がいまの名前空間と比べて作る。移行のタグは持たない。もとから古いキー値の保存のクラスは legacy-kv のまま宣言する。手元も同じ宣言を使う
  • Cloudflare に名前空間があり compose から消えたクラスは、{"state": "deleted"} の墓標として宣言して消す
  • 消すクラスがあれば中身も消えるので、消すものとして示し、環境名の打ち直しで確かめる

DES-011道具のサービス REQ-017・REQ-013・REQ-016・REQ-006

  • データのサービス(手元だけ): その環境のすべての D1・R2・KV への、ふつうのバインディングを持つ Worker。同じ wrangler dev の中で動き、backup・restore・down --purge・ps が使う。リモートには置かない(REQ-017)。以前の版がリモートに置いた <プロジェクト>-<環境>-wc-data は、up・down が wrangler delete で消す
  • 入口のサービス(手元だけ): DES-008
  • 守り方: 256 ビットの乱数の合言葉を Worker のシークレットとして入れ、Authorization の見出しで一致する要求だけに応える(一定時間で比べる)。127.0.0.1 だけで受ける
  • 名前は wc-data・wc-gateway

DES-012down REQ-011

  • リモート: 依存の逆の順に delete。--purge なら、D1 は d1 delete、R2 はデータのサービスで空にしてから r2 bucket delete、KV は kv namespace delete、Queue は queues delete。下ろさないサービスがつながる資源があれば何も消さずに止まる
  • 消す前の数え(表・オブジェクト・キーの数)もデータのサービスと Wrangler で行う。打ち直しは 0.1 系のものを引き継ぐ
  • 手元: down は動いている up を止める。down web のように名前を付けると、動いている up がその Worker を外して動かし直し、ほかは動き続ける(データのサービスは手元では止めるものが無い)。下ろした Worker は、もう一度 up(up web)を打つと動いている up に戻る。下ろしたものが無いときの 2 つ目の up は止まる。--purge は止めたあと .wrangler/compose/local/state を消す。サービスを名前で指すと、そのサービスの資源とつなぐ資源(Durable Object の保存先を含む)だけを空にし、名前に無い Worker もつながる資源があれば、何も止めず何も消さずに止まる

DES-013ps・logs REQ-012

  • ps(リモート): Worker・資源は DES-004 の一覧、未適用の移行は D1 の履歴の表を API で SELECT で読む。compose に無い Worker は「残り」として出す。手元: 動いている記録と URL
  • logs(リモート): Worker ごとに wrangler tail --format json を並べて動かし、サービス名 | を頭に付けて出す(手元の受け手と同じ形)。過去のログは読めないので、-f が無くても今から追う。手元: up が書く .wrangler/compose/local/logs/up.log を読む(-f なら追う)

DES-014backup・restore REQ-013

  • D1・R2・KV のどれも、データのサービスで、その環境の中から書き出し・読み込む。道具は控えのファイルとの受け渡しだけを行う。D1 もデータのサービスで扱うのは、手元で up が動いている最中に別のプロセスから D1 を書き出す・戻すと、同時の書き込みで失敗する(SQLITE_BUSY。実測)ため
  • 控えの形(format: 3。環境によらず同じ。2 も読む): manifest.json(最後に書く。無いフォルダは書きかけ)に project・environment・created・資源ごとの type・key・ファイルと SHA-256。D1 は d1/<key>.jsonl(表の作り・行・索引など。1 行 1 つの JSON。BLOB は base64)、R2 は r2/<key>/ にオブジェクトとメタデータ、KV は kv/<key>.jsonl(キー・値(base64)・メタデータ・期限)
  • 戻すときは、資源の名前と型で compose ファイルに照らし、すべてのファイルの SHA-256 を確かめてから始める。D1 は表の作り → 行(50 行ずつ。外部キーは確かめを後回しにする)→ 索引などの順に入れ、最後に控えのあとの移行を当てる(移行の SQL の分け方は Wrangler の unstable_splitSqlQuery)。KV は戻す時点で期限が切れたものを戻さない
  • D1 は、すべての表と AUTOINCREMENT の数え(sqlite_sequence)を 1 つの batch(1 つのトランザクション)で読むので、up が動いている最中の控えも 1 つの時点のものになる。生成列は書き出さない(入れるときに計算し直される)。整数の主キーを持たない表は、隠れた rowid も残す
  • JSON では正しく運べない値(2^53 を超える整数、整数に見える実数・無限大、印の文字で始まる文字列)は、印(文字コード 1)を付けた文字列で書き、戻すときに CAST で元の型に戻す
  • restore --drop は消す前にいまの中身を .wrangler/compose/<環境>/before-restore/ に控え、途中で失敗すれば消して控えを戻す(成功すれば控えは消す)。空の先への restore が失敗したときは空に戻す
  • D1 の仮想表(FTS など)は控えられない(止まって示す)
  • 手元で up が動いていなければ、操作の間だけ入口とデータのサービスだけの実行環境を立てる

DES-015dry-run と確かめ REQ-014・REQ-015

  • どの操作も「確かめ → することの一覧を作る → 変える」の 3 段にし、--dry-run は 2 段目で一覧を示して終わる(止まる条件を本番と別に書かない)
  • 消すものを含む一覧は、変える前に環境名の打ち直しで確かめる(端末でなければ止まる)

DES-0160.1 系から引き継ぐもの

  • 引き継ぐ: .env の読み・git の確かめ・打ち直しの確かめ・止め方・表示の言語・D1 の書き出しと戻しと履歴の表の読み・控えの目録と書きかけの扱い
  • 作り直す: 設定の読み方(compose ファイルから作る)・up・down・restore・コマンド
  • 捨てる: S3 互換の API で R2 を扱う部分(データのサービスに置き換える)
  • 0.1 系の使い方との互換は持たない。版は 0.2.0

DES-017試験

  • 単体: compose ファイルの確かめ・値の展開・サービスの順・作る設定・Worker のフォルダの確かめ・Durable Objects のタグ・控えの目録
  • 手元の結合(CI。3 つの OS): 受け入れ条件の試験用のプロジェクトで、手元の AC(AC-003・AC-005・AC-008・AC-009・AC-013 の手元の分など)を動かす
  • リモートの流れ(CI。Linux): 偽の Cloudflare の API(tests/fake-cloudflare.py。CLOUDFLARE_API_BASE_URL で道具と Wrangler の両方を向ける)に対し、新しい環境の up(打ち直しを含む)・2 回目は何も上げない・シークレット/受け手/クラスを消す・移行の失敗で止まる・残りの Worker・ps・down web・down を通す。道具の段を確かめるもので、Cloudflare の本当の振る舞いではない
  • リモートの本物: 試験用のアカウントで、利用者の許可を得てから。まず --dry-run で全操作を通す

DES-019手元の R2 の口 REQ-009

  • 手元の模擬の S3 互換の口は、バケットの CORS の設定によらず、すべての送り元を許す(実測)。そのままでは手元で通って本番で失敗するので、ports を書いた r2 のサービスは、道具がそのポートで HTTP を受ける
  • キーの渡し方: 公開の URL のキーも、データのサービスへ渡すキーも、パスではなく問い合わせ(?key=)に入れる。キーの . や .. がパスの段として読まれて、バケットの外やほかの資源に届くことは無い。メタデータは百分率符号化して見出しで渡す(日本語も落ちない)。控えの目録が指すファイルは控えのフォルダの中だけで、外を指す目録は何もせずに止まる
  • S3 互換の口(/cdn-cgi/local/r2/s3/<バケット>): ブラウザの事前確認(OPTIONS)には、道具が compose ファイルの cors どおりに答える(合わなければ 403)。ほかの要求は、見出しを変えずに(署名がそのまま通る)入口の内側のポートの手元の模擬へ渡し、答えの CORS の見出しを捨てて cors どおりに付け直す。送り元の決まりは R2 と同じ(送り元に * を 1 つ書ける)
  • 外(LAN)から届いた要求: 手元の模擬は、/cdn-cgi/ への要求の Host と Origin のホスト名が localhost・127.0.0.1・[::1](か Worker の routes のホスト名)でなければ、署名を見る前に 403(Invalid Host header・Invalid Origin header)で断る(実測 2026-10-12・miniflare の entry worker。routes にアドレスを足すと Wrangler が要求の URL をそのホストに書き換えるので使えない)。そこで、Host か Origin がそれ以外の要求は、道具が手元の S3 の鍵で、届いたままの見出し(つないだアドレスの Host)で署名を計算して確かめる。合えば、Host を localhost:<ポート> に替え、Origin を外し、署名し直して手元の模擬へ渡す(見出しの署名は Authorization の Signature、署名付き URL は X-Amz-Signature を替える)。合わない・署名の無い要求は署名し直さずに同じく替えて渡し、手元の模擬に本物と同じ理由で拒ませる。日時・期限・鍵の範囲・本体のハッシュの検査は手元の模擬に任せる。署名の計算は手元の模擬と同じ(パスはそのまま・問い合わせはフォームの形で読んでから符号化して並べる・見出しの値は前後の空白を落とし続く空白を 1 つにする)。CORS の見出しは、外した Origin ではなく届いた Origin で cors どおりに付ける
  • 公開の URL: Host が <バケット名>.localhost の要求は、public: true のバケットだけ、データのサービスから中身を取って配る(内容の種類などの見出しを付ける)。範囲指定の取得(Range)と ETag には答えない
  • 1 つの接続で 1 つの要求だけを受け、答えたら閉じる(Connection: close)。HTTP の読み取りを見出しだけにするため

確かめていないこと(作る前・受け入れの前に確かめる)
