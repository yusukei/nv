wrangler-compose 設計

wrangler-compose の要求仕様(REQ)と受け入れ条件(AC)を満たす作り。Wrangler の振る舞いは、手元の Wrangler 4.128.0(wrangler-dist/cli.js)の実装と、手元の D1(miniflare)での実測で確かめた。Cloudflare には一度も触れていない。

この頁は、Wrangler の設定ファイルを正とした前の版の要求(0.1 系)に対する設計。要求仕様は compose ファイルを正とする形に書き直したので、この頁も合わせて書き直す。それまでは、確かめた事実と実測の記録として読む。

確かめた事実

事実出典
Wrangler の「対話できる」は process.stdin.isTTY && process.stdout.isTTY。対話できないとき、確かめの問い(confirm)は既定の答え(多くは「はい」)を使い、自動で作った資源の ID を設定ファイルへ書き戻さないisTtyInteractive・confirm2・provisionBindings
D1 の移行の適用(d1 migrations apply)の確かめは、対話できないと「はい」で進む。未適用が無ければ何もしないd1 migrations apply の実装
deploy --secrets-file は JSON か .env の形を受ける。ファイルに無いシークレットは前の版から残る(消えない)deploy の引数の説明・parseBulkInputToObject
設定は require("wrangler").unstable_readConfig({ env }) で、環境を当てはめた値(Worker 名・D1・R2・ルート・Cron・Durable Objects・ビルドのコマンド)が読める。環境の一覧は experimental_readRawConfig の envmarche-ar の workers/delivery/wrangler.jsonc で実測
D1 の書き出しは、表の作りと中身と、移行の履歴の表 d1_migrations を含む。D1 の内部の表 _cf_METADATA・sqlite_sequence は表を消しても残る手元の D1 で実測(--local)
表をすべて消した D1 に書き出しの SQL を流し、移行を適用すると、控えのあとに足した移行だけが当たる手元の D1 で実測(--local)
Cloudflare の側の D1 の書き出し(--remote)も d1_migrations を含み、restore --drop のあと控えのあとの移行だけが当たるtesting 環境で実測(wrangler-compose 0.1.0)
D1 の書き出しの間、その D1 は問い合わせに応えないd1 export の注意文
R2 の S3 API の口は https://<アカウント ID>.r2.cloudflarestorage.com、管轄のあるバケットは https://<アカウント ID>.<管轄>.r2.cloudflarestorage.com。署名の地域は auto。ListObjectsV2・DeleteObjects・GetObject・PutObject を受けるR2 S3 API・Data location
wrangler whoami --json はログインしたアカウントを accounts の配列で返し、ログインしていなければ 0 以外で終わるwhoami の実装
wrangler deploy --dry-run は、資源の自動作成とアップロードの分岐に入らずに終わるdeploy の実装(isDryRun の分岐)
wrangler secret list --format json は、シークレットの name を持つ配列を出すsecret list の実装
wrangler r2 bucket delete の管轄は --jurisdiction で渡す。d1 execute は --yes で確かめを飛ばせる各コマンドの引数の定義

手元の環境(local)のための事実。手元の Wrangler 4.149.0 で、2026-10-11 に実測した(Cloudflare には触れていない)。

事実出典
Wrangler 4.115.0 で、R2 バインディングに local_dev.experimental_s3_credentials(accessKeyId・secretAccessKey)が入った。書くと、手元の開発の間 /cdn-cgi/local/r2/s3/<バケット> に S3 互換の口が開く(<バケット> は bucket_name、無ければバインディング名)。受ける操作: GetObject・HeadObject・PutObject・CopyObject・DeleteObject・DeleteObjects・ListObjects・ListObjectsV2・HeadBucket・ListBuckets・分割アップロード一式。署名は SigV4 のヘッダと URL の両方。いまの下限 4.128.0 はこれを含むWrangler・miniflare の CHANGELOG(#14280)
Wrangler 5(alpha)では、手元の開発だけの設定が dev の下へまとめられ、R2 の手元の鍵も dev.experimentalS3Credentials の形へ移るminiflare の CHANGELOG(#15318・#15130)。実物では未確認
require("wrangler").unstable_startWorker({ config, dev: { server: { hostname, port }, inspector: false, watch }, bindings }) で手元の Worker が動く。bindings は設定のバインディングに足し・上書きする(上書きしなかった D1 も設定のまま使える)。R2 を { type: "r2_bucket", bucket_name, local_dev: { experimental_s3_credentials } } で上書きすると、設定ファイルを変えずに S3 の口が開く実測
口へ SigV4(地域 auto)で ListObjectsV2・PutObject が通り、Worker の env.BUCKET で置いたものが口で見え、口で置いたものが env.BUCKET.get で読める。違う鍵は 401実測(curl --aws-sigv4)
@aws-sdk/s3-request-presigner で口の URL http://127.0.0.1:<ポート>/cdn-cgi/local/r2/s3・forcePathStyle から作った署名付き URL で、鍵の無い curl から PUT・GET が通る。署名を変えると 403実測
unstable_startWorker の dev.watch: true で、コードを変えると作り直される。console.log と要求ごとの記録([wrangler:info] GET /a 200 OK)が標準出力に出る。.env.local の値が Worker の env に入る実測
手元のデータは .wrangler/state/v3/(d1・r2・kv など)。wrangler d1 migrations apply <DB> --local・d1 export <DB> --local は、unstable_startWorker と同じ置き場を読み書きする。書き出しの SQL は d1_migrations を含む実測
手元の Worker を同じポートで 2 つ動かすと、2 つ目は bind(): Address already in use で落ちる実測
unstable_startWorker を 2 つ、同じ dev.registry(dev registry のフォルダ)と同じ dev.persist で、別のポートに動かすと: サービスバインディング(services)と、ほかの Worker の Durable Object(script_name)の呼び出しが通る(Wrangler の表示は local [connected])。同じ bucket_name の R2 は 2 つの Worker から同じ中身が見え、どちらのポートの S3 の口からも見える。dev.persist に渡したフォルダの下に v3/ が作られる(wrangler dev の既定と同じ形)実測
wrangler dev -c a -c b(1 つの dev に複数の設定)は、最初の設定の Worker だけを外に見せ、ほかはサービスバインディングからだけ届く。複数の dev を別々に動かすと、どの Worker にも手元の URL がある。資料は、送り手と受け手を別の Worker にした Queues と、script_name で使う Durable Objects・Workflows には 1 つの dev を勧めている資料(Developing with multiple Workers)
wrangler dev -c a -c b の中身(MultiworkerRuntimeController)は Wrangler から外に出ていない。外に出ている createTestHarness は複数の Worker を 1 つにまとめるが、試験用(データを残さず、作り直しもしない)実装(require("wrangler") の公開の名前)
バインディングの種類ごとの手元の扱いは、Wrangler の BINDING_LOCAL_SUPPORT が決める: local-only(remote: true なら止まる)・local-and-remote・remote(手元に無い。remote: false なら止まり、書かなければ警告)・常に Cloudflare(remote: false なら止まり、書かなければ料金の警告)。表に無い種類は local-only 扱い。表は Wrangler から外に出ていない実装(getBindingLocalSupport・validateBindingRemoteSetting)
Queues は表では local-and-remote だが、miniflare は remote: true を無視する(workers-sdk #13727)実装(表の注記)

設計

DES-001作りの全体 REQ-002・REQ-010

  • ワークスペースのクレート crates/wrangler-compose。nv のクレートのコードには頼らない(要るものは自前で持つ)
  • 頼るクレート: clap・ureq 3・rusty-s3(S3 の署名だけを作る。HTTP は ureq で送る)・serde_json・sha2
  • 却下: AWS の公式 SDK(非同期の実行環境を抱え、実行ファイルが大きくなる。使う S3 の操作は 4 つだけ)
  • 却下: R2 も Wrangler で扱う(Wrangler はオブジェクトの一覧が取れない。要求仕様の決定)

DES-002Wrangler の呼び方 REQ-002

  • nv は wrangler-compose の実行ファイルと同じフォルダの nv(Windows は nv.exe)を使う。無ければ止まり、入れ方を示す
  • Wrangler はプロジェクトのフォルダで nv run wrangler <引数> --env <環境名> として動かす
  • 標準入力は常に空にする。Wrangler から見て対話できない状態にし、(1) 自動で作った資源の ID を設定ファイルへ書き戻させない、(2) Wrangler の確かめの問いで止まらせない。人への確かめは wrangler-compose が自分で行う(DES-008)
  • Wrangler の出力は、そのまま利用者の画面へ流す(何が起きているかを見せる)。結果を読む必要があるもの(--json)だけ取り込む
  • 要る版は 4.128.0 以上(確かめた版。--secrets-file が入った版は資料で確かめられなかったので、確かめた版を下限にする)。設定を読むときに版も読み、下回れば止まる
  • 却下: 環境変数 CI=true で対話を止める(ほかの振る舞いも CI 向けに変わる。標準入力を空にすれば足りる)
  • 成り立たない場合: Wrangler が「対話できない」の判定を変えると、書き戻しが起きうる。up の前後で設定ファイルが変わっていないかを確かめ、変わっていれば止まって示す(AC-002 の確かめを毎回行う)

DES-003設定の読み方 REQ-001・REQ-002

  • wrangler-compose に埋め込んだ小さな JavaScript を、nv run node -e <スクリプト> <環境名> で動かす。スクリプトはプロジェクトの wrangler を読み、unstable_readConfig の結果から要るものだけを JSON で標準出力に出す: Worker 名・D1(バインディング・名前・ID・移行のフォルダ)・R2(バインディング・バケット名・管轄)・ルート・Cron・Durable Objects・account_id・環境の一覧・Wrangler の版
  • プロジェクトは、いまいるフォルダから上へたどって最初に Wrangler の設定ファイルがあるフォルダ
  • 却下: JSONC・TOML を自前で読む(Wrangler の読み方と食い違う。要求仕様の決定)
  • 成り立たない場合: unstable_ の名のとおり Wrangler の版で形が変わりうる。読めなかった項目があれば止まり、確かめた版を示す

DES-004環境の指定 REQ-001

  • --env/-e を先に、無ければ CLOUDFLARE_ENV を見る。build 以外で環境が無ければ止まる
  • 設定の環境の一覧(DES-003)に無い名前なら止まり、一覧を示す。前方一致などで補わない

DES-005.env.<環境名> と git REQ-004・REQ-009・REQ-007

  • .env.<環境名> はプロジェクトのフォルダのものを読む。書式は .env の基本(名前=値、# の行、引用符で囲んだ値)
  • WRANGLER_COMPOSE_ で始まるものを除いた値を、一時のフォルダに JSON で書き(Unix は 0600)、--secrets-file で渡す。デプロイが終われば、失敗しても消す
  • API キーは環境変数を先に、無ければ .env.<環境名> から読む
  • git の確かめは git の読み取りのコマンドで行う: git rev-parse --show-toplevel(git の中か)、git check-ignore -q(外れているか)、git ls-files --error-unmatch(すでに入っているか)。git が無い、または git の中でなければ確かめない。git に書き込む操作はしない
  • 却下: .gitignore を自前で読む(否定・入れ子・グローバルの設定まで git と同じに読むのは難しい)

DES-006build REQ-003

  • wrangler deploy --dry-run --outdir <一時のフォルダ> を動かす(設定のビルドのコマンドも走り、Cloudflare には上げない)

DES-007up REQ-004

  1. 設定を読む(DES-003)。.env と git を確かめる(DES-005)
  2. wrangler d1 list --json で、アカウントにある D1 の名前と ID を得る。設定の各 D1 が、ID があれば ID で、無ければ名前であるかを見る。ID を書いた D1 が無ければ、名前と ID を示して止まる
  3. すべてあれば: 移行のフォルダに .sql がある D1 ごとに wrangler d1 migrations apply <バインディング> --remote → wrangler deploy [--secrets-file]
  4. 無いものがあれば: wrangler deploy [--secrets-file](Wrangler が D1・R2 を作る) → 移行の適用。移行で止まったら、デプロイは済んでいることを示す
  5. wrangler secret list --format json で、Worker にあって .env.<環境名> に無いシークレットの名前を示す(.env があるときだけ)
  6. 設定ファイルが up の前と同じかを確かめる(DES-002)
  • 段ごとに「[1/3] D1 の移行」のように示し、止まった段と理由を出す

DES-008打ち直しの確かめ REQ-005・REQ-006・REQ-008

  • 端末かどうかは、down・down --purge・restore --drop の最初に見る(Cloudflare に問い合わせる前に止まる)
  • 標準入力と標準エラーの両方が端末のときだけ、環境名を打ってもらう。どちらかが端末でなければ、何も消さずに止まり、端末から打つよう示す
  • 打った文字列の前後の空白を除いて、環境名と完全に一致したときだけ進む

DES-009down REQ-005

Worker があるかは、wrangler secret list(読み取り)の結果で見る。Wrangler に「あるか」を問う口が無く、無い Worker には「not found」で失敗するため(testing 環境での dry-run で確認)。無ければ、消すものは無いと示して終わる。

  1. 消えるものを示す: Worker 名、シークレットの名前(wrangler secret list)、設定のルート・カスタムドメイン・Cron・Durable Objects
  2. 打ち直しの確かめ(DES-008)
  3. wrangler delete は、利用者の端末をつないで動かす(delete だけは標準入力を空にしない)。ほかの Worker が頼っているとき、Wrangler は頼っている先を並べて強制で消すかを尋ねるが、標準入力が空だと既定の「はい」で強制削除まで進んでしまう(4.128.0 の checkAndConfirmForceDeleteIfNecessary と confirm2 で確認)。端末をつなげば、その問いに利用者が答える。Wrangler 自身の「本当に消すか」の問いにも、もう一度答えることになる。書き戻しはデプロイでしか起きないので、delete を対話で動かしても DES-002 は崩れない

DES-010R2 の S3 API REQ-006・REQ-007・REQ-008・REQ-009

  • アカウント ID は、設定の account_id、無ければ wrangler whoami --json のアカウントが 1 つならそれ。複数あって決められなければ、設定に account_id を書くよう示して止まる
  • 口は管轄が無ければ https://<アカウント ID>.r2.cloudflarestorage.com、あれば https://<アカウント ID>.<管轄>.r2.cloudflarestorage.com。地域は auto
  • キーが正しいかは、各バケットへの ListObjectsV2(1 件)が通るかで見る。403 などは「キーが無い・正しくない」として、何もせずに止まる
  • オブジェクトの消去は DeleteObjects で 1000 件ずつ。消えた件数は応答の Deleted から数え、途中で失敗しても呼び出し元へ返す(途中経過の報告に使う)
  • 時間切れ: 接続 30 秒・要求の送信 60 秒・応答の受け取り 120 秒(ureq の既定はどれも無し)。本体の受け取りには上限を付けない(大きなオブジェクトがあるため)

DES-011down --purge REQ-006

  1. API キーを確かめ(DES-010)、各バケットのオブジェクトの数を数える
  2. 消すものを示す(DES-009 の 1 に加えて、D1 の名前、バケットの名前とオブジェクトの数、database_id を書いた D1 は次の up で作られないこと)
  3. 打ち直しの確かめ
  4. Worker を消す(すでに無ければ飛ばす。down のあとの --purge) → 各バケットのオブジェクトを消してバケットを消す(wrangler r2 bucket delete) → 各 D1 を消す(wrangler d1 delete -y)。Worker を先に消すのは、消している途中のデータを人に見せないため
  5. 途中で止まったら、消し終えたものと残っているものを並べて示す
  6. すでに無いバケット・D1(途中で止まった前回の --purge で消えたもの)は飛ばして、残りを消す。打ち直せば最後まで消せる。何も残っていなければ、そう示して終わる(testing 環境で確認)

DES-012backup REQ-007

  • 書き出し先: 引数が無ければプロジェクトの backups/。その下の <環境名>/<協定世界時の日時 yyyyMMddTHHmmssZ>/
  • 中身:
    • d1/<バインディング>.sql: wrangler d1 export <バインディング> --remote --output …
    • r2/<バインディング>/<通し番号>: 各オブジェクトの中身(キーは目録に持ち、ファイル名には使わない。キーに使えない文字があっても書ける)
    • manifest.json: 環境名・作った日時・Wrangler の版・D1 ごとのファイル・R2 ごとのオブジェクト(キー・ファイル・大きさ・SHA-256・内容の種類などの見出し・利用者のメタデータ)
  • manifest.json を最後に書く。目録の無いフォルダは書きかけ(restore は受けない)。目録には Wrangler の版も書く
  • 日時のフォルダは毎回新しく作る(あれば止まる。同じ秒の 2 回目が前の控えに書き込まない)
  • 書き出し先がプロジェクトの git の外なら、git の確かめはしない
  • 書き出し先がプロジェクトの git の中にあれば、DES-005 と同じ確かめを backups/(または渡された場所)に対して行う
  • D1 の書き出しが失敗したら(書き出せない表があるなど)、Wrangler の理由を示して止まる。目録は書かない

DES-013restore REQ-008

  1. 目録を読む。無ければ書きかけとして止まる。D1 の SQL に d1_migrations の表が無ければ(移行の履歴が無い)止まる
  2. API キーを確かめる。戻す先の D1(d1 list)とバケット(ListObjectsV2)があるかを見る。無ければ up を求めて止まる
  3. 空かを見る: D1 は wrangler d1 execute … --json で、sqlite_・_cf_ で始まらない表があるか。バケットはオブジェクトが 1 つでもあるか
  4. 控えの R2 のすべてのファイルがあり、SHA-256 が目録と合うことを、何かを消す前に確かめる(1 つでも合わなければ何も変えずに止まる)
  5. 空でなく --drop が無ければ止まる。--drop なら消すもの(表の数・オブジェクトの数)を示す。--drop の有無によらず、戻している間に欠けたデータが見えることを示す。--drop なら打ち直しの確かめ
  6. --drop: 表・ビュー・トリガーを DROP し(外部キーの順に左右されないよう PRAGMA defer_foreign_keys=ON を付けて 1 回で流す)、バケットのオブジェクトを消す
  7. wrangler d1 execute <バインディング> --remote --file <SQL> で D1 を戻し、PutObject で各オブジェクトを、目録の見出しとメタデータを付けて戻す(戻す前に SHA-256 を照らす)
  8. 移行の適用(DES-007 の 3 と同じ)で、控えのあとに足された移行を当てる

DES-014出力と終了コード REQ-009

  • wrangler-compose 自身の出力は標準エラーへ(nv と同じ)。自身が止まったときの終了コードは 2
  • 言語(REQ-012)の決め方と書き方は nv の DES-012 と同じ(NV_LANG → OS の言語。tr!("日本語", "English"))。nv のクレートには頼らず、同じ小さな仕組みを自分で持つ(DES-001)
  • シークレットの値と API キーは、どこにも出さない。シークレットは名前だけを示す。目録にも書かない
  • Ctrl+C を受けても wrangler-compose はすぐには終わらない。端末の Ctrl+C は Wrangler にも届いてそちらが止まり、wrangler-compose は後片付け(シークレットの一時ファイルの消去)と、何をして何が残っているかの報告を済ませてから終わる。Wrangler を動かしていない段(R2 のオブジェクトごとの処理)では、1 件ごとに中断を見る
  • up で、デプロイのあとのシークレットの一覧に失敗しても、警告にとどめる(デプロイが済んだことを隠さない)

DES-015試験

  • 単体: .env の読み、環境の選び方、目録の読み書き、S3 の口の組み立て、空かの判定に使う表の名前の選り分け
  • 手元の結合: 実行ファイルを動かし、Cloudflare に触れない範囲(環境の指定の誤り、nv が無い、.env が git に入っている、端末でない down、書きかけの控え、build)を確かめる
  • 手元の環境の受け入れ条件(AC-013〜AC-017、AC-018・AC-020・AC-021)は Cloudflare に触れないので、CI(Windows・macOS・Linux)で毎回動かす: 試験用のプロジェクトで --env local up を裏で動かし、Worker と S3 の口(署名付き URL を含む)を確かめ、backup → down --purge → restore を通して中身が一致することを見る
  • Cloudflare を相手にする受け入れ条件は、試験用のアカウントで、利用者の許可を得てから行う。まず全操作を --dry-run で通し、次に使い捨ての環境で up → backup → restore --drop → down → down --purge を実際に動かす

DES-016dry-run REQ-011

  • --dry-run はどの操作にも付く共通の引数。各操作は本番と同じ確かめ(設定・.env と git・API キー・控えの照合・戻す先の有無と空かどうか)を同じ順で行い、変える段の直前で「何をするか」を示して終わる。止まる条件を本番と別に書かないことで、dry-run が通れば本番もそこまでは通ることを保つ
  • dry-run で動かす Wrangler は読み取りだけ: d1 list・secret list・whoami・d1 execute の SELECT・deploy --dry-run(組めるか)。R2 は ListObjectsV2 だけ
  • 未適用の移行は、移行の履歴の表(既定 d1_migrations。設定の migrations_table があればそれ)を SELECT で読み、移行のフォルダの .sql の名前から適用済みを除いて求める。表が無ければすべてが未適用。d1 migrations list は使わない: 履歴の表が無いと作る(CREATE TABLE IF NOT EXISTS。4.128.0 の initMigrationsTable)ので、何も変えない約束が破れる
  • 打ち直しの確かめと、端末であることの確かめは飛ばす(何も消さないので、エージェントからも打てる)
  • 手元のファイルも書かない: backup は書き出し先のフォルダを作らず、up はシークレットの一時ファイルを作らない(名前だけを示す)
  • 却下: Wrangler の dry-run だけに頼る(deploy と delete にしか無く、D1・R2 の操作を確かめられない)
  • 成り立たない場合: 読み取りから実際の操作までの間に Cloudflare の側が変われば(ほかの人のデプロイなど)、本番の結果は dry-run の表示と違いうる

DES-017local の受け持ち方 REQ-013

  • 環境の指定(DES-004)で local を先に見分ける。設定は環境なし(一番上の階層)で読み(DES-003 のスクリプトに環境名を渡さない)、環境の一覧に local があれば止まる
  • Project に「Cloudflare か手元か」を持たせ、Wrangler の呼び方を 1 か所で切り替える: Cloudflare は --env <環境名> と --remote、手元は --env を付けず --local。いま d1.rs・backup.rs・restore.rs に散らばる "--remote" は、この切り替えを通す
  • 手元の操作は whoami・d1 list・secret list など Cloudflare に問う段を通らない。アカウント ID も求めない
  • .env.local の git の確かめは DES-005 と同じ。.env.local を Wrangler の --secrets-file に渡す段は持たない(Wrangler が手元の開発で自ら読む)
  • DES-003 のスクリプトが読むものに、R2 ごとの local_dev.experimental_s3_credentials(有無)、dev.port・dev.ip を足す
  • 却下: local を設定の env.local と読む(手元のために設定へ環境を足させることになり、wrangler dev の既定とも食い違う)

DES-018手元の Worker の動かし方 REQ-014・REQ-015・REQ-017

  • wrangler-compose に埋め込んだ JavaScript を nv run node -e <スクリプト> <JSON の引数> で動かす(DES-003 と同じ形)。スクリプトはプロジェクトの wrangler の unstable_startWorker を呼ぶ: config は設定ファイル、dev.server は DES-020 のアドレスとポート、inspector: false、watch は up なら true・一時の口なら false、bindings は R2 バインディングごとに { type: "r2_bucket", bucket_name, jurisdiction, local_dev: { experimental_s3_credentials: 手元の鍵 } }
  • 動き出したら、スクリプトは標準出力に目印の行(@@WRANGLER_COMPOSE_READY@@ と URL の JSON)を出す。wrangler-compose はそれを読んで REQ-014 の案内を出し、ほかの出力(Worker のログ)はそのまま流す
  • スクリプトは SIGINT・SIGTERM で dispose() してから終わる。wrangler-compose は Ctrl+C を受けても自分では終わらず、子が終わるのを待つ(DES-014 の終了コードは子に合わせる)
  • Wrangler 5 以上では bindings の形が変わりうる(確かめた事実)。版を見て、確かめた形の分からない版なら R2 の上書きをせずに動かし、口が開かないことを示す(REQ-015)。確かめた版の範囲は設計に書き足していく
  • 却下: 設定ファイルに鍵を書き足して wrangler dev を動かす(REQ-002 で設定を書き換えない)
  • 却下: 鍵を足した設定を別のフォルダに書いて wrangler dev -c に渡す(main・assets・移行のフォルダなどの相対パスが設定ファイルの場所で決まり、書き換えが要る)
  • 却下: S3 の口を Rust で自前に作り、miniflare の置き場を直に読み書きする(置き場の形は miniflare の内側のもので、版で変わる)
  • 却下: wrangler dev をそのまま動かし、鍵は利用者に設定へ書いてもらう(それでも動くように DES-022 の 1 番目の鍵として受けるが、書かなくても使えることを既定にする)
  • 成り立たない場合: unstable_ の名のとおり形が変わりうる。unstable_startWorker が無い・投げるときは、理由と確かめた版を示して止まる。wrangler dev の対話のキー(b・x など)は出ない(要るなら nv run wrangler dev を直接打つ)

DES-019動いている up の記録 REQ-014・REQ-016・REQ-017

  • --env local up は、プロジェクトの .wrangler/compose/local.lock に排他の錠(File::try_lock)をかけて持ち続け、動き出したら .wrangler/compose/local.json に子の PID・Worker の URL・S3 の口の URL を書く。終わるときに消す
  • .wrangler/ は Wrangler が手元の開発のために作る作業のフォルダで、Wrangler の雛形は git から外している。wrangler-compose が書くのは .wrangler/compose/ の下だけ
  • 動いているかは「錠が取れないこと」で見る(PID の使い回しや、落ちて残った local.json に惑わされない)。錠が取れれば、残った local.json は消す
  • 2 つ目の up は錠が取れないので止まり、local.json の URL を示す。backup・restore・down --purge は、錠が取れなければ local.json の口を使い、取れれば錠を持ったまま一時の口を開く(DES-022。その間に up が始まらない)
  • 止め方: Unix は子の PID に SIGTERM、Windows は taskkill /PID <PID> /T。10 秒待って錠が外れなければ、強く止める(SIGKILL・taskkill /F)

DES-020local の up REQ-014

  • 段: 設定を読む → .env.local と git → 錠(DES-019) → 手元の鍵(DES-022) → 移行のフォルダを持つ D1 ごとに wrangler d1 migrations apply <DB> --local(標準入力は空。DES-002 で、確かめの問いは「はい」で進む) → 手元の Worker(DES-018) → 案内
  • アドレスは設定の dev.ip、無ければ 127.0.0.1。ポートは dev.port、無ければ 8787。動かす前に、そのアドレスとポートで待ち受けられるかを Rust で確かめ(すぐ閉じる)、使えなければ止まる(Wrangler に別のポートを選ばせない。案内した URL と食い違うため)
  • 案内: Worker の URL、S3 の口の URL(http://<アドレス>:<ポート>/cdn-cgi/local/r2/s3)、地域 auto・パス形式、バケットごとの バインディング → バケット名、手元の鍵(とどこから選んだか)
  • dry-run: 当てる移行の名前、開く口、選ばれる鍵を示す。未適用の移行は DES-016 と同じく履歴の表を SELECT で読むが、手元の置き場がまだ無ければ問わずにすべてを未適用とする(問うと置き場ができ、何も変えない約束が破れる)

DES-021local の down REQ-016

  • down: 錠が取れれば「動いていない」と示して 0 で終わる。取れなければ DES-019 の止め方で止め、錠が外れるまで待つ
  • down --purge: (1) 動いていれば止める → (2) 錠を取る → (3) 消すものを数える(D1 は d1 execute --local の SELECT、R2 は一時の口の ListObjectsV2) → (4) 打ち直し(DES-008。local) → (5) .wrangler/state/ を消す
  • 消すのは .wrangler/state/ だけ。設定で persist の置き場を変える手立ては Wrangler の --persist-to だけで、wrangler-compose はそれを使わないので、置き場は常にここ

DES-022手元の S3 の口と鍵 REQ-015・REQ-017

  • 手元の鍵の選び方: (1) 設定の R2 バインディングの local_dev.experimental_s3_credentials(バインディングごと) → (2) 環境変数 → .env.local の WRANGLER_COMPOSE_R2_ACCESS_KEY_ID・WRANGLER_COMPOSE_R2_SECRET_ACCESS_KEY → (3) 決まった値 wrangler-compose-local・wrangler-compose-local-secret(要求仕様の決めること 2 の案 A)。(1) があるバインディングは上書きの鍵に (1) をそのまま入れる
  • wrangler-compose が手元の R2 を読み書きするときは、DES-010 の r2::Store をそのまま使い、口だけを差し替える: 口は http://127.0.0.1:<ポート>/cdn-cgi/local/r2/s3、パス形式、地域 auto、鍵は上の手元の鍵。Store の作り方を「アカウントと管轄から」と「口の URL から」の 2 つにする
  • 一時の口: up が動いていなければ、DES-018 を watch: false、空いているポート(127.0.0.1:0 で開いて番号を得て閉じたもの)で動かし、操作が終われば(失敗しても、Ctrl+C でも)止める

DES-023local の backup・restore REQ-017

  • backup.rs・restore.rs は、DES-017 の切り替え(--local/--remote)と DES-022 の Store の作り方の違いだけで、Cloudflare と手元の両方を受け持つ。控えの形(目録の format: 1)は変えない。手元の控えの目録の environment は local
  • 手元では、API キーの確かめ(DES-010 のキーの確かめ)とアカウント ID を飛ばし、D1・バケットがあるかの確かめ(d1 list)も飛ばす(REQ-017)
  • restore は、戻す前に目録の environment を「控えを取った環境」として示す
  • D1 の書き出しは d1 export <DB> --local、戻しは d1 execute <DB> --local --yes --file、移行は d1 migrations apply <DB> --local

DES-024compose ファイルの読み方 REQ-018

  • YAML を読むクレートを 1 つ足す。候補は serde-saphyr(YAML 1.2、純 Rust)と serde_yaml_ng(serde_yaml の後継)。作る時点で手入れが続いている方を選ぶ。serde_yaml は手入れが止まっているので使わない
  • いったん serde_json::Value の木に読み、自前で確かめる(serde の deny_unknown_fields では、x- を許しつつ知らないキーで止まる、という docker と同じ決まりを書けない)。知らないキーは、どこ(services.web.environment など)にあるかを示して止まる
  • 探し方: いまのフォルダから上へ、各フォルダで wrangler-compose.<環境名>.yaml・.yml、wrangler-compose.yaml・.yml を見て、どれかがある最初のフォルダで止まる。そのフォルダに環境のファイルがあればそれを、無ければ共通のファイルを使う(置き換え。中身は混ぜない)。同じ名前の .yaml と .yml が両方あれば止まる。環境名は --env(無ければ CLOUDFLARE_ENV)のもので、環境の指定の無い build は共通のファイルだけを見る。compose ファイルより先に Wrangler の設定ファイルが見つかっても、上へたどるのをやめない(サービスのフォルダの中で打っても、まとめた全体を使う。docker と同じ)。見つからなければ DES-003 の探し方に戻る
  • compose ファイルが無いときは、Wrangler の設定ファイルのフォルダを compose の根とし、その Worker の名前(無ければフォルダ名)のサービス 1 つを持つものとして扱う。以下の作りは、サービスが 1 つの場合もいつも同じ道を通る(分かれ道を作らない)
  • ports の短い書き方は "ポート:ポート"・"アドレス:ポート:ポート"。IPv6 のアドレスは "[::1]:8787:8787"
  • 設定はサービスごとに DES-003 のスクリプトで読む。スクリプトは compose の根で動かし、unstable_readConfig に設定ファイルのパスを渡す(Wrangler は compose の根の node_modules のもの)
  • サービスのフォルダに package.json があり、compose の根と違うフォルダなら、組む前にそのフォルダで nv sync を動かす(Wrangler の組み立ては、各サービスのフォルダから node_modules を探す)

DES-025サービスの順と絞り込み REQ-019・REQ-020

  • 順は depends_on だけで決める。トポロジカルソートで、決まらないところは compose ファイルに書いた順。輪があれば、輪になっているサービスを示して止まる
  • build・up に名前を渡せば、その名前から depends_on をたどって閉じた集まりを作る。down に名前を渡せば、その名前だけ。どちらも、知らない名前なら止まる
  • 依存の知らせ(REQ-019): 環境を当てはめた設定の services[].service と、Durable Objects の script_name を、ほかのサービスの Worker の名前(同じ環境を当てはめたもの)と照らし、depends_on をたどった先に無ければ知らせる
  • up の途中で止まったら、済んだサービス・止まったサービス・行っていないサービスを並べて示す(DES-014)

DES-026共有する資源と控えの形 REQ-019

  • 資源の見分け: D1 は database_id、無ければ database_name。R2 はバケット名と管轄。環境を当てはめた値で比べる(手元ではバケット名・D1 の名前で比べる。miniflare の置き場の分け方と同じ)
  • 移行: 同じ D1 を使うサービスの移行のフォルダを、実際のパス(canonicalize)と履歴の表の名前で比べ、違えば止まる。同じなら最初のサービスの段で 1 度だけ当てる
  • 控えの目録を format: 2 にする: name・services(サービス名と Worker 名)・d1 と r2 は資源ごとに 1 つで、users にそれを使う [サービス, バインディング] の組を並べる。restore は、目録の users の組が、いまの compose のどの資源に当たるかで照らす(1 つの資源に当たらなければ止まる)
  • format: 1 の控え(compose 以前)は、サービスが 1 つのときだけ、そのサービスの控えとして読む
  • down --purge は、消す資源ごとに、下ろさないサービスの users が無いかを先に見て、あれば何も消さずに止まる

DES-027手元でまとめて動かす REQ-020

  • サービスごとに、DES-018 のスクリプトを別の子プロセス(nv run node -e …)として、依存の順に動かす。前のサービスの目印の行(READY)を待ってから次を動かす
  • すべての子に、同じ dev.registry(compose の根の .wrangler/compose/registry/)と同じ dev.persist(compose の根の .wrangler/state/)を渡す。サービスの間のつながりは dev registry が受け持つ(確かめた事実)
  • 子の標準出力・標準エラーは wrangler-compose が 1 行ずつ読み、サービス名 | を頭に付けて出す(docker compose と同じ形。名前は桁をそろえる)。子を分けるのはこのため(1 つの Node の中に複数の Worker を置くと、Wrangler のログが混ざって見分けられない)
  • ポート: ports → 設定の dev.port → 8787 から順に空いている番号。決めたすべてのポートを、動かす前に Rust で待ち受けられるか確かめる(DES-020)
  • DES-019 の記録(local.json)は、子の PID と URL の一覧にする。錠は compose の根に 1 つ。止めるときは依存の逆の順に止める。1 つの子が落ちたら、残りも止めて、どのサービスが落ちたかを示す(docker compose の --abort-on-container-exit の振る舞いを既定にする。手元で一部だけが動いている状態を作らない)
  • 却下: wrangler dev -c a -c b を動かす(S3 の口の鍵を差し込めない(DES-018)。最初の Worker にしか手元の URL が無い)
  • 却下: createTestHarness を使う(試験用で、データを残さず、作り直しもしない)
  • 成り立たない場合: 送り手と受け手を別のサービスにした Queues が、別々の dev のあいだで届かないかもしれない(資料は 1 つの dev を勧めている)。届かなければ 手元で使えないものに書き、REQ-021 の知らせに足す

DES-028手元で使えないものの見分け REQ-021

  • DES-003 のスクリプトで、設定のバインディングを unstable_convertConfigBindingsToStartWorkerBindings で種類つきの一覧にし、種類・バインディング名・remote の値を JSON で返す。ほかに routes・triggers.crons・placement・limits・tail_consumers・logpush・containers・Hyperdrive の localConnectionString の有無を返す
  • 種類ごとの扱いは、Wrangler の BINDING_LOCAL_SUPPORT(確かめた事実)を写した表を wrangler-compose の中に持つ。表は Wrangler から外に出ていないため。表を写した Wrangler の版(4.149.0)を持ち、それより新しい Wrangler では、表に無い種類を「分からない」と示す
  • 止まるのは、Wrangler が止まるのと同じ組み合わせだけ(local-only に remote: true、remote と常に Cloudflare のものに remote: false)。Wrangler を動かす前に、サービス名とバインディング名をつけて示す
  • Hyperdrive は、設定の localConnectionString も、環境変数 CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_<バインディング名> も無ければ知らせる。Containers は、docker が PATH に無いか docker info が失敗すれば知らせる
  • 文言と項目は 手元で使えないものの頁と 1 対 1 にする(頁の項目を足したら、知らせの表も足す)

確かめていないこと(作る前・受け入れの前に確かめる)

  • Cloudflare の側の D1 で、外部キーのある表を defer_foreign_keys を付けて消せること
  • R2 の PutObject の 1 回の上限を超える大きなオブジェクト(分割アップロードが要るもの)。当面は上限を超えるものがあれば restore の前に止める
  • 手元: unstable_startWorker の Windows での振る舞い(taskkill /T で子の workerd まで止まり、置き場が壊れないこと)
  • 手元: up が動いている間に d1 export・d1 execute --local を別のプロセスから動かしても、SQLite の錠で失敗しないこと
  • 手元: rusty-s3 が、パスの付いた口の URL(/cdn-cgi/local/r2/s3)にバケット名を正しく継ぎ足して署名すること
  • 手元: Wrangler 5 での unstable_startWorker の bindings の形
  • 手元の複数の Worker: 送り手と受け手を別のサービスにした Queues と、script_name で使う Workflows が、別々の dev のあいだで通ること(DES-027)
  • 手元の複数の Worker: 同じ D1 を 2 つの workerd が同時に書いても壊れないこと(R2 の共有は確かめた)
  • Cloudflare: サービスバインディングの先の Worker がまだ無いときに、wrangler deploy が止まるか(depends_on の順が要る理由。止まらないなら、知らせは弱めてよい)
  • 手元で使えないものの頁の「推測」の項目(ルート・Smart Placement・上限・ゾーンの機能・R2 のバケットの設定・D1 の Time Travel・KV の整合性・キャッシュ)
