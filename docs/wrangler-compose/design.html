wrangler-compose 設計

要求仕様(compose ファイルを正とする版)と受け入れ条件を満たす作り。Wrangler は中の実行役として使い、足りないところは wrangler-compose が作る。事実は手元の Wrangler 4.149.0 で 2026-10-11 に実測・読み取りした(Cloudflare には触れていない)。

確かめた事実

事実出典
手元の Worker を別々の実行環境(workerd)で 2 つ動かし、同じ手元の D1 に同時に書くと、40 回中 10 回が database is locked: SQLITE_BUSY で失敗する実測
wrangler dev -c a -c b(1 つの実行環境に複数の Worker)では、同じ書き込み 40 回がすべて通る。Queue の送り手と受け手を別の Worker にしても届き、共有する KV も見える。外から届くのは最初の設定の Worker だけで、ほかはサービスバインディングから届く実測・資料
最初の Worker を入口にし、ポートごとに TCP をそのまま入口のポートへ中継すると、入口の Worker から見える要求の URL と Host は、利用者がつないだポートのまま。入口がポートで振り分けてサービスバインディングへ渡すと、渡した先の Worker からも元の URL のまま見える実測
R2 バインディングに local_dev.experimental_s3_credentials を書くと、手元の開発で /cdn-cgi/local/r2/s3/<バケット> に S3 互換の口が開く(SigV4 のヘッダと署名付き URL の両方。違う鍵は 401、署名を変えると 403)。バインディングと同じ中身が見える実測・CHANGELOG(4.115.0)
Wrangler のログイン(OAuth)の既定の権限には、R2 の中身を一覧する REST の口が無い(r2 object は get・put・delete だけ)。一覧には S3 互換の API とその API キーが要る実装(DefaultScopes・r2 object の定義)
バインディングに remote: true を書くと、手元で動く Worker から Cloudflare の本物の資源を使える(remote bindings)。手元とリモートが混ざるので、wrangler-compose は使わない(REQ-020)資料
Worker の R2 バインディングは list(1000 件ずつ、cursor で続き)・get(本体はストリーム)・put(ストリームを受ける)・delete(1000 件まで一度に)を持ち、KV バインディングは list(1000 件ずつ)・getWithMetadata・put(expiration・metadata)・delete を持つ。どれも Worker の中で、その環境の資源に対して動く資料(R2・KV の Workers API)
手元のデータの置き場は --persist-to で決められ、その下に v3/ が作られる。d1 migrations apply・d1 export・d1 execute は --local --persist-to で同じ置き場を読み書きする実測
D1 の書き出しは表の作りと中身と d1_migrations を含み、表を消した D1 に流して移行を当てると、控えのあとの移行だけが当たる(手元・Cloudflare とも)実測(0.1 系)
Wrangler の標準入力を空にすると、確かめの問いは既定の答えで進み、自動で作った資源の ID を設定ファイルへ書き戻さない実装(0.1 系で確認)
deploy --secrets-file はファイルに無いシークレットを消さない(前の版から残る)実装(0.1 系で確認)
バインディングの種類ごとの手元の扱いは Wrangler の BINDING_LOCAL_SUPPORT が決める。使う型(D1・R2・KV・Queue・サービス・Durable Objects)はどれも手元で動く実装

設計

DES-001作りの全体 REQ-001・REQ-018

  • クレート crates/wrangler-compose を作り直す。流れは: compose ファイルを読む(DES-002) → 変数を展開する(DES-003) → サービスの順を決める → 環境ごとの Wrangler の設定を作る(DES-005) → nv run wrangler … で動かす
  • wrangler-compose が作るものは、すべてプロジェクトの .wrangler/compose/<環境>/ の下に置く: 作った Wrangler の設定、資源の記録(DES-004)、手元のデータ(local/state/)、手元のログ。プロジェクトのファイルは書き換えない
  • Wrangler は compose の根の package.json の版を使う。Worker のフォルダに別の package.json があれば、組む前にそこで nv sync を動かす
  • 前の版(0.1 系)のコードのうち、使えるもの(.env の読み・git の確かめ・打ち直しの確かめ・D1 の書き出しと戻し・控えの目録・表示の言語)は引き継ぐ(DES-015)

DES-002compose ファイルの読み方 REQ-001・REQ-002・REQ-003

  • YAML を読むクレートを 1 つ足す。候補は serde-saphyr と serde_yaml_ng。作る時点で手入れが続いている方を選ぶ。手入れの止まった serde_yaml は使わない
  • いったん値の木に読み、自前で確かめてから型のある形へ移す(x- を許しつつ知らないキーで止まる、を書くため)。止まるときは場所(services.web.image)と理由を示す
  • サービスの順: bindings・consumes の相手と depends_on を依存として、トポロジカルソートする。決まらないところはファイルに書いた順。輪は止まる
  • 引数でサービスを指定したとき: up は依存をたどった閉じた集まり、down は指定したものだけ

DES-003変数の展開 REQ-005・REQ-004

  • docker compose の展開の決まりを自前で書く: ${VAR}・${VAR:-既定}・${VAR-既定}・${VAR:?説明}・${VAR?説明}・$$。$VAR(波かっこ無し)も docker と同じに受ける
  • 展開するのは YAML の文字列の値だけ(キーは展開しない)。展開は型の確かめの前に行う(展開した結果で確かめる)
  • 値の探し方: 環境変数 → .env.<環境>。.env の読み方は 0.1 系のものを引き継ぐ
  • 無い変数はすべて集めてから、まとめて示して止まる
  • シークレットの値は、展開した値を出す場面(--dry-run など)で伏せる

DES-004資源の記録と見つけ直し REQ-006

  • リモートの資源の実際の名前は、サービスの name、無ければ <プロジェクト>-<環境>-<サービス>。Cloudflare の名前の決まり(長さ・使える字)に合わない名前になるときは止まる
  • 記録(.wrangler/compose/<環境>/resources.json)は、名前と ID の対応の写しにすぎない。up のたびに、名前で Cloudflare を引いて確かめ直す(d1 list・kv namespace list・r2 bucket list・queues list)。だから記録を失っても、別の PC からでも、同じ資源につながる
  • 名前の資源が無ければ作る(d1 create・r2 bucket create・kv namespace create・queues create)。あれば作らずに使う
  • 環境があるか(初めての up か)は、その環境のどれかの Worker か資源が Cloudflare にあるかで見る(REQ-016 の確かめに使う)

DES-005Wrangler の設定を作る REQ-007・REQ-002・REQ-003

  • Worker のサービスごと・環境ごとに、Wrangler の設定(JSON)を .wrangler/compose/<環境>/<サービス>/wrangler.json に書く。環境の階層(env)は使わない(1 つの環境に 1 つの設定)
  • 中身: name(DES-004)・main と組み立てのキー(DES-006。Worker のフォルダの設定ファイルから写し、パスは絶対パスに直す)・compatibility_date・compatibility_flags・vars・routes・triggers.crons・assets・バインディング(相手の型と、DES-004 の名前と ID から)・queues.consumers・durable_objects と migrations(DES-008)
  • 手元では、資源の ID の代わりにサービスの名前を使う(手元の置き場はその名前で分かれる)。R2 のバインディングに手元の S3 の鍵(local_dev.experimental_s3_credentials)を入れる。鍵は決まった値
  • D1 の移行のフォルダ(migrations_dir)は、compose ファイルの migrations を絶対パスにして書く
  • Durable Object を別の Worker から使うバインディングには script_name(相手の Worker の実際の名前)を入れる

DES-006組み立てのキーの一覧 REQ-007

  • Worker のフォルダの設定ファイルで受けるキー: $schema・main・build(command・cwd・watch_dir)・rules・find_additional_modules・base_dir・preserve_file_names・no_bundle・minify・tsconfig・alias・upload_source_maps
  • この一覧に無いキーがあれば止まる。止まるときに、そのキーが compose ファイルのどこに当たるか(vars → services.<名前>.vars など)を示す表を持つ
  • define は組み立てのときの置き換えだが、値が振る舞いを変えるので受けない(要るなら vars を使う)
  • 設定ファイルは Wrangler の読み方(experimental_readRawConfig)で読む(JSONC・TOML を自前で読まない)

DES-017build REQ-022

  • Worker のサービスごとに、環境によらない組み立て用の設定(バインディングを持たない)で wrangler deploy --dry-run --outdir .wrangler/compose/build/<サービス>/ を動かし、組み立てたもの(バンドル)を置く。docker のイメージに当たる
  • 組み立てたものには、コードと Wrangler の設定ファイルの組み立てのキーと compose ファイルの要約(SHA-256)を添える。up は、いまのコードの要約と比べ、違えば組み立てたものが古いと示す(--build で組み直す。docker と同じく勝手には組み直さない)
  • up は環境ごとの設定(名前・バインディング・変数・ルート・Cron)を DES-005 で作り、組み立てたものを組み直さずに上げる(手元の wrangler dev も、リモートの deploy も同じバンドルを使う)

DES-007リモートの up REQ-008・REQ-004・REQ-016

  • 段: 確かめ(変数・.env と git・初めての環境なら確かめ) → 資源を合わせる(DES-004) → サービスの順に: D1 の移行(d1 migrations apply --remote) → 組み立てたもの(DES-017)を使う(無ければ組み立てる。--build なら組み立て直す)→ 前回と同じなら飛ばす → 組み立てたものをそのままデプロイ(組み直さない。deploy --no-bundle --secrets-file) → compose から消えたシークレットを消す(secret delete)
  • 「前回と同じ」は、組んだもの・作った設定・シークレットの値の要約(SHA-256)を記録と比べて決める。Cloudflare 側の版も見て、記録と違えば上げ直す
  • 移行が失敗したら、その D1 をつなぐ Worker と、それより後のサービスは行わない
  • compose から消えた Worker は、記録と、名前の決め方(<プロジェクト>-<環境>- で始まる Worker)から見つける。--remove-orphans のときだけ delete する

DES-008Durable Objects の移行 REQ-002・REQ-009

  • Cloudflare は Durable Object のクラスの足し・消しを、Worker の設定の migrations(タグつき)で受ける。compose ファイルにはクラスの一覧(durable_objects)しか無いので、移行のタグは wrangler-compose が作る
  • 前回デプロイしたクラスの一覧を、デプロイした Worker の設定から読み、足されたクラスは new_sqlite_classes、消えたクラスは deleted_classes の移行として、通し番号のタグ(wc-1・wc-2 …)で足す
  • クラスを消すとその中身も消えるので、消えるクラスがあれば up は消すものとして示し、環境名の打ち直しで確かめる(REQ-016)
  • クラスの名前の変更(renamed_classes)は、消して足すのと区別できないので、今は受けない(確かめていないこと)

DES-009手元の up REQ-014・REQ-004

  • すべての Worker を 1 つの wrangler dev で動かす: wrangler dev -c <入口> -c <サービス 1> -c <サービス 2> … --persist-to .wrangler/compose/local/state。1 つの実行環境なので、同じ資源への同時の書き込みで壊れない(確かめた事実)
  • 入口は道具のサービス(入口のサービス。REQ-021) で、外から届く唯一の Worker。ports を持つ各サービスへのサービスバインディングを持ち、要求の URL のポートで振り分ける(確かめた事実)。入口のポートは空いている番号を使い、利用者には見せない
  • wrangler-compose は、各サービスの ports のアドレスとポートで待ち受け、入口のポートへ TCP をそのまま中継する(HTTP を読まないので WebSocket もそのまま通る)
  • 手元の S3 の口(/cdn-cgi/local/r2/s3/)はどのポートからも届く(入口より前で miniflare が受ける)。up は口の URL・バケット名・決まった鍵を示す
  • 手元のシークレットと vars は、作った設定の横に .dev.vars を書いて渡す(Unix は 0600。.wrangler/ の下で git の外)
  • 動かす前に、移行を d1 migrations apply --local --persist-to … で当てる
  • 動いていることの記録と錠は、0.1 系の設計(錠のファイルと PID・URL の記録)を引き継ぐ。ログは画面に出すのと同時に .wrangler/compose/local/logs/ に書き、logs が読む
  • compose ファイルか .env.local が変われば、作った設定を作り直して wrangler dev を動かし直す。コードの変化は wrangler dev に任せる

DES-010データのサービス REQ-021・REQ-012・REQ-009・REQ-010・REQ-015・REQ-020

  • 道具のサービスの 1 つ。名前は <プロジェクト>-<環境>-wc-data(手元では wc-data)。その環境のすべての R2・KV への、ふつうのバインディングを持つ Worker
  • up が利用者のサービスと一緒に建てる: リモートでは Cloudflare にデプロイし、手元では同じ wrangler dev の中で動かす(1 つの実行環境。DES-009)。down が一緒に下ろす。R2・KV のサービスが足し引きされれば、up がバインディングを合わせて上げ直す
  • HTTP で list・get・put・delete を受ける。wrangler-compose は控えのファイルとの受け渡しだけを行う
  • 守り方: 256 ビットの乱数の合言葉を Worker のシークレットとして入れ、Authorization の見出しで一致する要求だけに応える(一定時間で比べる)。合言葉は .wrangler/compose/<環境>/ に覚えておく。覚えていない PC(別の PC・記録を消した)では、使う前に合言葉を作り直してシークレットを入れ直す。リモートではルートを持たず workers.dev の URL だけで受け、手元では 127.0.0.1 だけで受ける
  • D1 は Wrangler の管理の操作(d1 export・d1 execute --file)で扱う(手元は --local --persist-to、リモートは --remote)。要るなら、D1 もデータのサービスに足す
  • 却下: 操作のたびに使い捨てでデプロイする(要るサービスは初めから持つ。REQ-021)
  • 却下: 手元で動かし remote: true でリモートの資源につなぐ(手元とリモートが混ざる。REQ-020)
  • 却下: S3 互換の API(人が API キーを発行する段取りが要る。REQ-015)

DES-011down REQ-009

  • リモート: 依存の逆の順に delete。--purge なら、続けて資源を消す: D1 は d1 delete、R2 はデータのサービス で空にしてから r2 bucket delete、KV は kv namespace delete、Queue は queues delete。下ろさないサービスがつながる資源があれば、何も消さずに止まる
  • 消す前に数える(D1 の表の数・R2 のオブジェクトの数・KV のキーの数)のもデータのサービス と Wrangler で行う。打ち直しの確かめは 0.1 系のものを引き継ぐ
  • 手元: down は動いている up を止める(0.1 系の止め方を引き継ぐ)。--purge は止めたあと .wrangler/compose/local/state を消す

DES-012ps・logs REQ-010・REQ-011

  • ps(リモート): Worker は deployments list(無ければ無い)、資源は DES-004 の一覧、未適用の移行は移行の履歴の表を SELECT で読む(d1 migrations list は履歴の表を作ってしまうので使わない。0.1 系の DES-016)
  • ps(手元): 動いている記録と錠、手元の URL
  • logs(リモート): Worker ごとに wrangler tail --format json を並べて動かし、1 行ずつ読んで、サービス名 | を頭に付けて出す(名前の桁をそろえる)
  • logs(手元): .wrangler/compose/local/logs/ を読む(-f なら追う)。wrangler dev のログに Worker の名前が付いていなければ、入口と各 Worker のログを見分ける手立てが要る(確かめていないこと)

DES-013backup・restore REQ-012

  • 控えの形は 0.1 系の目録(書きかけの見分け・SHA-256 の照合)を引き継ぎ、format: 2 にする: project・environment・サービスごとに d1(SQL)・r2(オブジェクトと見出し)・kv(キー・値・メタデータ・期限)
  • 戻すときは、目録のサービスの名前と型で、いまの compose ファイルのサービスに照らす。型が違う・無いサービスは止まる
  • KV の期限は、戻す時刻で切れているものは戻さない(数を示す)

DES-014dry-run と確かめ REQ-013・REQ-016

  • どの操作も、確かめ → 何をするかの一覧を作る → 変える、の 3 段に分ける。--dry-run は 2 段目で一覧を示して終わる(止まる条件を本番と別に書かない。0.1 系の DES-016 と同じ考え方)
  • 一覧の項目: 資源の作成・Worker のデプロイ(飛ばすものも)・移行・シークレットの足し・消し(名前だけ)・Durable Object のクラスの足し・消し・消す資源と中身の数
  • 消すものを含む一覧は、変える前に環境名の打ち直しで確かめる(端末でなければ止まる)

DES-015前の版から引き継ぐもの

  • 引き継ぐ: dotenv.rs・git.rs・confirm.rs・interrupt.rs・i18n.rs・d1.rs の書き出しと戻しと履歴の表の読み・backup.rs の目録と書きかけの扱い
  • 作り直す: project.rs(Wrangler の設定を読む → compose ファイルを読んで設定を作る)・up.rs・down.rs・restore.rs・main.rs(コマンド)
  • 捨てる: r2.rs(S3 互換の API。DES-010 でデータのサービス に置き換える)
  • 0.1 系の使い方(Wrangler の設定を正とする)との互換は持たない。compose ファイルが無いプロジェクトでは、書き始め方を示して止まる(REQ-001)。版は 0.2.0 にする

DES-016試験

  • 単体: compose ファイルの確かめ(知らないキー・型・輪)、変数の展開の決まり、サービスの順、作る Wrangler の設定(compose ファイルから期待する JSON)、組み立てのキーの選り分け、Durable Objects の移行のタグ、控えの目録
  • 手元の結合(CI。3 つの OS): 受け入れ条件の試験用のプロジェクトを tests/fixtures/ に置き、--env local up を裏で動かして、AC-003・AC-004・AC-014(同時の書き込みと S3 の口を含む)・AC-012 の手元の分を確かめる
  • リモート: 受け入れ条件のとおり、試験用のアカウントで、利用者の許可を得てから行う。まず --dry-run で全操作を通す

確かめていないこと(作る前・受け入れの前に確かめる)

  • リモートのデータのサービス: アカウントに workers.dev の名前(サブドメイン)がまだ無いときに、人の段取りなしにデプロイして呼べるか(REQ-015)。大きなオブジェクト(Worker の要求の本体の上限を超えるもの)を、分けて受け渡せるか(試験用のアカウントが要る)
  • 手元の入口の Worker: WebSocket・大きな本体・Server-Sent Events が、中継と入口を通っても本物と同じに届くこと
  • 手元のログの見分け: wrangler dev -c … -c … のログから、どの Worker の行かを見分けられること
  • 作った設定でのコードの見張り: 設定ファイルを .wrangler/ の下に置いても、wrangler dev が Worker のフォルダのコードの変化を見て作り直すこと
  • Durable Objects: クラスの名前の変更の扱い。前回デプロイしたクラスの一覧を Cloudflare から読めること
  • 組み立てたものをそのまま使うこと: deploy --dry-run --outdir で作ったバンドルを、環境ごとの設定と --no-bundle で上げられること。wrangler dev が、組み直さずに同じバンドルで動き、コードの変化のときだけ組み直せること(手元の開発の見張りとの兼ね合い)
  • Windows: 中継・錠・止め方が同じに動くこと
