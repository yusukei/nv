wrangler-compose 要求仕様

Cloudflare Workers のアプリを、docker compose と同じく「1 つのファイルに書き、コマンド 1 つで建てる」ための道具。Worker も D1・R2・KV・Queue も、compose ファイルのサービスとして並べる。同じファイルが、手元(local)でも Cloudflare の環境(staging・production など)でも同じ形で建つ。

目的

  1. 複数のサービスをまとめて扱う: Worker と、それが使う資源(D1・R2・KV・Queue・シークレット)を、まとめて建てる・止める・見る・控える
  2. 手元で作ったものを、リモートで安全に再現する: 手元で動いたものと同じ構成を、Cloudflare の環境に、何が変わるかを見てから建てる

理念(docker compose から)

  • ファイルが唯一の正: アプリの構成は compose ファイルだけが持つ。ファイルと .env.<環境> の値があれば、どこでも同じものが建つ
  • 手で行う段取りが無い: 書いたあとは up 1 つで揃う。資源の作成・移行・シークレットの投入・手元の鍵などは、道具が行う(REQ-015)
  • 宣言した状態に合わせる: up は何度打っても同じ結果になり、変わったところだけを変える
  • 入れ物とデータを分ける: down は作り直せるもの(Worker)だけを下ろし、データは --purge を付けたときだけ消す
  • 論理名で書く: ファイルにはサービスの名前だけを書き、Cloudflare の実際の名前は道具が決める(REQ-006)
  • 名前で呼び合う: Worker は、つながる相手をサービスの名前で指す

compose ファイルの例

# wrangler-compose.yaml
name: shop

services:
  web:
    type: worker
    build: ./web                    # Worker のコードのフォルダ
    ports: ["8787:8787"]            # 手元の URL
    routes: ["${WEB_DOMAIN}"]       # 環境ごとの値は .env.<環境> から展開する
    depends_on: [api]
    bindings:
      API: api                      # 相手が worker なら、サービスバインディング
      FILES: files

  api:
    type: worker
    build: ./api
    ports: ["8788:8788"]
    compatibility_date: "2026-09-01"
    depends_on: [db, files, cache, jobs]
    bindings:
      DB: db                        # 相手の type でバインディングの種類が決まる
      FILES: files
      CACHE: cache
      JOBS: jobs                    # queue へのバインディングは、送り手
    consumes: [jobs]                # 受け手
    durable_objects: [Counter]      # この Worker のコードにあるクラス
    secrets: [stripe-key]

  db:
    type: d1
    migrations: ./api/migrations

  files:
    type: r2

  cache:
    type: kv

  jobs:
    type: queue

secrets:                            # docker compose の secrets と同じ形
  stripe-key:
    environment: STRIPE_KEY         # 値は .env.<環境> の STRIPE_KEY
# .env.staging(git の外)
WEB_DOMAIN=staging.shop.example.com
STRIPE_KEY=sk_test_...

コマンド体系

形はどの場合も wrangler-compose --env <環境> [--dry-run] <操作> [<操作の引数>…] [サービス…]。--env(短く -e、または環境変数 CLOUDFLARE_ENV)はどの操作にも要る。docker compose で組み合わせを切り替える -f に当たるのが --env で、-f は持たない。

操作localリモートの環境条項
up [サービス…]手元で資源を用意し、移行を当て、Worker を動かす(前面で動き、Ctrl+C で止まる)資源を作り、移行を当て、シークレットを入れ、Worker をデプロイするREQ-008
down [サービス…]動いているものを止めるWorker を消す。データは残すREQ-009
down --purge [サービス…]手元のデータも消すD1・R2・KV・Queue も中身ごと消すREQ-009
psサービスごとの状態(あるか・動いているか・URL・未適用の移行)を並べるREQ-010
logs [-f] [サービス…]Worker のログを、行の頭にサービス名を付けて出すREQ-011
backup [<書き出し先>]D1・R2・KV の中身を手元のフォルダへ控えるREQ-012
restore [--drop] <控え>控えを戻す。どの環境の控えでも、どの環境へでも戻せるREQ-012
--dry-run <操作>何も変えずに、何が変わるかを示すREQ-013

決定(利用者)

  • 目的は 2 つ: 複数のサービスをまとめて扱うこと、手元で作ったものをリモートで安全に再現すること
  • Wrangler でできることから組み立てず、compose として何ができるべきかから決める。実現の手段(Wrangler を使うか、自前で作るか)はそのあとに選ぶ
  • 手で行う段取り(設定を手で書き足す、値を手で入れる、資源を手で作る)が要る形にしない
  • docker compose の image の代わりに type を置き、Worker も D1・R2・KV・Queue もサービスとして並べる。型は worker・d1・r2・kv・queue
  • 主に使うのは Workers・D1・R2・KV・Queues・Durable Objects・Secrets Store。使うものだけを作り、作るものは本物と互換にする
  • 環境の違いは、compose ファイルの中の変数(${VAR})を .env.<環境> から展開して表す(docker compose と同じ)
  • 切り替えの口は --env 1 つ。-f は持たない。compose ファイルは 1 つ
  • Wrangler の設定ファイルは、環境に依存しない組み立て(ビルド)のための内容だけなら残してよい。振る舞いに関わる内容は書けない
  • ローカルで開発できる必要がある(手元の開発に Cloudflare への接続を要らせない)
  • Wrangler に無い機能は、wrangler-compose が自分のサービス(道具のサービス)として初めから持ち、up が利用者のサービスと一緒に各環境へ建てる。操作のたびに使い捨てで作ったり、利用者に補わせたりしない
  • 手元とリモートを混ぜない。1 つの環境のものは、すべてその環境の中で動かす(手元で動くコードから Cloudflare の資源に触れる、Cloudflare で動くコードから手元に触れる、をしない)
  • down は作り直せるものだけを消し、データは --purge のときだけ消す
  • Node・npm の扱いは nv が受け持つ。wrangler-compose は Node のことを何も知らない
  • GitHub の公開のリポジトリに置き、GitHub Actions で Release に OS ごとの実行ファイルを置く。更新とエージェント用のスキルは nv に寄せる
  • シークレットは Worker のシークレットとして入れる(Secrets Store は使わない)
  • 資源の実際の名前は、既定では道具が決め、サービスの name に書けばそれを使う(既存の資源をそのまま使える)
  • 手元の down --purge も、リモートと同じく環境名を打ち直して確かめる
  • Queue の受け手の細かい設定は今は持たず、Cloudflare の既定に任せる
  • リモートの環境の Worker の名前は、資源と同じく <プロジェクト>-<環境>-<サービス>

用語

語意味
compose ファイルwrangler-compose.yaml。アプリの構成を書く唯一のファイル
プロジェクトcompose ファイルのあるフォルダと、その中のすべて。名前は compose ファイルの name
サービスcompose ファイルの services の 1 つ。型(type)を持つ
環境建てる先。local(この PC)か、リモートの環境(staging・production・pr-123 など、名前は自由)
資源型が worker 以外のサービスが、ある環境で実際に作る D1・R2 バケット・KV 名前空間・Queue
作り直せるものWorker(コード・ルート・Cron・シークレットの結び付け)。compose ファイルとコードから up で同じものができる
データ資源の中身と、Durable Objects の中身。作り直せない
手元この PC。--env local の操作は Cloudflare に触れない

要求

REQ-001compose ファイル

  • 名前は wrangler-compose.yaml(.yml も読む。両方あれば止まる)。いまのフォルダから上へたどって最初に見つかったものを使う。見つからなければ止まり、書き始め方を示す
  • 書式は YAML で、docker compose の compose.yaml に寄せる: 一番上に name・services・secrets。サービスに type・build・ports・depends_on など(REQ-002)
  • name を省くと、compose ファイルのあるフォルダ名。英小文字・数字・- だけ
  • サービスの名前は、英小文字・数字・- だけ
  • x- で始まるキーは、どの階層でも読み飛ばす(docker と同じ)
  • 知らないキー、型に合わないキー、無いサービスを指すもの、depends_on の輪は、何もせずに止まり、どこ(services.web.environment など)の何がいけないかを示す
  • compose ファイルは環境によらず 1 つ。環境の違いは変数の展開(REQ-005)だけで表す

REQ-002サービスの型

型書けるキー建つもの
worker build(必須。コードのフォルダ)・name・ports・depends_on・bindings・consumes・durable_objects・secrets・vars・routes・crons・compatibility_date・compatibility_flags・assets Worker 1 つ
d1name・migrations(移行の SQL のフォルダ)D1 データベース 1 つ
r2nameR2 バケット 1 つ
kvnameKV 名前空間 1 つ
queuename(受け手の細かい設定は持たず、Cloudflare の既定に任せる)Queue 1 つ
  • name は Cloudflare での実際の名前(REQ-006)。省けば道具が決める
  • vars は Worker に渡す秘密でない値。routes はルート・カスタムドメイン、crons は Cron の式。どれも環境ごとに違うなら変数で書く
  • assets は静的なファイルのフォルダ(Workers の静的なファイル)
  • durable_objects は、その Worker のコードにある Durable Object のクラス名の一覧。Durable Objects は Worker の中のものなので、型にはしない
  • 型は使うものから足す(決定)。足すときは、手元で本物と互換に動く手立て(Wrangler の手元の模擬、または自前の代役)を同時に決める

REQ-003つながり(バインディング)

  • Worker の bindings は「バインディング名: 相手」。Worker のコードからは env.<バインディング名> で見える
  • 相手がサービスの名前なら、相手の型でバインディングの種類が決まる: worker → サービスバインディング、d1 → D1、r2 → R2、kv → KV、queue → Queue の送り手
  • 相手が <worker サービス>.<クラス名> なら、そのサービスの Durable Object へのバインディング(相手の durable_objects にそのクラスが無ければ止まる)
  • consumes は、その Worker が受け手になる Queue のサービスの一覧
  • つながる相手は、depends_on に書かなくても依存として扱う(相手を先に建てる)。depends_on はそれに足す順
  • つながりは、手元でもリモートでも同じにつながる(手元でも、別のサービスの Worker・Durable Object・Queue へ届く)

REQ-004シークレット

  • 一番上の secrets に、docker compose と同じ形で宣言する: <名前>: { environment: <変数名> }。値はその変数(REQ-005 と同じ探し方)から読む
  • Worker の secrets に並べたシークレットだけが、その Worker から見える(env.<変数名>)
  • リモートの環境では、up が値をその Worker のシークレットとして入れる(足す・変える)。compose ファイルから消したシークレットは、up が Worker からも消す(宣言した状態に合わせる)。Secrets Store は使わない(決定)
  • 手元では、up が同じ値を手元に入れる(手で入れる段取りは無い)
  • 値が無ければ、何もせずに止まり、無い変数の名前を示す

REQ-005変数の展開(環境の違い)

  • compose ファイルの文字列の中の ${VAR} を展開する。書き方は docker compose と同じ: ${VAR}・${VAR:-既定の値}・${VAR:?無いときの説明}・$$($ そのもの)
  • 値は、環境変数、次にプロジェクトの .env.<環境>(--env で選んだもの)から読む。環境変数を優先する
  • 既定の値の無い変数が無ければ、何もせずに止まり、どの環境のどの変数が無いかをまとめて示す
  • 展開はどの操作でも同じに行う(--dry-run でも)。展開した結果は、シークレットの値を除いて --dry-run で見られる
  • .env.<環境> は git に入れない。プロジェクトが git の中にあって、そのファイルが .gitignore で外れていないか、すでに git に入っていれば、何もせずに止まる

REQ-006環境と資源の名前

  • 環境の名前は自由(staging・production・pr-123 など)。local だけは手元を指す決まった名前
  • リモートの環境の Worker と資源の Cloudflare での名前は、道具が <プロジェクト名>-<環境>-<サービス名> で決める(例: shop-staging-db)。同じ compose ファイルから、名前の違う環境をいくつでも並べて建てられ、互いに混ざらない
  • 資源の ID(D1 の ID・KV の ID など)は道具が覚えておき、利用者は書かない。覚えたものを失っても、名前から見つけ直せる
  • サービスに name を書けば、決め方より優先してその名前を使う(既存の資源をそのまま使う、本番の名前を短くするなど)。環境ごとに変えるなら変数で書く(name: ${DB_NAME})。同じ名前の資源がすでにあれば、作らずにそれを使う

REQ-007Wrangler の設定ファイル

  • Wrangler の設定(wrangler.jsonc など)は、wrangler-compose が compose ファイルと環境から作る。利用者は書かなくてよい
  • Worker のフォルダ(build)に Wrangler の設定ファイルを置いてもよいが、書けるのは、環境に依存しない組み立て(ビルド)のための内容だけ: エントリーのファイル(main)・ビルドのコマンド(build)・モジュールの決まり(rules・find_additional_modules・base_dir・preserve_file_names)・no_bundle・minify・tsconfig・alias に当たるもの
  • 振る舞いに関わる内容(名前・バインディング・変数・ルート・Cron・環境・互換日付・Durable Objects の移行・配置・上限・ログの送り先など)が書いてあれば、何もせずに止まり、そのキーと、compose ファイルのどこに書くかを示す
  • どのキーが組み立てのためのものかの一覧は、設計で Wrangler の版ごとに決める。一覧に無いキーは、振る舞いに関わるものとして扱う(止まる)
  • wrangler-compose が作った設定は、プロジェクトの git の外(.wrangler/ の下など)に置き、プロジェクトのファイルを書き換えない

REQ-008up(建てる・合わせる)

  • up [サービス…] は、指定したサービスと、そのつながり・depends_on をたどった先を、依存の順に、compose ファイルの状態に合わせる。何も指定しなければすべて
  • サービスごとに行うこと: 資源が無ければ作る → D1 は未適用の移行を当てる → Worker はシークレットを入れてデプロイする(手元では動かす)
  • 何度打っても同じ結果になる。変わっていないものは変えない(変わっていない Worker を上げ直さない、など)
  • 移行が失敗したら、その D1 を使う Worker はデプロイしない。どのサービスまで済んだか、どこで止まったか、なぜかを示す。それより後のサービスは行わない
  • リモートの環境で、compose ファイルから消えたサービスの Worker が残っていれば、それを示す(--remove-orphans を付けたときだけ消す。docker と同じ)。データを持つ資源は、ここでは消さない
  • 移行を当てるときに確認を求めない(up を打ったことを確認とみなす)

REQ-009down(下ろす)

  • down [サービス…] は、指定したサービス(無ければすべて)の Worker を、依存の逆の順に下ろす。資源とデータは残す。そのあと up で、残したデータにつなぎ直して元に戻る
  • Worker と一緒に消えるもの(ルート・Cron・Durable Objects とその中身)を、消す前に示す
  • down --purge [サービス…] は、加えて資源を中身ごと消す。下ろさないサービスがつながっている資源は消さずに止まる
  • リモートの環境での down・down --purge は、消す前に、消すもの(Worker の名前、資源の名前と中身の数)を示し、環境名を打ち直して確かめる。打ち直しを受けられない場(端末でない)では止まる
  • 手元での down は、動いている up を止めるだけで、確かめを求めない。手元での down --purge は、リモートと同じく local を打ち直して確かめる(決定)

REQ-010ps(状態を見る)

  • ps は、サービスごとに、その環境での状態を並べる: Worker はデプロイされているか(手元では動いているか)・URL・最後にデプロイした日時。資源はあるか・未適用の移行の数
  • compose ファイルと違うもの(compose にあるのに無い、compose に無いのに残っている)を示す
  • 何も変えない

REQ-011logs(ログを見る)

  • logs [サービス…] は、Worker のログを、docker compose と同じく、行の頭にサービス名を付けて出す。-f で流し続ける
  • リモートの環境では、Cloudflare のその Worker のログ(リアルタイムのもの)を流す
  • 手元では、up が動いている間のログを、ほかの端末から見られる

REQ-012backup・restore(データを控える・戻す)

  • backup は、その環境のすべての d1・r2・kv サービスの中身を、手元のフォルダへ書き出す(既定はプロジェクトの backups/<環境>/<日時>/)。D1 は表の作りと中身と移行の履歴、R2 はオブジェクトとメタデータ、KV はキーと値とメタデータと期限
  • restore <控え> は、控えをサービスの名前で照らして、その環境へ戻す。戻す先が空のときだけ戻す。--drop を付けると、いまの中身を消してから戻す(打ち直しで確かめる)
  • 控えはどの環境で取ったものでも、どの環境へでも戻せる(本番 → 手元で調べる、手元 → staging を埋める)。戻す前に、控えを取った環境を示す
  • 戻したあと、控えのあとに足された移行を当てる
  • 控えには環境のデータが丸ごと入るので git に入れない(書き出し先が git の中で外れていなければ止まる)。書きかけの控えは戻さない
  • Durable Objects・Queue の中身・シークレットは控えない(範囲外)

REQ-013dry-run(何が変わるかを見る)

  • --dry-run はどの操作にも付く。何も変えずに、その操作で何が変わるかを示す: 作る・変える・消す資源と Worker、当てる移行、入れる・消すシークレットの名前(値は出さない)、展開した変数
  • 本番の操作が止まる条件は、dry-run でも同じに確かめ、同じに止まる
  • dry-run は、確かめのために Cloudflare へ読み取りだけの問い合わせを行う。打ち直しの確かめは求めない

REQ-014手元(local)

  • --env local up は、Cloudflare に触れず(ログインも要らず)、すべてのサービスを手元で動かす。前面で動き、Ctrl+C ですべて止まり、手元のプロセスを残さない
  • すべての Worker を 1 つの手元の実行環境で動かす(同じ資源を共有しても、同時の書き込みで壊れない)
  • ports を書いた Worker は、それぞれその手元の URL で応える
  • コードが変われば作り直して動かし直す
  • 手元の D1・R2・KV・Queue・Durable Objects・シークレットは、本物と同じ使い方で動く(Wrangler の手元の模擬、足りなければ本物と互換の代役)
  • R2 は、バインディングに加えて S3 互換の API(署名付き URL を含む)でも手元で読み書きできる。鍵は道具が決めて示す(利用者が書き足さない)
  • 手元のデータは、プロジェクトの .wrangler/ の下に置く。down では消えず、down --purge で消える
  • 同じプロジェクトで --env local up が動いていれば、2 つ目は止まり、動いているものを示す。ほかの端末からの --env local down で止められる

REQ-015手で行う段取りを持たない

  • 利用者が書くのは、compose ファイル・コード・.env.<環境> の値だけ。ほかに要るものは道具が用意する
  • 道具が用意するもの: 資源の作成と ID の記録、移行の適用、シークレットの投入(リモート・手元とも)、手元の S3 の鍵、Wrangler の設定
  • Cloudflare へのログイン(wrangler login に当たるもの)だけは、人が 1 度行う。ほかに人が Cloudflare のダッシュボードで行う段取り(API キーの発行など)を要らせない
  • 手で行う段取りが要る作りになりそうなら、要求として扱い直す(作りの都合で利用者に段取りを足さない)

REQ-020手元とリモートを混ぜない

  • 1 つの環境のものは、すべてその環境の中で動かす: --env local では、Worker も資源も手元にだけあり、Cloudflare に触れない。リモートの環境では、Worker も資源も Cloudflare にだけあり、そのデータを読み書きするコードも Cloudflare で動く
  • 手元で動くコードから Cloudflare の資源につなぐ作り(Wrangler の remote: true・wrangler dev --remote など)は、利用者の Worker にも、wrangler-compose が中で使うものにも使わない。compose ファイルにも書けない
  • 環境の間でデータを移す(backup・restore)ときは、手元のファイル(控え)を間に置く: 移し元の環境の中で書き出し、控えにし、移し先の環境の中で読み込む
  • 環境の外から行ってよいのは、Cloudflare の管理の操作(資源の作成・削除、デプロイ、D1 の書き出し・取り込みなど Wrangler のコマンドが行うもの)と、控えのファイルの受け渡しだけ

REQ-021道具のサービス

  • Wrangler に無い機能は、wrangler-compose が持つ Worker(道具のサービス)で受け持つ。道具のサービスは、compose ファイルに書かなくても、up が各環境に利用者のサービスと一緒に建て、down が一緒に下ろす。ps には道具のサービスとして分けて出す
  • 道具のサービスは、その環境の中で動き(REQ-020)、その環境の資源に、ふつうのバインディングでつながる
  • いま持つもの
    • データのサービス(すべての環境): R2・KV の中身の一覧・読み・書き・消去。backup・restore・down --purge・ps が使う
    • 入口のサービス(手元だけ): ports を書いた Worker に、それぞれの手元の URL を持たせる(REQ-014)
  • 道具のサービスは wrangler-compose が呼ぶためだけのもので、外からの要求には応えない(呼ぶための合言葉は道具が作って持つ)
  • 機能が足りなければ、道具のサービスを足して受け持つ(作りの都合で利用者に段取りを足さない。REQ-015)

REQ-016安全

  • 消す操作(down・down --purge・restore --drop)は、消すものを示し、環境名を打ち直して確かめる
  • シークレットの値を、どの操作でも、画面・ログ・控えの目録に出さない
  • .env.<環境> と控えが git に入る形なら止まる(REQ-005・REQ-012)
  • 環境の名前の打ち間違いで新しい環境を建ててしまわないよう、まだ無い環境への初めての up では、新しく作ることを示して確かめる(--dry-run では確かめない)

REQ-017手元と本番の違いの知らせ

  • 手元で動かしたときに本番と振る舞いが違う点を、手元で使えないものに、使う型(Workers・D1・R2・KV・Queues・Durable Objects・シークレット)に絞って列挙する。根拠(実装・資料・実測)を項目ごとに書く
  • --env local up は、compose ファイルにそれに当たるもの(ルート・Cron など)があれば、動かす前に、手元ではどうなるか・どう試すかを示す

REQ-018Wrangler と nv

  • Wrangler は中の実行役として使ってよい(compose ファイルが正で、Wrangler の書式を利用者に見せない)。使う Wrangler は、プロジェクトの package.json に入れた版を、nv を通して動かす(nv run wrangler …)
  • Worker のフォルダに自分の package.json があれば、その依存は nv で揃えてから組む
  • nv が無い、Wrangler が無い・古いときは、何もせずに止まり、入れ方を示す

REQ-019配り方・表示の言語

  • OS ごとの単体の実行ファイルで、nv と同じリポジトリ・同じ版のタグ・同じ Release で配る。nv と同じフォルダに置いて使う。更新とスキルは nv が受け持つ
  • wrangler-compose が自分で出すメッセージと --help は、nv と同じ決め方で日本語か英語で出す(NV_LANG も効く)。打ち直しの確かめで打つのは、言語によらず環境名そのもの

範囲外

  • 使わない型(Vectorize・Workers AI・Hyperdrive・Workflows など)。使うときに型を足す(REQ-002)
  • Durable Objects・Queue の中身の控え(Cloudflare に中身を書き出す方法が無い・流れて消える)。シークレットの控え
  • docker compose にあって要らないもの: image(type が代わり)・-f と重ね合わせ(--env が代わり)・profiles・extends・include・networks・volumes・scale・exec・run
  • DNS・WAF・Access などゾーンの設定(Worker と資源の外のもの)
  • Node・npm の取得と版の管理(nv が受け持つ)
