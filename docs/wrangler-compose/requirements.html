wrangler-compose 要求仕様

Cloudflare Workers のプロジェクトを、docker compose のように「環境を指定して 1 コマンド」で建てる・組む・下ろす・控える・戻すための道具。どのプロジェクトでも使い回す。

コマンド体系

形は wrangler-compose --env <環境名> <操作>。--env は短く -e、または環境変数 CLOUDFLARE_ENV で指定する(REQ-001)。

操作すること条項
buildWorker と静的なファイルを組むだけで、Cloudflare には何も上げないREQ-003
upD1 の移行を当て、Worker をデプロイする(初回も更新も同じ)。.env.<環境名> のシークレットを入れるREQ-004
downWorker だけを消す。D1・R2 は残すREQ-005
down --purgeWorker に加えて D1・R2 を中身ごと消す(API キーが要る)REQ-006
backup [<書き出し先>]D1 と R2 の中身を手元のフォルダへ書き出す(既定はプロジェクトの backups/。API キーが要る)REQ-007
restore <控えのフォルダ>控えを空の D1・R2 へ戻す(API キーが要る)REQ-008
restore --drop <控えのフォルダ>いまの D1・R2 の中身を消して、控えに入れ替える(API キーが要る)REQ-008

Cloudflare に触れる操作(up・down・backup・restore)は、環境の指定が無ければ止まる。Wrangler の操作そのものは nv run wrangler … で行える。

wrangler-compose の更新とエージェント用のスキルは nv が受け持つ(nv self update・nv install skill。REQ-010)。wrangler-compose 自身はこの 2 つを持たない。

決定(利用者)

  • コマンドの形は wrangler-compose --env <環境名> <操作>(例: wrangler-compose --env staging up)
  • down は作り直せるもの(Worker)だけを消し、データ(D1・R2)は残す。down --purge でデータも含めて消す(docker のコンテナとボリュームの分け方と同じ)
  • データを消す・読むために R2 の中身を一覧するときは、S3 互換の API とその API キーを使う(Wrangler は R2 の API キーを発行できず、オブジェクトの一覧も取れないため)
  • --purge で正しい API キーが渡されていないときは、警告して、データを消さない
  • R2・D1 の書き出しと取り込みで、バックアップとリストアを持つ
  • Durable Objects のデータは Worker に属するものとして扱い、down で Worker と一緒に消えてよい
  • backup の書き出し先は、既定でプロジェクトの backups/。引数で別の場所を渡せる
  • 入れ物(D1・バケット)は up が作り、restore は中身だけを扱う。いまの中身を捨てて入れ替えるときは restore --drop
  • Node・npm の扱いは nv(同じリポジトリの別の道具)が受け持つ。wrangler-compose は Node のことを何も知らない
  • シークレットと wrangler-compose が使う値は、プロジェクトの .env.<環境名> に書く
  • GitHub の公開のリポジトリに置き、GitHub Actions で Release に OS ごとの実行ファイルを置く
  • 個人の道具として nv と 1 つのリポジトリにまとめる。更新とエージェント用のスキルは nv に寄せる(wrangler-compose に self update・install skill を持たせない)

用語

語意味
プロジェクトWrangler の設定ファイル(wrangler.jsonc / wrangler.json / wrangler.toml)を持つフォルダ。wrangler-compose はそのフォルダで動かす
環境Wrangler の設定の環境(env.<環境名>)
作り直せるものWorker(コード・静的なファイル・ルート)。git にあるものから up で同じものができる
データ環境の設定がつなぐ D1 データベースと R2 バケットの中身。git に無く、作り直せない
API キーR2 の S3 互換の API のアクセスキー ID とシークレット(ダッシュボードで人が発行する)

要求

REQ-001環境の指定

  • 環境は --env <環境名>(短く -e)か、環境変数 CLOUDFLARE_ENV で指定する。両方あれば --env を優先する
  • 環境名は Wrangler の設定の環境名そのもの。別名は持たない
  • Cloudflare に触れる操作(up・down・backup・restore)は、環境の指定が無ければ何もせずに止まる(設定の一番上の階層を誤ってデプロイしない)
  • 設定に無い環境名なら、何もせずに止まり、設定にある環境名を並べて示す

REQ-002設定の持ち主と Wrangler の呼び方

  • 環境の値(名前・変数・バインディング・ルート)は Wrangler の設定ファイルだけが持つ。wrangler-compose は自分の環境定義を持たない
  • Wrangler は、プロジェクトの依存(package.json・package-lock.json)に入れた版を、nv を通して動かす(nv run wrangler …)。wrangler-compose は Wrangler も Node も抱えず、版も持たない
  • nv は、wrangler-compose と同じフォルダにあるものを使う(nv の self update が 2 つを同じフォルダで揃えるのと合わせる。nv の REQ-010)。nv はプロジェクトのフォルダ(Wrangler の設定のあるフォルダ)で動かす
  • 設定の読み方が Wrangler と食い違わない(環境・バインディング・移行のフォルダを、Wrangler が読むのと同じに読む)
  • wrangler-compose は、プロジェクトのファイル(Wrangler の設定ファイルを含む)を書き換えない。Wrangler が自動で作った資源の ID を設定ファイルへ書き戻す動き(端末から対話で動かしたときに起きる)も起こさせない
  • nv が無い、またはプロジェクトの依存に Wrangler が無いときは、何もせずに止まり、入れ方を示す。Wrangler が wrangler-compose の要る版より古いときも、止まって要る版を示す(要る版は、頼る Wrangler の機能から設計で決める)

REQ-003build(組めるかを確かめる)

build は、その環境の設定で Worker と静的なファイルを組み(設定のビルドのコマンドを含む)、Cloudflare には何も上げない。組めなければ理由を出して止まる。

REQ-004up(建てる・更新する)

  • up は初回も更新も同じコマンドで、環境の状態によって次の順で行う
    • D1 がすべてある環境: (1) 移行のフォルダを持つ D1 ごとに、未適用の移行を当てる → (2) Worker をデプロイする(組むのを含む)。移行が失敗したらデプロイしない
    • まだ無い D1 がある環境(初回など): (1) Worker をデプロイし、無い D1・R2 を Wrangler に作らせる → (2) 移行を当てる。移行が失敗したら、デプロイは済んでいて移行が当たっていないことを示して止まる(新しい環境は使う人がまだいないので、この順でよい)
  • Wrangler が作るのは、設定に名前だけを書いた D1(database_id の無いもの)と R2 バケット。同じ名前のものがあればそれにつなぐ(Wrangler 4.128 の実装で確認)。database_id を書いた D1 は作られず、その ID の D1 が無ければ、up はその D1 の名前と ID を示して止まる
  • プロジェクトに .env.<環境名>(git の外。例: .env.staging・.env.production)があれば、デプロイと一緒に、そこに書いた値を Worker のシークレットとして入れる(足す・上書きする)。無ければ、すでに入っているシークレットを使う(利用者の決定。Wrangler が --env で .env.<環境名> を選ぶ決まりと揃える)
  • .env.<環境名> から消した名前のシークレットは、Worker から消えない(Wrangler のデプロイがファイルに無いシークレットを残すため)。up のあと、Worker にあって .env.<環境名> に無いシークレットの名前を示す
  • .env.<環境名> のうち WRANGLER_COMPOSE_ で始まる名前は、wrangler-compose だけが使う値(API キーなど)で、Worker のシークレットに入れない
  • 移行を当てるときに確認を求めない(up を打ったことを確認とみなす)
  • どの段で止まったかと、その理由を出す。途中で止まったら、それより後の段は行わない

REQ-005down(作り直せるものを消す)

  • down は、その環境の Worker を消す。D1・R2 は消さない
  • Worker と一緒に消えるもの(シークレット・ルート・カスタムドメイン・Cron・Durable Objects とそのデータ)を、消す前に示す。Durable Objects のデータは Worker に属するので、down で消えてよい(利用者の決定)
  • 消す前に、環境名を打ち直して確かめる。打ち直した名前が違えば何も消さない
  • 打ち直しを受けられない場(入力が端末でない。エージェントやパイプから動かしたとき)では、何も消さずに止まる(確かめを流し込みで抜けられない)
  • down のあと up で、残した D1・R2 につなぎ直して元に戻る(シークレットは REQ-004 の .env.<環境名> があれば入る)

REQ-006down --purge(データも消す)

  • down --purge は、Worker に加えて、その環境の設定がつなぐ D1 データベースと R2 バケット(中身ごと)を消す
  • R2 の中身は S3 互換の API で一覧して消し、空にしてからバケットを消す
  • 消す前に、API キーが正しいことを確かめる(そのバケットの一覧が取れること)。API キーが無い・正しくないときは、警告して、何も消さない(Worker も消さない)
  • 消す前に、消すもの(Worker 名・D1 の名前・バケットの名前と中のオブジェクトの数)を並べて示し、環境名を打ち直して確かめる(打ち直しを受けられない場では止まる。REQ-005 と同じ)
  • 設定に database_id を書いた D1 を消すときは、消したあとの up がその D1 を作り直さないこと(設定の database_id を外すまで up が止まること。REQ-004)を、消す前に示す
  • 途中で止まったら、何を消して何が残っているかを示す

REQ-007backup(控える)

  • backup は、その環境の設定がつなぐすべての D1 と R2 バケットの中身を、手元のフォルダへ書き出す
    • D1: スキーマと中身(SQL)。どの移行まで当たっていたか(移行の履歴)を含む(REQ-008 で、控えのあとの移行だけを当てるため)
    • R2: すべてのオブジェクト(キーと中身と、内容の種類などのメタデータ)
  • 書き出し先は <書き出し先>/<環境名>/<日時>/ で、何が入っているかの目録を置く
  • D1 の書き出しの間、その D1 は問い合わせに応えなくなる(Wrangler 4.128 の書き出しが出す注意)。backup は書き出す前にそのことを示す
  • backup だけを打てば、<書き出し先> はプロジェクトの backups/。backup <書き出し先> で別の場所を渡せる(利用者の決定)
  • 控えには環境のデータが丸ごと入るので、git に入れない。書き出し先がプロジェクトの git の中にあり、.gitignore で外れていなければ、何も書き出さずに止まる(.env.<環境名> と同じ決まり。REQ-009)
  • R2 の一覧には API キーが要る。API キーが無い・正しくないときは、警告して、何も書き出さない(R2 の無い控えを控えと呼ばない)
  • 書き出しの途中で止まった控えは、完成した控えと見分けられ、restore に使われない
  • 書き出せない D1 があれば(Wrangler の書き出しが受けない表があるなど)、その D1 と理由を示して止まり、完成した控えとして残さない

REQ-008restore(戻す)

  • 入れ物(D1・バケット)は up が作り、restore は中身だけを扱う(利用者の決定)。戻す先の D1・バケットが無ければ、何もせずに止まり、先に up を求める
  • restore <控えのフォルダ> は、控えの D1(表の作りと中身)と R2 の中身を、指定した環境の同じバインディングの D1 と R2 へ入れる。戻す先が空(D1 に表が無く、バケットにオブジェクトが無い)のときだけ戻す。空でなければ、何もせずに止まり、空でないものと、--drop で入れ替えられることを示す
  • restore --drop <控えのフォルダ> は、戻す先の D1 の表をすべて消し、バケットのオブジェクトをすべて消してから、控えを戻す(MongoDB の mongorestore --drop と同じ考え方。利用者の決定)
  • --drop は消す操作なので、down --purge と同じに扱う: 消すもの(D1 ごとの表の数、バケットごとのオブジェクトの数)を先に示し、環境名を打ち直して確かめる。打ち直しを受けられない場では止まる(REQ-005)
  • 戻したあと、控えのあとに足された移行を当てて、D1 をいまのコードに合わせる(up の移行の段と同じ)。控えに移行の履歴が入っていることが前提で、入っていない控えなら戻す前に止まる
  • 戻している間も Worker は動いたままで、欠けたデータが見える。始める前にそのことを示す
  • 書きかけの控え(REQ-007)は戻さない
  • R2 を読み書きするには API キーが要る。無い・正しくないときは、警告して、何もしない(--drop でも何も消さない)
  • 途中で止まったら、何を消し、何を入れて、何が残っているかを示す

REQ-009秘密の扱い

  • シークレットの値と API キーを、どの操作でも、画面・ログ・控えの目録に出さない
  • API キーは .env.<環境名> の WRANGLER_COMPOSE_R2_ACCESS_KEY_ID・WRANGLER_COMPOSE_R2_SECRET_ACCESS_KEY、または同じ名前の環境変数から受け取る(環境変数を優先する)
  • S3 互換の API に要るアカウント ID と管轄(EU など)は、Wrangler の設定とログインから得る(利用者に別に書かせない)
  • .env.<環境名> を読む操作(up・down --purge・backup・restore)は、プロジェクトが git の中にあって、そのファイルが .gitignore で外れていないか、すでに git に入っていれば、何もせずに止まる。プロジェクトが git の外なら確かめない

REQ-010配り方と更新

  • OS ごとの単体の実行ファイルで配る(Windows x64、macOS arm64・x64、Linux x64)。nv と同じリポジトリ・同じ版のタグ・同じ Release で配る(nv の REQ-009)
  • nv と同じフォルダに置いて使う(REQ-002)。最初の導入の手順は nv の REQ-009 に従う
  • 更新は nv self update が nv と一緒に行う(nv の REQ-010)。エージェント用のスキルは nv install skill が nv のものと一緒に入れる(nv の REQ-008)。wrangler-compose は更新とスキルの口を持たない

範囲外

  • Node・npm の取得と版の管理(nv が受け持つ)
  • 手元の開発(wrangler dev)、状態の一覧(ps)、ログの表示(logs)。必要になったら足す(Wrangler の操作そのものは nv run wrangler … で行える)
  • R2 の CORS・ライフサイクルの設定(Wrangler の設定ファイルに書けない、バケットごとの設定のため。nv run wrangler r2 bucket cors … などで行える)
  • D1・R2 以外の資源(KV・Queues など)の控えと消去。Durable Objects のデータの控え(消えるのは down で Worker と一緒に。REQ-005)
