wrangler-compose 要求仕様

Cloudflare Workers のプロジェクトを、docker compose のように「環境を指定して 1 コマンド」で建てる・組む・下ろす・控える・戻すための道具。手元の開発も、local という環境として同じ操作で扱う。複数の Worker は、compose.yaml に寄せた wrangler-compose.yaml にまとめる。どのプロジェクトでも使い回す。

コマンド体系

形は wrangler-compose --env <環境名> <操作>。--env は短く -e、または環境変数 CLOUDFLARE_ENV で指定する(REQ-001)。

操作すること条項
buildWorker と静的なファイルを組むだけで、Cloudflare には何も上げないREQ-003
upD1 の移行を当て、Worker をデプロイする(初回も更新も同じ)。.env.<環境名> のシークレットを入れるREQ-004
downWorker だけを消す。D1・R2 は残すREQ-005
down --purgeWorker に加えて D1・R2 を中身ごと消す(API キーが要る)REQ-006
backup [<書き出し先>]D1 と R2 の中身を手元のフォルダへ書き出す(既定はプロジェクトの backups/。API キーが要る)REQ-007
restore <控えのフォルダ>控えを空の D1・R2 へ戻す(API キーが要る)REQ-008
restore --drop <控えのフォルダ>いまの D1・R2 の中身を消して、控えに入れ替える(API キーが要る)REQ-008
--dry-run <操作>上のどの操作も、何も変えずに何をするかだけを示すREQ-011

環境名 local は手元の開発のための決まった名前で、同じ操作が Cloudflare ではなくこの PC の上で動く(REQ-013)。

操作(--env local)すること条項
up手元の D1 に未適用の移行を当て、手元で Worker を動かす(前面で動き、Ctrl+C で止まる)。R2 は S3 互換の口(署名付き URL を含む)でも読み書きできるREQ-014・REQ-015
downほかの端末で動いている --env local up を止める。手元のデータは残すREQ-016
down --purge手元のデータ(D1・R2 ほか、Wrangler が手元に置いた状態)を消すREQ-016
backup [<書き出し先>]手元の D1・R2 の中身を <書き出し先>/local/<日時>/ へ書き出す(API キーは要らない)REQ-017
restore [--drop] <控えのフォルダ>控え(staging などほかの環境で取ったものも)を手元の D1・R2 へ戻すREQ-017

複数の Worker を wrangler-compose.yaml にまとめたプロジェクトでも、形は変わらない。docker compose と同じく、操作のあとにサービス(Worker)の名前を並べて絞れるだけ(REQ-018〜REQ-020)。

形はどの場合も wrangler-compose --env <環境名> [--dry-run] <操作> [<操作の引数>…] [サービス…](例: wrangler-compose --env staging up・wrangler-compose --env local up web)。docker compose で組み合わせを切り替える -f に当たるのが --env で、wrangler-compose は compose ファイルを選ぶ引数(-f)を持たない。compose ファイルは、いまのフォルダから上へたどって見つける 1 つだけ(利用者の決定)。

形(wrangler-compose --env <環境名> のあと)すること条項
build [サービス…]指定したサービス(無ければすべて)を組むREQ-019
up [サービス…]指定したサービスと、その depends_on をたどった先を、依存の順に建てる(無ければすべて)。--env local なら手元でまとめて動かすREQ-019・REQ-020
down [サービス…]指定したサービスだけを、依存の逆の順に下ろす(無ければすべて)REQ-019
backup・restoreすべてのサービスの D1・R2 をまとめて 1 つの控えにする・戻す(同じ D1・バケットを共有するものは 1 度だけ)REQ-019

Cloudflare に触れる操作(up・down・backup・restore)は、環境の指定が無ければ止まる。Wrangler の操作そのものは nv run wrangler … で行える。

wrangler-compose の更新とエージェント用のスキルは nv が受け持つ(nv self update・nv install skill。REQ-010)。wrangler-compose 自身はこの 2 つを持たない。

決定(利用者)

  • コマンドの形は wrangler-compose --env <環境名> <操作>(例: wrangler-compose --env staging up)
  • down は作り直せるもの(Worker)だけを消し、データ(D1・R2)は残す。down --purge でデータも含めて消す(docker のコンテナとボリュームの分け方と同じ)
  • データを消す・読むために R2 の中身を一覧するときは、S3 互換の API とその API キーを使う(Wrangler は R2 の API キーを発行できず、オブジェクトの一覧も取れないため)
  • --purge で正しい API キーが渡されていないときは、警告して、データを消さない
  • R2・D1 の書き出しと取り込みで、バックアップとリストアを持つ
  • Durable Objects のデータは Worker に属するものとして扱い、down で Worker と一緒に消えてよい
  • backup の書き出し先は、既定でプロジェクトの backups/。引数で別の場所を渡せる
  • 入れ物(D1・バケット)は up が作り、restore は中身だけを扱う。いまの中身を捨てて入れ替えるときは restore --drop
  • --dry-run で、どの操作も何も変えずに何をするかを示せる(試すときは dry-run から始める)
  • Node・npm の扱いは nv(同じリポジトリの別の道具)が受け持つ。wrangler-compose は Node のことを何も知らない
  • シークレットと wrangler-compose が使う値は、プロジェクトの .env.<環境名> に書く
  • GitHub の公開のリポジトリに置き、GitHub Actions で Release に OS ごとの実行ファイルを置く
  • 個人の道具として nv と 1 つのリポジトリにまとめる。更新とエージェント用のスキルは nv に寄せる(wrangler-compose に self update・install skill を持たせない)
  • 手元の開発を主な使い道として育てる。手元は --env local という環境として、Cloudflare の環境と同じ操作(up・down・backup・restore)で扱う(dev のような別の操作を足さない)
  • 手元で使えない R2 の機能のうち、S3 互換の API(署名付き URL を含む)と、手元への backup・restore を補う。R2 の S3 互換の口は、Wrangler が持つ手元の口(local_dev.experimental_s3_credentials)を使い、自前のサーバは作らない
  • 手元の控えと Cloudflare の環境の控えは同じ形にし、互いに戻せる(本番の控えを手元に戻して開発できる)
  • 複数の Worker は、docker compose の compose.yaml と同じような compose ファイル(wrangler-compose.yaml)にまとめる。書式はなるべく compose.yaml に寄せる(name・services・build・ports・depends_on・x- の拡張・サービス名での絞り込み)。コマンドの形は wrangler-compose --env <環境名> <操作> のまま変えず、docker の -f に当たるものは --env が受け持つ(-f は持たない)
  • 手元で開発するときに使えない・本番と振る舞いが違う機能を列挙し(手元で使えないもの)、--env local up は設定にそれがあれば動かす前に知らせる

用語

語意味
プロジェクトWrangler の設定ファイル(wrangler.jsonc / wrangler.json / wrangler.toml)を持つフォルダ。wrangler-compose はそのフォルダで動かす
環境Wrangler の設定の環境(env.<環境名>)
作り直せるものWorker(コード・静的なファイル・ルート)。git にあるものから up で同じものができる
データ環境の設定がつなぐ D1 データベースと R2 バケットの中身。git に無く、作り直せない
API キーR2 の S3 互換の API のアクセスキー ID とシークレット(ダッシュボードで人が発行する)
手元この PC。--env local の操作は、Cloudflare ではなく手元の Wrangler(miniflare)の上で動く
手元のデータWrangler が手元の開発のためにプロジェクトの .wrangler/state/ に置く D1・R2 などの中身
手元の S3 の口手元の R2 バケットを S3 互換の API で読み書きする口(http://127.0.0.1:<ポート>/cdn-cgi/local/r2/s3/<バケット名>)。Worker のバインディング(env.<バインディング>)と同じ中身が見える
手元の鍵手元の S3 の口の署名に使うアクセスキー ID とシークレット。手元でしか通じない
compose ファイルwrangler-compose.yaml(または .yml)。どの Worker を 1 つのプロジェクトとして扱うかと、手元の待ち受けのポート・依存の順だけを書く
サービスcompose ファイルの services の 1 つ。1 つの Wrangler の設定ファイル(1 つの Worker)に当たる。compose ファイルが無いプロジェクトは、設定ファイル 1 つだけのサービスを持つものとして扱う
compose の根compose ファイルのあるフォルダ(無ければ Wrangler の設定ファイルのあるフォルダ)。Wrangler の版、backups/、手元のデータの置き場はここで決まる

要求

REQ-001環境の指定

  • 環境は --env <環境名>(短く -e)か、環境変数 CLOUDFLARE_ENV で指定する。両方あれば --env を優先する
  • 環境名は Wrangler の設定の環境名そのもの。別名は持たない。ただし local だけは手元の開発のための決まった名前として wrangler-compose が受け持つ(REQ-013)
  • Cloudflare に触れる操作(up・down・backup・restore)は、環境の指定が無ければ何もせずに止まる(設定の一番上の階層を誤ってデプロイしない)
  • 設定に無い環境名なら、何もせずに止まり、設定にある環境名を並べて示す

REQ-002設定の持ち主と Wrangler の呼び方

  • 環境の値(名前・変数・バインディング・ルート)は Wrangler の設定ファイルだけが持つ。wrangler-compose は自分の環境定義を持たない。compose ファイル(REQ-018)が持つのは、どの Worker をまとめるか・手元のポート・依存の順だけで、環境ごとの値は書けない
  • Wrangler は、プロジェクトの依存(package.json・package-lock.json)に入れた版を、nv を通して動かす(nv run wrangler …)。wrangler-compose は Wrangler も Node も抱えず、版も持たない
  • nv は、wrangler-compose と同じフォルダにあるものを使う(nv の self update が 2 つを同じフォルダで揃えるのと合わせる。nv の REQ-010)。nv はプロジェクトのフォルダ(Wrangler の設定のあるフォルダ)で動かす
  • 設定の読み方が Wrangler と食い違わない(環境・バインディング・移行のフォルダを、Wrangler が読むのと同じに読む)
  • wrangler-compose は、プロジェクトのファイル(Wrangler の設定ファイルを含む)を書き換えない。Wrangler が自動で作った資源の ID を設定ファイルへ書き戻す動き(端末から対話で動かしたときに起きる)も起こさせない
  • nv が無い、またはプロジェクトの依存に Wrangler が無いときは、何もせずに止まり、入れ方を示す。Wrangler が wrangler-compose の要る版より古いときも、止まって要る版を示す(要る版は、頼る Wrangler の機能から設計で決める)

REQ-003build(組めるかを確かめる)

build は、その環境の設定で Worker と静的なファイルを組み(設定のビルドのコマンドを含む)、Cloudflare には何も上げない。組めなければ理由を出して止まる。

REQ-004up(建てる・更新する)

  • up は初回も更新も同じコマンドで、環境の状態によって次の順で行う
    • D1 がすべてある環境: (1) 移行のフォルダを持つ D1 ごとに、未適用の移行を当てる → (2) Worker をデプロイする(組むのを含む)。移行が失敗したらデプロイしない
    • まだ無い D1 がある環境(初回など): (1) Worker をデプロイし、無い D1・R2 を Wrangler に作らせる → (2) 移行を当てる。移行が失敗したら、デプロイは済んでいて移行が当たっていないことを示して止まる(新しい環境は使う人がまだいないので、この順でよい)
  • Wrangler が作るのは、設定に名前だけを書いた D1(database_id の無いもの)と R2 バケット。同じ名前のものがあればそれにつなぐ(Wrangler 4.128 の実装で確認)。database_id を書いた D1 は作られず、その ID の D1 が無ければ、up はその D1 の名前と ID を示して止まる
  • プロジェクトに .env.<環境名>(git の外。例: .env.staging・.env.production)があれば、デプロイと一緒に、そこに書いた値を Worker のシークレットとして入れる(足す・上書きする)。無ければ、すでに入っているシークレットを使う(利用者の決定。Wrangler が --env で .env.<環境名> を選ぶ決まりと揃える)
  • .env.<環境名> から消した名前のシークレットは、Worker から消えない(Wrangler のデプロイがファイルに無いシークレットを残すため)。up のあと、Worker にあって .env.<環境名> に無いシークレットの名前を示す
  • .env.<環境名> のうち WRANGLER_COMPOSE_ で始まる名前は、wrangler-compose だけが使う値(API キーなど)で、Worker のシークレットに入れない
  • 移行を当てるときに確認を求めない(up を打ったことを確認とみなす)
  • どの段で止まったかと、その理由を出す。途中で止まったら、それより後の段は行わない

REQ-005down(作り直せるものを消す)

  • down は、その環境の Worker を消す。D1・R2 は消さない
  • Worker と一緒に消えるもの(シークレット・ルート・カスタムドメイン・Cron・Durable Objects とそのデータ)を、消す前に示す。Durable Objects のデータは Worker に属するので、down で消えてよい(利用者の決定)
  • 消す前に、環境名を打ち直して確かめる。打ち直した名前が違えば何も消さない
  • 打ち直しを受けられない場(入力が端末でない。エージェントやパイプから動かしたとき)では、何も消さずに止まる(確かめを流し込みで抜けられない)
  • down のあと up で、残した D1・R2 につなぎ直して元に戻る(シークレットは REQ-004 の .env.<環境名> があれば入る)

REQ-006down --purge(データも消す)

  • down --purge は、Worker に加えて、その環境の設定がつなぐ D1 データベースと R2 バケット(中身ごと)を消す
  • R2 の中身は S3 互換の API で一覧して消し、空にしてからバケットを消す
  • 消す前に、API キーが正しいことを確かめる(そのバケットの一覧が取れること)。API キーが無い・正しくないときは、警告して、何も消さない(Worker も消さない)
  • 消す前に、消すもの(Worker 名・D1 の名前・バケットの名前と中のオブジェクトの数)を並べて示し、環境名を打ち直して確かめる(打ち直しを受けられない場では止まる。REQ-005 と同じ)
  • 設定に database_id を書いた D1 を消すときは、消したあとの up がその D1 を作り直さないこと(設定の database_id を外すまで up が止まること。REQ-004)を、消す前に示す
  • 途中で止まったら、何を消して何が残っているかを示す

REQ-007backup(控える)

  • backup は、その環境の設定がつなぐすべての D1 と R2 バケットの中身を、手元のフォルダへ書き出す
    • D1: スキーマと中身(SQL)。どの移行まで当たっていたか(移行の履歴)を含む(REQ-008 で、控えのあとの移行だけを当てるため)
    • R2: すべてのオブジェクト(キーと中身と、内容の種類などのメタデータ)
  • 書き出し先は <書き出し先>/<環境名>/<日時>/ で、何が入っているかの目録を置く
  • D1 の書き出しの間、その D1 は問い合わせに応えなくなる(Wrangler 4.128 の書き出しが出す注意)。backup は書き出す前にそのことを示す
  • backup だけを打てば、<書き出し先> はプロジェクトの backups/。backup <書き出し先> で別の場所を渡せる(利用者の決定)
  • 控えには環境のデータが丸ごと入るので、git に入れない。書き出し先がプロジェクトの git の中にあり、.gitignore で外れていなければ、何も書き出さずに止まる(.env.<環境名> と同じ決まり。REQ-009)
  • R2 の一覧には API キーが要る。API キーが無い・正しくないときは、警告して、何も書き出さない(R2 の無い控えを控えと呼ばない)
  • 書き出しの途中で止まった控えは、完成した控えと見分けられ、restore に使われない
  • 書き出せない D1 があれば(Wrangler の書き出しが受けない表があるなど)、その D1 と理由を示して止まり、完成した控えとして残さない

REQ-008restore(戻す)

  • 入れ物(D1・バケット)は up が作り、restore は中身だけを扱う(利用者の決定)。戻す先の D1・バケットが無ければ、何もせずに止まり、先に up を求める
  • restore <控えのフォルダ> は、控えの D1(表の作りと中身)と R2 の中身を、指定した環境の同じバインディングの D1 と R2 へ入れる。戻す先が空(D1 に表が無く、バケットにオブジェクトが無い)のときだけ戻す。空でなければ、何もせずに止まり、空でないものと、--drop で入れ替えられることを示す
  • restore --drop <控えのフォルダ> は、戻す先の D1 の表をすべて消し、バケットのオブジェクトをすべて消してから、控えを戻す(MongoDB の mongorestore --drop と同じ考え方。利用者の決定)
  • --drop は消す操作なので、down --purge と同じに扱う: 消すもの(D1 ごとの表の数、バケットごとのオブジェクトの数)を先に示し、環境名を打ち直して確かめる。打ち直しを受けられない場では止まる(REQ-005)
  • 戻したあと、控えのあとに足された移行を当てて、D1 をいまのコードに合わせる(up の移行の段と同じ)。控えに移行の履歴が入っていることが前提で、入っていない控えなら戻す前に止まる
  • 戻している間も Worker は動いたままで、欠けたデータが見える。始める前にそのことを示す
  • 書きかけの控え(REQ-007)は戻さない
  • R2 を読み書きするには API キーが要る。無い・正しくないときは、警告して、何もしない(--drop でも何も消さない)
  • 途中で止まったら、何を消し、何を入れて、何が残っているかを示す

REQ-009秘密の扱い

  • シークレットの値と API キーを、どの操作でも、画面・ログ・控えの目録に出さない。手元の鍵(REQ-015)は手元でしか通じないので秘密として扱わず、--env local up が画面に示す
  • API キーは .env.<環境名> の WRANGLER_COMPOSE_R2_ACCESS_KEY_ID・WRANGLER_COMPOSE_R2_SECRET_ACCESS_KEY、または同じ名前の環境変数から受け取る(環境変数を優先する)
  • S3 互換の API に要るアカウント ID と管轄(EU など)は、Wrangler の設定とログインから得る(利用者に別に書かせない)
  • .env.<環境名> を読む操作(up・down --purge・backup・restore)は、プロジェクトが git の中にあって、そのファイルが .gitignore で外れていないか、すでに git に入っていれば、何もせずに止まる。プロジェクトが git の外なら確かめない

REQ-010配り方と更新

  • OS ごとの単体の実行ファイルで配る(Windows x64、macOS arm64・x64、Linux x64)。nv と同じリポジトリ・同じ版のタグ・同じ Release で配る(nv の REQ-009)
  • nv と同じフォルダに置いて使う(REQ-002)。最初の導入の手順は nv の REQ-009 に従う
  • 更新は nv self update が nv と一緒に行う(nv の REQ-010)。エージェント用のスキルは nv install skill が nv のものと一緒に入れる(nv の REQ-008)。wrangler-compose は更新とスキルの口を持たない

REQ-011dry-run(何も変えずに、何をするかを示す)

  • --dry-run を付けると、up・down・down --purge・backup・restore(--drop を含む)は、Cloudflare の資源・データ・シークレット・手元のファイル(控えを含む)を何も変えずに、その操作が何をするかを示す(利用者の決定)
  • 示すもの: up は当てる移行の名前と、Worker が組めるか、入れるシークレットの名前。down・--purge は消すもの(REQ-005・REQ-006 で消す前に示すものと同じ)。backup は書き出す D1・バケットとオブジェクトの数と書き出し先。restore は戻すもの、--drop なら消すもの
  • 本番の操作が止まる条件(環境の指定・.env が git に入る・API キーが無い・正しくない・控えが書きかけ・照らした値が合わない・戻す先が無い・空でない)は、dry-run でも同じに確かめ、同じに止まる
  • dry-run は、確かめるために Cloudflare へ読み取りだけの問い合わせ(一覧・ログインの確認など)を行う。打ち直しの確かめは求めない(何も消さないため)
  • 終わりに、dry-run であり何も変えていないことを示す

REQ-012表示の言語

  • wrangler-compose が自分で出すメッセージ(段・消すものの一覧・確かめの問い・結果・エラー)と --help の説明は、nv と同じ決め方で日本語か英語で出す(nv の REQ-011。NV_LANG も同じに効く)(利用者の決定)
  • 打ち直しの確かめで打つのは、言語によらず環境名そのもの
  • Wrangler の出力は、そのまま出す(訳さない)

REQ-013手元の環境 local

  • --env local(-e local・CLOUDFLARE_ENV=local も同じ)は手元の開発を指す。local の操作は Cloudflare に触れず、ログインも要らない
  • local は Wrangler の設定の一番上の階層を使う(環境を付けずに wrangler dev を動かしたときと同じ)
  • 設定に env.local があれば、何もせずに止まり、名前がぶつかることと、その環境の名前を変えるよう示す(1 つの名前に 2 つの意味を持たせない)
  • 手元のデータは Wrangler の既定の置き場(.wrangler/state/)に置く。wrangler-compose は別の置き場を作らない(nv run wrangler d1 execute <DB> --local などで同じデータが見える)
  • .env.local は、Wrangler が手元の開発で自ら読み、Worker の変数として渡す(wrangler-compose はシークレットとして入れる段を持たない)。wrangler-compose はそこから WRANGLER_COMPOSE_ で始まる値(手元の鍵。REQ-015)だけを読む。git の確かめは REQ-009 と同じに行う
  • --env local build は、設定の一番上の階層を組む(環境を付けない build と同じ)
  • dry-run(REQ-011)と表示の言語(REQ-012)は、local の操作にも同じに効く

REQ-014local の up(手元で動かす)

  • --env local up は次の順で行う: (1) 移行のフォルダを持つ手元の D1 ごとに、未適用の移行を当てる(確認を求めない) → (2) 手元で Worker を動かす。移行が失敗したら動かさず、どの移行で止まったかを示す
  • 前面で動き続け、Worker のログ(console の出力と要求ごとの記録)を流す。Ctrl+C で止まり、止まったあとに手元のプロセスを残さない
  • コードと設定が変われば、作り直して動かし直す(wrangler dev と同じ)。動かし直しで移行は当てない(移行を足したら up を打ち直す)
  • 動き出したら、Worker の URL と、R2 のバインディングごとに、手元の S3 の口・バケット名・手元の鍵を示す(REQ-015)
  • 待ち受けのポートは、設定の dev.port、無ければ Wrangler の既定(8787)。使えなければ、理由を示して止まる
  • 待ち受けのアドレスは、設定の dev.ip、無ければ 127.0.0.1(手元の鍵は秘密でないので、既定ではほかの機械から届かないようにする)
  • 同じプロジェクトで --env local up がすでに動いていれば、2 つ目は何もせずに止まり、動いているものの URL を示す(同じ手元のデータを 2 つが同時に書かないため)

REQ-015手元の S3 の口(R2 の代わり)

  • --env local up は、設定のすべての R2 バインディングについて、手元の S3 の口を開く。Wrangler の手元の口(local_dev.experimental_s3_credentials の働き)を使い、設定ファイルは書き換えない(REQ-002)
  • 口は Worker のバインディングと同じ中身を読み書きする(バインディングで置いたものが口で見え、口で置いたものがバインディングで見える)
  • 口が受ける操作は、Wrangler の手元の口のとおり(GetObject・HeadObject・PutObject・CopyObject・DeleteObject・DeleteObjects・ListObjectsV2・分割アップロードなど)。署名は AWS Signature Version 4 で、ヘッダの署名と、URL に署名を載せる署名付き URL の両方が通る。鍵や署名が合わなければ拒む
  • 手元の鍵は次の順で決める
    1. 設定の R2 バインディングに local_dev.experimental_s3_credentials が書いてあれば、それ(Wrangler の決まりを優先する)
    2. 環境変数か .env.local の WRANGLER_COMPOSE_R2_ACCESS_KEY_ID・WRANGLER_COMPOSE_R2_SECRET_ACCESS_KEY(Cloudflare の環境の API キーと同じ名前。環境変数を優先する)
    3. どちらも無ければ、wrangler-compose の決まった値
  • 口の URL は http://<アドレス>:<ポート>/cdn-cgi/local/r2/s3(パス形式)、バケット名は設定の bucket_name、地域は auto。アプリが本番と手元で変えるのは、口の URL と鍵だけで済むようにする(up がこの 3 つを示す)
  • Wrangler の版によって手元の口の設定の書き方が違うときは(Wrangler 5 で dev の下へ移る)、wrangler-compose が版に合わせる。合わせ方の分からない版なら、口を開かずに動かし、そのことを示す

REQ-016local の down(止める・手元のデータを消す)

  • --env local down は、同じプロジェクトでほかの端末から動かしている --env local up を止める。手元のデータは残す。動いていなければ、そう示して何もしない(失敗としない)
  • --env local down は打ち直しの確かめを求めない(止めるのは動いているプロセスだけで、データは消さないため)
  • --env local down --purge は、手元のデータ(.wrangler/state/。D1・R2 に加えて、KV・Durable Objects など Wrangler が手元に置いたすべて)を消す。up が動いていれば先に止める
  • 消す前に、消すもの(置き場のフォルダ、D1 ごとの表の数、バケットごとのオブジェクトの数)を示し、local を打ち直して確かめる。打ち直しを受けられない場では止まる(REQ-005 と同じ。決めること 1)
  • 手元のデータだけを消す。.wrangler/ のほかのもの(Wrangler の組み立ての一時ファイルなど)と、プロジェクトのファイルには触れない

REQ-017local の backup・restore(手元を控える・手元へ戻す)

  • --env local backup は、手元の D1・R2 の中身を、REQ-007 と同じ形(目録・D1 の SQL と移行の履歴・R2 のオブジェクトとメタデータ)で <書き出し先>/local/<日時>/ に書き出す。書き出し先の決まり・git の確かめ・書きかけの扱いは REQ-007 と同じ
  • --env local restore [--drop] <控えのフォルダ> は、REQ-008 と同じ決まり(空でなければ止まる・--drop で入れ替える・打ち直しは local・控えのあとの移行を当てる・書きかけの控えは戻さない)で手元へ戻す
  • 控えはどの環境で取ったものでもよい。バインディングの名前で照らす(staging や production の控えを手元に戻して開発できる)。戻す前に、控えを取った環境名を示す
  • 逆に、手元の控え(backups/local/…)を Cloudflare の環境へ戻すこともできる(REQ-008 のとおり。手元で作ったデータで staging を埋めるなど)
  • 手元では入れ物を作る段が要らない(Wrangler が使うときに作る)。REQ-008 の「戻す先が無ければ止まる」は local には当てはめない
  • R2 は手元の S3 の口で読み書きする。API キーは要らない(手元の鍵を使う)。--env local up が動いていればその口を使い、動いていなければ、操作の間だけ手元で Worker を動かして口を開き、終われば止める(up を打っておかなくてよい)
  • 戻している間に up が動いていれば、Worker から欠けたデータが見えうる。REQ-008 と同じく、始める前にそのことを示す

REQ-018compose ファイル(複数の Worker をまとめる)

docker compose の compose.yaml に寄せた書式で、複数の Worker を 1 つのプロジェクトにまとめる。

# wrangler-compose.yaml
name: shop                     # 省略すると compose の根のフォルダ名(docker と同じ)

services:
  web:
    build: ./web               # Wrangler の設定ファイルのあるフォルダ
    ports:
      - "8787:8787"            # 手元の待ち受け(--env local のときだけ使う)
    depends_on:
      - api                    # api を先に建て・先に動かす
  api:
    build:
      context: ./api
      config: wrangler.jsonc   # docker の dockerfile に当たる。省略すると wrangler.jsonc → .json → .toml
    ports:
      - "127.0.0.1:8788:8788"

x-notes: 何を書いてもよい      # x- で始まるキーは読み飛ばす(docker と同じ)
  • ファイル名は wrangler-compose.yaml(wrangler-compose.yml も読む。両方あれば止まる)。docker compose の compose.yaml とは別の名前にし、同じリポジトリに両方を置ける
  • いまのフォルダから上へたどって最初に見つかったものを使う。ファイルを選ぶ引数(docker の -f)は持たない(何を扱うかは --env で切り替える。利用者の決定)。見つからなければ、いまの決まり(いまのフォルダから上へたどって最初の Wrangler の設定ファイル 1 つ)で動く
  • 環境ごとに compose ファイルを分けない(wrangler-compose.staging.yaml のようなものは持たない)。環境ごとの違いは、各サービスの Wrangler の設定の env.<環境名> が持つ
  • 受けるキー(docker compose と同じ名前・同じ意味)
    • name: プロジェクトの名前。表示と控えの目録に使う
    • services.<名前>: サービス。名前は docker と同じ決まり(英小文字・数字・-・_)
    • build: 文字列なら Wrangler の設定ファイルのあるフォルダ(compose ファイルからの相対)。context(フォルダ)と config(そのフォルダの中の設定ファイル名。docker の dockerfile に当たる)を持つ形も受ける
    • ports: 手元の待ち受け。docker の短い書き方 "[アドレス:]手元のポート:中のポート" を受ける。Worker には中のポートが無いので、2 つのポートは同じ数にする(違えば止まる)。--env local のときだけ使う。1 つのサービスに 1 つだけ
    • depends_on: 先に建て・先に動かすサービスの一覧。docker の長い書き方(condition: service_started)も受ける。ほかの condition は止まる
    • x- で始まるキー(どの階層でも): 読み飛ばす
  • 上に無いキー(image・environment・env_file・volumes・networks・profiles・secrets など)があれば、何もせずに止まり、そのキーと理由を示す(環境の値は Wrangler の設定が持つ。REQ-002)。docker と違って黙って読み飛ばさない(効くと思って書いたものが効かないのを防ぐ)
  • 2 つのサービスが同じ Wrangler の設定ファイルを指す、または depends_on が輪になる、無いサービスを指すときは、止まる
  • Wrangler は compose の根の package.json に入れた版を、すべてのサービスで使う(1 つのプロジェクトに Wrangler は 1 つ)。サービスのフォルダに自分の package.json があれば、その依存は nv で揃えてから組む

REQ-019複数の Worker と Cloudflare の環境

  • --env <環境名> はすべてのサービスに同じに効く。選んだサービスのどれかの設定にその環境が無ければ、何もせずに止まり、無いサービスを並べて示す
  • build [サービス…]・up [サービス…] は、指定したサービスと、その depends_on をたどった先を、依存の順(依存される側が先)に行う。何も指定しなければすべて。docker compose の up と同じく、依存先も一緒に建てる
  • up は、サービスごとに REQ-004 の段(移行 → デプロイ)を行う。途中のサービスで止まったら、それより後のサービスは行わず、どのサービスまで済んだかを示す
  • サービスバインディング(services)や Durable Objects の script_name が、同じ compose ファイルのほかのサービスの Worker を指しているのに、depends_on にそのサービスが無ければ、知らせる(順は depends_on だけで決め、勝手に足さない)
  • .env.<環境名> のシークレットは、サービスのフォルダのものをそのサービスの Worker に入れる(REQ-004)。WRANGLER_COMPOSE_ の値(API キー)は、サービスのフォルダ、無ければ compose の根の .env.<環境名> から読む
  • down [サービス…] は、指定したサービスだけを(依存先は含めない。docker と同じ)、依存の逆の順(依存する側が先)に下ろす。何も指定しなければすべて。打ち直しの確かめは全体で 1 度
  • 2 つ以上のサービスが同じ D1(同じ database_id、無ければ同じ名前)・同じバケットを使っているときは、共有している資源として扱う
    • 移行は 1 度だけ当てる。サービスによって移行のフォルダが違えば、何もせずに止まる
    • down --purge で、下ろさないサービスも使っている資源は消さずに止まり、そのことを示す
    • backup・restore は 1 度だけ書き出し・戻す
  • backup は、すべてのサービスの D1・R2 を 1 つの控えにする(目録に、どのサービスのどのバインディングかを書く)。restore はサービスの名前とバインディングの名前で照らす。compose ファイルを使う前の控え(サービス 1 つ)は、サービスが 1 つのプロジェクトにだけ戻せる

REQ-020複数の Worker と local

  • --env local up [サービス…] は、指定したサービスと依存先を手元でまとめて動かす。1 つの Ctrl+C ですべて止まる
  • サービスごとに、ports のアドレスとポートで待ち受ける(どのサービスにも手元の URL がある)。ports が無いサービスは、設定の dev.port、それも無ければ 8787 から順に空いている番号を使う。2 つのサービスが同じポートを書いていれば止まる
  • サービスバインディング・Durable Objects の script_name・Queues などのサービスの間のつながりは、手元でも本番と同じにつながる
  • 手元のデータの置き場は compose の根の .wrangler/state/ 1 つで、すべてのサービスが共有する(同じ名前の D1・バケットは同じ中身が見える)
  • 手元の移行は、共有している D1 には 1 度だけ当てる(REQ-019 と同じ)
  • Worker のログには、docker compose と同じく、行の頭にサービス名を付けて出す
  • 動き出したら、サービスごとの URL と、R2 のバインディングごとの手元の S3 の口を示す。手元の鍵はすべてのサービスで同じ
  • --env local down は、まとめて動いているものをすべて止める(サービスを指定しても、手元では一部だけを止めない。止めるのはまとめて動かしている 1 つのプロセスだから)。down --purge は compose の根の手元のデータを消す

REQ-021手元で使えないものの知らせ

  • 手元で開発するときに使えない、または本番と振る舞いが違う機能を、手元で使えないものに列挙する。何が根拠か(Wrangler の実装・Cloudflare の資料・実測)を項目ごとに書く
  • --env local up(と --dry-run)は、動かす前に、サービスごとの設定を見て、そこにある「手元で使えないもの」を示す。示すもの
    • 手元で動かないバインディング(Vectorize・mTLS・ディスパッチ名前空間など)と、remote: true にすれば Cloudflare の本物につなげること
    • 手元でも常に Cloudflare につながり、料金がかかるバインディング(Workers AI・AI Search・Media・VPC など)
    • remote: true を書いたバインディングと、それが設定の一番上の階層の ID(本番かもしれない資源)につながること
    • 手元では効かない設定(ルート・カスタムドメイン、Cron が自動では動かないこととその試し方、配置・上限、ログの送り先など)と、手元での代わり
    • 手元で動かすのに追加の用意が要るもの(Hyperdrive の手元の接続文字列、Containers の Docker)。用意が無ければ何が要るかを示す
  • 知らせるだけで止めない。止まるのは、Wrangler 自身が手元では受けない設定(手元だけのバインディングに remote: true を書いた、手元で動かないバインディングに remote: false を書いたなど)のときで、そのときは Wrangler を動かす前に理由を示して止まる
  • 見分け方は、使う Wrangler の版の決まりに合わせる。wrangler-compose が知らない種類のバインディングがあれば、「分からない」と示す(黙って手元で使えるとはみなさない)

決めること(利用者)

  1. --env local down --purge を、端末でない場(エージェント)から打てるようにするか。案 A(推奨): いまの決まりと同じく、打ち直しを受けられない場では止まる(本番の控えを戻した手元のデータも、消すと戻せないため)。案 B: local だけは --yes で打ち直しを省ける(エージェントが手元を作り直せる)
  2. 手元の鍵の既定の値。案 A(推奨): どの PC・どのプロジェクトでも同じ決まった値(手元でしか通じない。README とスキルに書ける)。案 B: プロジェクトごとに作って .wrangler/ に置く
  3. up を裏で動かす(up -d)を今回持つか。案 A(推奨): 持たない。前面で動かし、ほかの端末から down で止められれば足りる。案 B: 持つ(ログは logs が要るようになる)
  4. compose ファイルの名前。案 A(推奨): wrangler-compose.yaml(docker の compose.yaml と同じリポジトリに置ける)。案 B: compose.yaml も読む(docker compose と取り合う)
  5. ports の書き方。案 A(推奨): docker の短い書き方 "[アドレス:]ポート:ポート" を受け、2 つのポートは同じ数に限る。案 B: "8787" のように 1 つだけ(docker では 1 つだけ書くと「中のポート」の意味になり、意味が食い違う)
  6. 知らない compose のキー。案 A(推奨): 止まる。案 B: docker のように知らせて読み飛ばす

範囲外

  • Node・npm の取得と版の管理(nv が受け持つ)
  • 状態の一覧(ps)、Cloudflare の環境のログの表示(logs)、手元の up を裏で動かすこと(up -d)。必要になったら足す(Wrangler の操作そのものは nv run wrangler … で行える)
  • R2 の公開の URL(r2.dev・独自ドメイン)を手元で再現すること。手元では Worker を通すか、手元の S3 の口の署名付き URL で配る
  • compose ファイルの、docker compose にあって wrangler-compose が受けない機能: profiles・extends・include・-f(ファイルの指定と重ね合わせ。--env が受け持つ)・変数の差し込み(${VAR})・environment・env_file・volumes・networks・scale。必要になったら足す
  • backup・restore をサービスで絞ること(控えはプロジェクト全体で 1 つ)
  • 手元でサービスの一部だけを止める・入れ替えること
  • 手元の KV・Queues・Durable Objects の控え(local down --purge では消える)
  • 設定で remote: true にしたバインディング(手元の開発から Cloudflare の資源につなぐもの)。Wrangler の振る舞いに従い、wrangler-compose は手を加えない
  • R2 の CORS・ライフサイクルの設定(Wrangler の設定ファイルに書けない、バケットごとの設定のため。nv run wrangler r2 bucket cors … などで行える)
  • D1・R2 以外の資源(KV・Queues など)の控えと消去。Durable Objects のデータの控え(消えるのは down で Worker と一緒に。REQ-005)
