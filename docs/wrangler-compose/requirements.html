wrangler-compose 要求仕様

docker compose のように手元で開発し、それを安全に Cloudflare(リモート)へ展開する道具。この頁は「何ができるべきか」だけを書く。どう作るか(どの道具を中で使うか)は設計で決める。

定義

(利用者の決定。すべての要求はこの定義から決める。定義するのはここまで)

  1. wrangler-compose は、docker compose のように「手元(local)で開発したサービス」を、安全に「リモート(Cloudflare の環境)へ展開する」ためのもの。
  2. wrangler-compose は、内部では Wrangler が稼働している。
  3. wrangler-compose は、ほかの wrangler-compose のアプリと一切の資源を共有せず、プロジェクト(compose ファイル)の単位で分離している。
  4. wrangler-compose は、Cloudflare への操作を Wrangler のコマンドと Cloudflare の API で行う。ただし、使える API は wrangler login で付与される API のみとする。(2026-10-13)

これをどう使うかは、使うアプリの側の責任である。

理念(docker compose から)

  • ファイルが唯一の正: アプリの構成は compose ファイルだけが持つ。compose ファイルとコードと .env.<環境> があれば、どこでも同じものが建つ
  • コマンド 1 つで揃う: 書いたあとは up だけで動く。人が手で行う段取りを持たない
  • 宣言した状態に合わせる: up は何度打っても同じ結果になり、変わったところだけを変える
  • 作り直せるものとデータを分ける: down はデータを残し、データは明示したときだけ消す
  • 論理名で書き、名前で呼び合う: compose ファイルにはサービスの名前だけを書き、サービスは互いを名前で指す。実際の名前は道具が決める
  • 環境を混ぜない: 1 つの環境のものは、すべてその環境の中で動く。手元のものがリモートの資源に触れることも、その逆もない
  • 1 つの compose ファイルが 1 つの塊: 1 つの compose ファイル(プロジェクト)は、それだけで完結した 1 つの塊として動く。その中のサービスは、compose ファイルに書いたつながり(bindings・consumes)で、互いの資源(D1・R2・KV・Queue・Worker の呼び出し)を使う。塊の外(別の compose ファイル・別のプロジェクト)のものとは、資源を一切共有しない。プロセス・待ち受けのポート・データの置き場・Worker の呼び出し先の登録(Wrangler の dev registry)も共有しない(docker compose のプロジェクトどうしが混ざらないのと同じ)

使い方の流れ

wrangler-compose --env local up              # 手元で開発する(全サービスが手元で動く)
wrangler-compose --env staging --dry-run up  # staging に何が起きるかを見る
wrangler-compose --env staging up            # 手元で動いたものを staging へ展開する
wrangler-compose --env production --dry-run up
wrangler-compose --env production up         # 同じものを本番へ展開する

compose ファイルの例

# wrangler-compose.yaml
name: shop

services:
  web:
    type: worker
    build: ./web                    # Worker のコードのフォルダ
    compatibility_date: "2026-09-01"  # どの日付の Workers の動き方で動かすか(必須)
    ports: ["8787:8787"]            # 手元の URL
    routes: ["${WEB_DOMAIN}"]       # 環境ごとの値は .env.<環境> から展開する
    depends_on: [api]
    bindings:
      API: api                      # 相手が worker なら、その Worker を呼べる
      FILES: storage.files          # <サービス>.<バケット>

  api:
    type: worker
    build: ./api
    compatibility_date: "2026-09-01"
    ports: ["8788:8788"]
    depends_on: [db, storage, cache, jobs]
    bindings:
      DB: db                        # 相手の型で、つながり方が決まる
      FILES: storage.files
      UPLOADS: storage.uploads
      CACHE: cache
      JOBS: jobs                    # queue へ送る
    consumes: [jobs]                # queue から受け取る
    durable_objects: [Counter]      # この Worker のコードにあるクラス
    environment:                    # Worker に渡す秘密でない値(docker compose と同じ。NAME=値 の並びでもよい)
      GREETING: hello
    secrets: [STRIPE_KEY]           # 値は .env.<環境> の STRIPE_KEY。Worker からは env.STRIPE_KEY

  db:
    type: d1
    migrations: ./api/migrations

  storage:
    type: r2
    ports: ["9000:9000"]            # 手元の R2 の口(S3 互換の API・公開の URL)
    buckets:                        # 複数のバケット。1 つなら省略形でもよい(REQ-002)
      files:
        public: true                # 公開の URL で配る
        cors:
          - origins: ["${WEB_ORIGIN}"]
            methods: [GET, PUT]
      uploads:
        lifecycle:
          - prefix: tmp/
            expire_after_days: 7
        notifications:
          - queue: jobs
            events: [object-create]

  cache:
    type: kv                        # 省略形: このサービスが KV 名前空間 1 つ

  jobs:
    type: queue
# .env.staging(git の外)
WEB_DOMAIN=staging.shop.example.com
WEB_ORIGIN=https://staging.shop.example.com
STRIPE_KEY=sk_test_...

決定(利用者)

  • 定義: docker compose のように手元で開発したサービスを、安全にリモートへ展開するためのもの(最も重要)
  • コマンドと書式は docker compose に合わせる。勝手に足したり変えたりしない
  • 何ができるべきかから決め、中で使う道具の都合で要求を変えない
  • 人が手で行う段取り(設定を手で書き足す、値を手で入れる、資源を手で作る、API キーを手で発行する)が要る形にしない
  • docker compose の image の代わりに type を置き、Worker も D1・R2・KV・Queue もサービスとして並べる。型は worker・d1・r2・kv・queue
  • 主に使うのは Workers・D1・R2・KV・Queues・Durable Objects・シークレット。使うものだけを作り、作るものは本物と互換にする
  • 手元では、ふつうのプロダクトを作るのに無いと困る機能を本物と同じに提供する。ほとんど使わない機能は再現しない
  • Cloudflare の操作には Wrangler と Cloudflare の API を使う。使える API は wrangler login で付与される API のみ(2026-10-13。2026-10-12 の決定を改める)
  • リモートの環境の Worker は、利用者のサービスのものだけ(2026-10-12)
  • 環境の違いは、compose ファイルの中の変数(${VAR})を .env.<環境> から展開して表す。切り替えの口は --env 1 つ
  • 手元とリモートを混ぜない。1 つの環境のものは、すべてその環境の中で動かす
  • 1 つの compose ファイルが 1 つの塊。中のサービスはつながり(bindings・consumes)で互いの資源を使い、塊の外(別の compose ファイル・別のプロジェクト)とは、プロセス・ポート・データの置き場・Worker の呼び出し先の登録を含めて資源を一切共有しない(2026-10-12)
  • Worker のフォルダには、環境に依存しない組み立てのためのものだけを置いてよい。振る舞いに関わる設定は書けない
  • シークレットは Worker ごとのシークレットとして入れる
  • r2 のサービスにも ports を書ける。そのポートが手元の R2 の口(S3 互換の API とバケットの CORS・公開の URL)になる
  • 実際の名前は既定では道具が環境の名前を付けて決め(<プロジェクト>-<環境>-<サービス>、複数形は <プロジェクト>-<環境>-<サービス>-<名前>)、name に書けばそれを使う
  • D1・R2・KV・Queue は、1 つのサービスに複数を名前つきで定義できる。1 つなら省略形で書いてよく、そのときの名前はサービスの名前から決まる
  • R2 のバケットの設定(公開・CORS・ライフサイクル・通知・ロック・保管の種類)は compose ファイルにバケットごとに書き、手元にもリモートにも同じに入れる
  • down はデータを残し、データは --purge のときだけ消す。手元の --purge も、リモートと同じく環境名を打ち直して確かめる
  • Queue の受け手の細かい設定は今は持たず、Cloudflare の既定に任せる
  • Node・npm の扱いは nv が受け持つ。GitHub の Release で nv と一緒に配り、更新とエージェント用のスキルは nv に寄せる

要求

REQ-001compose ファイル

  • 名前は wrangler-compose.yaml(.yml も読む。両方あれば止まる)。いまのフォルダから上へたどって最初に見つかったものを使う。見つからなければ止まり、書き始め方を示す
  • 書式は YAML で、docker compose の compose.yaml に寄せる: 一番上に name・context・services
  • context は、Wrangler と Node の版を決める package.json のあるフォルダ(compose ファイルから見た相対)。省くと compose ファイルのあるフォルダ。compose ファイルを展開用のフォルダに置き、コードと依存は別のフォルダに置けるようにする(docker compose の build.context と同じ考え)。package.json が無ければ止まる。ほかのパス(build・assets・migrations)はこれまでどおり compose ファイルから見た相対で、.env.<環境>・.wrangler/compose/・backups/ も compose ファイルのあるフォルダに置く
  • name を省くと、compose ファイルのあるフォルダ名。プロジェクトとサービスの名前は、英小文字・数字・- だけ
  • x- で始まるキーは、どの階層でも読み飛ばす(docker と同じ)
  • 知らないキー、型に合わないキー、無いサービスを指すもの、depends_on の輪は、何もせずに止まり、どこ(services.web.image など)の何がいけないかを示す
  • compose ファイルは環境によらず 1 つ。環境の違いは変数の展開(REQ-004)だけで表す

REQ-002サービスの型

型書けるキー建つもの
workerbuild(必須。コードのフォルダ)・compatibility_date(必須)・name・ports・depends_on・bindings・consumes・durable_objects・secrets・environment・routes・crons・compatibility_flags・assetsWorker 1 つ
d1省略形: name・migrations(移行の SQL のフォルダ)。複数形: databases.<名前> の下に同じキーD1 データベース 1 つ以上
r2ports(手元の R2 の口)。省略形: バケットのキー。複数形: buckets.<名前> の下にバケットのキー。バケットのキーは name・public・cors・lifecycle・notifications・lock・storage_class・jurisdictionR2 バケット 1 つ以上
kv省略形: name。複数形: namespaces.<名前> の下に nameKV 名前空間 1 つ以上
queue省略形: name。複数形: queues.<名前> の下に nameQueue 1 つ以上
  • 省略形と複数形: d1・r2・kv・queue は、1 つのサービスに資源を複数定義できる(複数形。buckets・databases・namespaces・queues の下に名前を付けて並べる)。1 つだけなら、サービスそのものを 1 つの資源として書いてよい(省略形。資源の名前はサービスの名前)。1 つのサービスで両方は書けない
  • 複数形で並べる名前は、そのサービスの中で重ならなければよい(サービスの名前はプロジェクトの中で重ならないので、<サービス>.<名前> の組で必ず 1 つに決まる)。英小文字・数字・- だけ
  • name は Cloudflare での実際の名前(REQ-006)。省けば道具が決める
  • R2 のバケットのキーは、本物の R2 のバケットの設定と同じ意味を持つ: public(公開の URL で配る)・cors(CORS の決まり)・lifecycle(期限で消す・保管の種類を変える)・notifications(変化を同じプロジェクトの Queue へ送る)・lock(消せない期間)・storage_class(保管の種類)・jurisdiction(置き場の管轄)。どれも手元でも同じに効く(REQ-009)
  • environment は Worker に渡す秘密でない値(Wrangler の vars)。docker compose と同じく「名前: 値」の対応表か NAME=値 の並びで書き、名前だけなら同じ名前の変数から取る。routes はルート・カスタムドメイン(変数が空で空になった要素は書かなかったことにする。ports があって routes が空の Worker は workers.dev で公開されるので、["${DOMAIN:-}"] と書けば、ドメインを書いた環境はそのドメイン、書かない環境は workers.dev になる)、crons は定期実行の式、assets は静的なファイルのフォルダ、compatibility_flags は Workers の互換の指定
  • compatibility_date は、Worker をどの日付の時点の Workers の動き方で動かすかを決める日付(例 "2026-09-01")。Cloudflare は動き方の変更を日付ごとに区切り、Worker はその日までの変更だけを受ける。省くと動かした日の日付になり、手元とリモート・動かした日ごとに動き方が変わりうるので、必須とする(利用者の決定)。無ければ止まる
  • durable_objects は、その Worker のコードにある Durable Object のクラス名の一覧(Durable Objects は Worker の中のものなので、型にはしない)
  • 型は使うものから足す。足すときは、手元で本物と互換に動く手立てを同時に決める

REQ-003つながり

  • Worker の bindings は「名前: 相手」。Worker のコードからは env.<名前> で見える
  • 相手の書き方: 省略形のサービスはサービスの名前(cache)、複数形のサービスの資源は <サービス>.<資源の名前>(storage.files)、Worker の Durable Object は <worker>.<クラス>(api.Counter)。複数形のサービスを名前だけで指すと止まる
  • 相手の型でつながり方が決まる: worker → その Worker を呼べる、d1・r2・kv → その資源を読み書きできる、queue → その Queue へ送れる、Durable Object → それを使える
  • consumes は、その Worker が受け取る Queue の一覧(書き方は上と同じ)
  • つながる相手は、depends_on に書かなくても先に建てる。depends_on はそれに足す順
  • つながりは、手元でもリモートでも同じに働く

REQ-004環境ごとの値

  • compose ファイルの文字列の中の ${VAR} を展開する。書き方は docker compose と同じ: ${VAR}・${VAR:-既定}・${VAR:?説明}・$$
  • 値は環境変数、次にプロジェクトの .env.<環境>(--env で選んだもの)から読む
  • 既定の無い変数が無ければ、何もせずに止まり、無い変数をまとめて示す
  • 道具が値を決める変数(WC_ で始まる)がある。WC_R2_<サービス>_S3(複数形のバケットは WC_R2_<サービス>_<名前>_S3。名前は英大文字にし - は _)は、その R2 のバケットの S3 互換の API の接続先(パス形式でバケット名まで): 手元は http://127.0.0.1:<ports>/cdn-cgi/local/r2/s3/<資源の名前>(r2 のサービスに ports が要る)、リモートは https://<CLOUDFLARE_ACCOUNT_ID>[.<jurisdiction>].r2.cloudflarestorage.com/<実際の名前>。Worker が S3 互換の API で R2 を読み書きするとき、接続先を人が環境ごとに書かずに済むようにする(利用者の決定。2026-10-12)。使えるのは Worker の environment の値だけで、ほかの場所・無いバケット・決まらないとき(手元で ports が無い、リモートでアカウントの ID が無い)は止まる。${X:-${WC_R2_STORAGE_S3}} のように既定にも使える
  • WC_R2_<サービス>_S3_KEY・WC_R2_<サービス>_S3_SECRET は、手元の S3 互換の API の鍵。鍵はプロジェクトごとの乱数で、道具が作って .wrangler/compose/local/s3-keys.json(本人だけが読める)に置き、画面には出さない。秘密の値なので、使えるのは Worker の secrets の値だけ。リモートの鍵(R2 の API トークン)は道具が作れない(Wrangler に無い)ので、${R2_KEY:-${WC_R2_STORAGE_S3_KEY}} のように .env.<環境> の変数で渡し、無ければ止まる(利用者の決定 2026-10-12。決まった鍵は誰でも知っているので、LAN に開いた口が誰にでも読み書き・削除される)
  • .env.<環境> は git に入れない。git の中で .gitignore で外れていない、またはすでに git に入っていれば止まる

REQ-005シークレット

  • Worker の secrets に、environment と同じ形で書く: 「名前: ${変数}」の対応表か、名前の並び(同じ名前の変数から取る)。名前は Worker から見える名前(env.<名前>)。値は REQ-004 と同じ探し方で読む
  • シークレットの値は必ず変数から取る。compose ファイルに値を書くと(変数を含まない値・NAME=値 の並び)止まる。シークレットが git に入らないため
  • その Worker の secrets に書いたものだけが、その Worker から見える
  • 0.1.7 までの書き方(Worker の vars、一番上の secrets と environment: <変数名>)は、書き直し方を示して止まる(利用者の決定。2026-10-12: docker compose の一番上の secrets はファイルとして渡すための仕組みで、Workers では名前が 3 つになるだけ)
  • up が、手元でもリモートでも、その Worker のシークレットとして入れる。compose ファイルから消したシークレットは、up が消す
  • 値が無ければ止まり、無い変数の名前を示す

REQ-006環境

  • 環境は --env で選ぶ。local は手元、それ以外はリモート(名前は自由。pr-123 のように並べて建てられる)
  • リモートの Worker と資源の Cloudflare での名前は、既定で環境の名前を付けて道具が決める: Worker は <プロジェクト>-<環境>-<サービス>、資源は <プロジェクト>-<環境>-<資源の名前>。資源の名前は、省略形はサービスの名前、複数形は <サービス>-<名前>(例: 省略形の cache は shop-staging-cache、storage の files は shop-staging-storage-files)。同じアカウントに環境を並べても名前がぶつからない(利用者の決定)
  • 決めた名前が Cloudflare の名前の決まり(長さなど)に合わなければ、何もせずに止まり、name で短い名前を書くよう示す
  • name を書けば、その名前を使う(既存のものを使う、環境ごとに ${VAR} で変えるなど)。同じ名前のものがすでにあれば、それを使う(作り直さない)
  • 手元では、資源の名前(cache・storage-files など)をそのまま使う
  • リモートの環境は、.env.<環境> に CLOUDFLARE_ACCOUNT_ID=<アカウントの ID> を書いたアカウントでだけ操作する(--dry-run も含むすべての操作)。書いていなければ、何もせずに止まり、ログインで使えるアカウントを示す。環境変数の CLOUDFLARE_ACCOUNT_ID がそれと違うとき、ログインがそのアカウントを使えないときも止まる。意図しないアカウントへの展開・削除を防ぐため(利用者の決定。2026-10-12)。手元では要らない
  • 違う環境どうしは混ざらない。ID などの実際の値は道具が扱い、利用者は書かない。別の PC からでも、同じ環境の同じ資源につながる
  • 1 つの環境のものは、すべてその環境の中で動く。手元のものがリモートの資源に触れる、リモートのものが手元に触れる、ということをしない(道具が中で行うことも含む)

REQ-007Worker のフォルダ

  • Worker のフォルダ(build)には、コードと、環境に依存しない組み立てのためのもの(どのファイルから組み立てるか、組み立ての手順など)だけを置いてよい
  • 振る舞いに関わる設定(名前・つながり・値・ルート・定期実行・環境など)がフォルダの中にあれば、何もせずに止まり、compose ファイルのどこに書くかを示す
  • 道具はプロジェクトのファイルを書き換えない。道具が作るものは、プロジェクトの中の決まった場所(.wrangler/compose/)に置く。git のリポジトリの中なら、そこが git から外れていなければ止まる。リポジトリでなければ確かめない(2026-10-13)

REQ-008build

  • build [サービス…] は、docker compose の build と同じく、Worker を組み立てるだけで、何も建てない・動かさない
  • 組み立てたものは環境によらず同じ。環境ごとの値は組み立てたものに入れず、up が環境に合わせて渡す
  • 組み立てられなければ、どのサービスがなぜかを示して止まる

REQ-009up(手元)

  • --env local up は、Cloudflare に触れず(ログインも網も要らず)、すべてのサービスを手元で動かす。前面で動き、Ctrl+C ですべて止まり、何も残さない
  • 手元では、ふつうのプロダクトを作るのに無いと困る機能を、本物と同じに提供し、同じに振る舞わせる(動作が違えば手元で開発する意義が薄れるため。利用者の決定)。本物にあって手元の模擬に無いものは、道具のサービス(REQ-017)で補う
  • 実際のプロダクトでほとんど使わない機能は、手元で再現しない(利用者の決定)。再現しないものは 手元で使えないものに理由とともに書く
  • r2 のサービスに ports を書くと、そのポートが手元の R2 の口になる: S3 互換の API(署名付き URL を含む)は http://127.0.0.1:<ポート>/cdn-cgi/local/r2/s3 で、CORS はバケットの cors どおりに答える。public: true のバケットは http://<バケット名>.localhost:<ポート>/<キー> で配る(利用者の決定)。ports が無いと CORS と公開の URL は本番と同じにならず、up がそのことを知らせる
  • ports にアドレスを書いて外(LAN)にも開いた口(0.0.0.0:9050:9050 など)は、ほかの機械(HMD・スマートフォン・別の PC)から、その機械のアドレスで届いた要求にも同じに応える。そのアドレスで作った署名付き URL は通り、署名が合わなければ本物と同じに拒む(利用者の決定 2026-10-12「LAN経由で動作しなければ意味がないです」)。ほかの機械が届くのは IP アドレスで、名前(DNS の名前)で届いた要求は手元の模擬と同じに拒む(悪いページが自分の名前を 127.0.0.1 に向け直して手元の口を読むのを防ぐ。利用者の決定 2026-10-12)
  • R2 は、手元でも本物と同じに使える: バインディングの API、S3 互換の API(署名付き URL を含む)、CORS、公開の URL、イベント通知(Queue へ)。ライフサイクル・オブジェクトのロック・保管の種類は手元では再現しない(リモートには設定を入れる)(利用者の決定)
  • D1・KV・Queue は、ふだん使う API(読み書き・一覧・一括処理・移行・送受信・やり直しなど)を手元でも本物と同じに使える。Queue の受け手は、手元でも本物の既定値(1 回にまとめる数 10・待つ時間 5 秒・やり直し 3 回)で動く。D1 の上限の一部・KV の結果整合・Queue の同時処理などは手元で再現しない(手元で使えないものに理由とともに書く)(利用者の決定)
  • それでも本物と違うところは、手元で使えないものに理由とともに書き、無くしていく(REQ-018)
  • 同じ資源を使うサービスが同時に書いても、データが失われない
  • ports を書いた Worker は、それぞれその手元の URL で応える
  • コードが変われば組み立て直して動かし直す。移行は動かす前に当てる
  • 手元のデータは down では残り、down --purge で消える
  • 同じプロジェクトで 2 つ目の --env local up は止まる。ほかの端末からの --env local down で止められる
  • 別のプロジェクトの --env local up とは、同時に動かせる(定義 3)。ports のポートをほかのもの(別のプロジェクト・ほかのプログラム)が使っているときは、その通信を横取りせず、何も動かさずに止まり、どのポートかを示す

REQ-010up(リモート)

  • リモートの up は、手元と同じ組み立てたもの(REQ-008)を展開する。組み立てたものが無ければ組み立て、--build なら組み立て直す(docker と同じ)
  • 依存の順に: 資源が無ければ作る → 移行を当てる → シークレットを入れる → Worker を展開する
  • 何度打っても同じ結果になる。変わっていないものは変えない
  • 移行が失敗したら、その D1 を使う Worker は展開しない。どこまで済み、どこでなぜ止まったかを示し、それより後は行わない
  • compose ファイルから消えたサービスの Worker は示すだけで、--remove-orphans のときだけ消す(docker と同じ)。データは消さない
  • 移行を当てるときに確認を求めない

REQ-011down

  • down [サービス…] は Worker を依存の逆の順に下ろし、データは残す。そのあとの up で元に戻る
  • down --purge [サービス…] はデータも消す。下ろさないサービスがつながる資源は消さずに止まる
  • 消す前に消すもの(Worker・資源の名前と中身の数)を示し、環境名を打ち直して確かめる(手元の --purge も)。打ち直しを受けられない場では止まる。手元の down(データを消さない)は確かめない

REQ-012ps・logs

  • ps は、サービスごとの状態(あるか・動いているか・URL・未適用の移行)と、compose ファイルとの違い(足りないもの・残っているもの)を示す。何も変えない
  • logs [-f] [サービス…] は、Worker のログを docker compose と同じく行の頭にサービス名を付けて出す。手元でもリモートでも同じ

REQ-013backup・restore

  • backup は、その環境の D1・R2・KV の中身を手元のフォルダ(既定は backups/<環境>/<日時>/)へ書き出す
  • restore <控え> は、サービスの名前で照らしてその環境へ戻す。戻す先が空のときだけ戻し、--drop ならいまの中身を消してから戻す(打ち直しで確かめる)。戻したあと、控えのあとの移行を当てる
  • 控えはどの環境のものでも、どの環境へでも戻せる。データは控えのファイルを間に置いて移す(移し元の中で書き出し、移し先の中で読み込む)
  • リモートの環境の中身は Wrangler のコマンドか Cloudflare の API で書き出し・読み込む
  • 控えは git に入れない。書きかけの控えは戻さない。Durable Objects・Queue の中身とシークレットは控えない

REQ-014dry-run

  • --dry-run はどの操作にも付き、何も変えずに何が変わるか(作る・変える・消すもの、当てる移行、入れる・消すシークレットの名前、展開した値)を示す。シークレットの値は出さない
  • 本番の操作が止まる条件では、dry-run も同じに止まる

REQ-015安全

  • リモートに展開するのは、手元と同じ組み立てたものだけ(REQ-010)
  • 消す操作は、消すものを示し、環境名の打ち直しで確かめる
  • まだ無い環境への初めての up は、新しく作ることを示して確かめる(環境名の打ち間違いで新しい環境を建てない)
  • シークレットの値を、どの操作でも画面・ログ・控えに出さない
  • .env.<環境> と控えが git に入る形なら止まる

REQ-016手で行う段取りを持たない

  • 利用者が用意するのは、compose ファイル・コード・.env.<環境> だけ。人が行うのは Cloudflare へのログインを 1 度だけ
  • 資源の作成、移行、シークレットの投入、手元の S3 互換の API の鍵など、ほかに要るものはすべて道具が用意する

REQ-017道具のサービス

  • 道具のサービスは手元(--env local)だけに置く。リモートの環境には置かない
  • 以前の版がリモートに置いた道具の Worker(<プロジェクト>-<環境>-wc-data)は、up・down が消す

REQ-018手元と本番の違いの知らせ

  • 手元で動かしたときに本番と振る舞いが違う点を、手元で使えないものに、使う型に絞って列挙する
  • --env local up は、compose ファイルにそれに当たるもの(routes・crons など)があれば、動かす前に、手元ではどうなるか・どう試すかを示す

REQ-019配り方・表示の言語

  • OS ごとの単体の実行ファイルで、nv と同じ Release で配る。nv と同じフォルダに置いて使う
  • メッセージと --help は、nv と同じ決め方で日本語か英語で出す。打ち直しの確かめで打つのは環境名そのもの

範囲外

  • 使わない型(Vectorize・Workers AI・Hyperdrive・Workflows など)。使うときに型を足す
  • docker compose にあって要らないもの: image(type が代わり)・-f(--env が代わり)・profiles・extends・include・networks・volumes・scale・exec・run
  • DNS・WAF・Access などゾーンの設定
  • Wrangler のコマンドでも Cloudflare の API でも行えない操作
